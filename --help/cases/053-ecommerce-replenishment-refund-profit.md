# UC-053：補貨前先查退貨吃掉多少利潤，避免補到賣得多卻不賺錢的商品

- 情境：工作
- 標籤：電商、補貨、退貨、核對
- 網站標題：電商補貨前，讓 Bot 交叉核對銷量、退貨和利潤，找出「賣得好但其實不賺錢」的商品
- 一句話用途：讓 Bot 讀過去半年的銷售、退款與利潤資料，用兩個資料來源互相核對，列出銷量高但退貨率高、幾乎沒有利潤的商品；你在下補貨單前先看這張表，再自己決定買哪些。
- 核心目標：把「銷量好就補貨」的直覺，改成補貨前先看退貨與淨利的書面檢查；Bot 只做分析與建議，下單與付款由人決定。
- 分類／標籤：電商營運／補貨決策／退貨與利潤分析
- 目標使用者：在 Amazon 等平台賣貨、要定期決定補貨量的小型賣家或營運人員
- 首次收錄／最近查證：2026-10-14／2026-10-14（台灣時間）
- 證據狀態：`author-demo`（作者自述實測，X 上單篇貼文）＋ `designed`（自行設計、未實測的提示）
- 是否獨立重現：否。本庫沒有看到作者的資料表、連接設定或實際補貨紀錄。

## 輸入與預期輸出

- 輸入：過去［N］個月的銷售與退款資料（來源例子：Amazon 賣家資料與 Sellerboard 利潤分析工具，兩邊都讀）、目前庫存或即將補貨的商品清單。
- 輸出：
  1. 一張表：每個商品（來源用 ASIN 商品編號）的銷量、退款率、扣掉退款後的實際利潤、兩個資料來源的數字是否一致。
  2. 「高銷量、高退貨、低利潤」的候選清單。
  3. 針對這次準備補貨的商品，標出建議補、暫緩、要再查的理由；數字對不上的地方標「待查」。

## 建議操作流程（本庫設計，未實跑）

1. 先用只讀權限：只給 Bot 讀報表的權限，或乾脆先手動匯出 CSV 上傳；不給下單、改價、改庫存的權限。
2. 先講清楚「利潤」怎麼算：要不要扣平台費、物流費、廣告費、退貨處理費；不清楚的請 Bot 列出它用的公式。
3. 要求兩個資料來源逐項對照，差距超過你設定的門檻就標「待查」，不要自己挑一個數字。
4. 先挑幾個你熟悉的商品手動驗算，確認表格可信，再看全部清單。
5. 補不補、補多少由你決定；下單與付款不交給 Bot。

4. 針對這份補貨候選清單［貼上商品編號］，逐一寫：建議補／暫緩／待查，附理由與數字出處。

## 所需連接、權限與限制

- 需要讀取銷售、退款與費用報表；建議用只讀權限或匯出檔，不要把賣家帳號密碼交給 Bot。
- 下補貨單、付款、改價、改庫存都是對外或有金錢影響的動作，必須由人確認。
- 退款率高可能有季節、批次品質或單一事件等原因；表格只能提示風險，不代表商品一定不該補。
- 平台 API 的可用欄位、授權方式與費用依平台規定，本庫未查證。

## 驗收與可重現性

- 隨機抽幾個商品，手動對回原始報表，銷量、退款與利潤數字一致。
- 兩個資料來源的差距有列出，沒有被悄悄忽略。
- 補貨決定有記錄理由，日後可回頭看該商品之後的實際利潤。
- 本庫未重現；目前只有一位作者的單篇自述。
