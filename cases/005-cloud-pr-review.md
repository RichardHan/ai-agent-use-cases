## 建議操作流程（整理者設計，未實跑）

1. 在測試repo先列需求、變更和完成條件
2. 人批准後才啟動Cloud Agent實作並建PR
3. 協調Bot核對差分與CI
4. Reviewer只讀審查風險、錯誤處理及測試缺口
5. 合併由人決定

## 可複製提示詞（自設未測，非作者原文）

針對我有權使用的測試repo［URL］與需求［功能］，先只讀檢查現況，列出改動計畫、完成條件、測試方式與未知項目。不要開始改碼或啟動付費代理。等我明確批准後，再把核准範圍交給指定Cloud Agent，在獨立分支實作並開draft PR；不部署、不合併、不改權限、不建立憑證。PR產生後，核對每項完成條件及CI，把『已驗證、未驗證、被阻擋』分開。再交給獨立Reviewer只讀審查需求一致性、回歸風險、錯誤處理、資料遷移及測試缺口，在此對話回報，不投稿PR評論。不自動開啟長期監看；缺少憑證或外部資料時停止相關驗證，不能以模擬成功冒充實際寫入。

### 怎麼開始（整理者設計，未測）

1. 先選只有假資料的練習專案，列出需求、完成條件及禁止操作。
2. 使用者確認工具與資料夾權限後，先做單件、人工觸發的檔案交接；不要一開始設成全天自動執行。
3. 實作者交付差分與測試，審查者逐條指出完成條件是否真的有證據。模型同意不取代測試。
4. 若之後批准排程，必須透過真正的排程入口重做相同測試；保存接收、啟動、完成、審查、回報各階段時間與錯誤。
5. 模擬重複任務、半寫檔、工具找不到與執行中斷。先驗證不重複執行及可停止，再考慮擴大範圍。

### 怎麼開始（整理者設計，未測）

1. 先只開 Bot A：在練習 repo 只讀 issue、只建議標籤，不真的貼標籤；人看一週建議是否合理。
2. 標籤規則寫清楚：只有範圍小、可測試、不碰權限與資料遷移的 issue 才算「可自動處理」。
3. Bot B 的審查結果要寫理由；不確定就退回人，不往下派工。
4. 自家電腦只開必要的存取，派給它的工作只能開 draft PR，不能 push 到主分支、不能合併或部署。
5. 人審 PR 與執行紀錄後才合併；誤判的 issue 回頭修正標籤規則。
