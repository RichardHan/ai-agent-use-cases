# UC-014：客服收件匣巡檢與「代理只提出、人核准」的退款／對外回覆

- 情境：工作
- 標籤：客服、收件匣、核准
- 核心目標：讓代理定時掃客服信箱或工單，依既有 playbook 起草回覆、處理技術問題；退款與對外承諾只能「提出請求」，由人逐筆核准。
- 分類／標籤：客服、收件匣、核准流程、小型企業
- 目標使用者：個人創業者、小型 SaaS 或在地服務業者
- 首次收錄／最近查證：2026-10-13／2026-10-13
- 證據狀態：`author-demo`（Grok Bot，作者自述使用；ChatGPT dots，影片僅讀描述）＋ `designed`
- 是否獨立重現：否

## 輸入與預期輸出

- 輸入：客服信箱／工單系統（作者例：Intercom 與 email）、客服 playbook、退款政策。
- 輸出：每輪巡檢的處理摘要；可直接處理的技術回覆；需退款或例外時產生一筆待核准請求；每週 playbook／文件改善建議。

## 建議操作流程（本庫設計，未實跑）

1. 先只讀：拿近 20 封已結案工單，讓代理依 playbook 分類並起草，與實際回覆比較。
2. 定義三類：可直接回覆（低風險 FAQ）、需人審草稿、需核准動作（退款、折扣、帳戶變更、承諾時程）。
3. 初期所有對外回覆都只建草稿；退款永遠走單筆核准，不給代理可自行退款的金鑰。
4. 每輪輸出處理摘要與待核准清單；每週提出 playbook 改進，由人決定是否採用。
5. 穩定後才把「低風險 FAQ」放寬為可送出，並保留抽查。

```
你是客服助理。範圍：［客服信箱／工單系統］最近［24小時］的未結案件；依據：［playbook 連結］與［退款政策連結］。
先只讀並分類：A 可依 playbook 直接回覆、B 需人審草稿、C 需核准動作（退款、折扣、帳戶變更、任何時程或金額承諾）。
A、B 都只建立草稿，不要寄出；C 只整理成待核准清單：客戶、訂單或工單連結、理由、對應政策條款、建議金額。
不得自行退款、改帳戶、對外承諾，不得在社群或公開頻道發文。資訊不足或與政策衝突就標「待確認」，不要猜。
不在輸出中重複完整信用卡、地址等個資。最後在此對話回報：A/B/C 數量、每筆一行摘要、你不確定的地方。
```

## 所需連接、權限與限制

- 需客服系統／郵件的讀取與建立草稿權；退款系統只能經單筆人工核准（S-014A 作者以 Stripe 的 agent action 確認）。不要把付款平台秘密金鑰貼入對話。
- 客戶個資：最小揭露；遵守當地個資法與平台條款。
- 成本：兩個來源皆未提供可靠費用；每小時巡檢會持續消耗用量，先以較低頻率測試。
- 對外回覆、退款、社群發文均屬需另行授權的動作；本研究不構成授權。
