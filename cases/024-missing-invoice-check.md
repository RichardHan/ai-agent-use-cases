# UC-024：找出可能漏開的帳單

- 情境：工作
- 標籤：帳單、對帳
- 網站標題：讓 dots 檢查已交付工作，找出可能漏開的帳單
- 一句話用途：將交付紀錄與開單清單交叉比對，準備待確認的請款草稿。
- 工具：ChatGPT dots／Grok Bot／指定文件與連接
- 證據狀態：dots官方轉述＋Grok Bot作者自報與後續錯誤；未獨立實測
- 查證日期：2026-10-14

- **證據界線：** 官方沒有提供姓名、帳單樣式、會計軟體、稅額處理、收款結果或完整提示詞。以下是由該情境啟發的原創檢查流程。

### 適合誰

接案工作者、自由撰稿人、小型工作室；重點是找出需要本人確認的漏項，不是自動判定債權或替代帳務審核。

### 建議操作步驟（原創，未實測）

1. 從本人挑選的交付記錄與既有開單清單開始，先用去識別化副本試做一次。
2. 以案件編號或明確對應關係比對；名稱近似但無法確定時列入待確認，避免誤判重複或漏開。
3. 對疑似漏項只產出草稿，金額、幣別、付款條件必須來自使用者提供的資料。
4. 本人核對收件人、重複開單與條件。任何寄出、修改帳務系統或催款都是後續另行授權的行動。

### 原創提示詞｜UNTESTED

> 我附上這個月的交付紀錄與已開單清單。請列出「已有明確交付紀錄，但找不到對應帳單」的候選案件，並逐筆引用兩份資料中的依據。證據不足就標待確認，不要判定對方欠款。先針對我選定的案件產出請款草稿；缺少金額、幣別、稅務欄位或付款條件就問我，不自行補值。不要寄信、不要登入付款服務，也不要修改帳務紀錄。

### 權限、費用與限制

- 初次試用可只提供必要資料的副本；避免將銀行資料、稅籍識別碼等不需要的內容帶入範例。
- 如要寄出，需另確認正確收件人與確切內容。官方故事明確保留了批准步驟；不能改寫成「自動發送所有帳單」。
- 費用：適用本頁共通方案說明；第三方帳務工具可能有自己的方案，官方故事未指定工具或價格。
- 編輯建議：不要宣稱符合任何地區電子發票或稅務規範；本案例沒有這方面的驗證。
- 預期可檢查的成果：疑似漏項、比對依據、缺少欄位、待批准草稿。

## Grok Bot貨運版本：先找缺簽收文件，再準備開單（2026-10-14）

[Reddit u/LogieBear46原串](https://www.reddit.com/r/GrokBot/comments/1vya1zs/i_own_a_trucking_company_i_trained_grokbot_for_8/)，英文；由[Bot Store整理頁](https://bot.store/academy/what-people-use-grok-bot-for)追回。原帖日期未核，更新自標「9.1.2026」且稱週二，保留原標記，不自行換算日期。

作者描述從未開單運單列出缺少的POD（交付證明／簽收文件），並依客戶要求準備各停靠站的帳單。後續更新承認金額錯誤、漏存文件及網站操作失效；代理對模糊文件的解釋不是已核根因。未公開帳單與原始紀錄，沒有可核零錯誤或節省工時。本庫未連接貨運系統或操作作者電腦。

### 自設只讀驗收（未實跑）

將虛構運單、交付文件索引與開單清單，以運單ID＋停靠站ID核對。分開「已交付且文件齊全但未開單」「缺POD」「已有帳單」「金額或身分衝突」。不把文件不存在當未交付，也不把有文件當已收款。金額看不清就留待確認，不以相似單據補值。

可貼指令：只讀這三份去識別範例清單，按運單及停靠站逐筆對應，產出缺文件與疑似漏單列表，每項附原始列號、金額來源及未確認欄位。已有帳單不得再建；狀態矛盾就暫停該筆。先交草稿，不登入系統、改派車、算薪資、寄信、付款或發布帳單。抽查所有金額及一對多關係，並對照輸入總筆數，漏讀檔案需列出。

此版本延伸同一交付對開單目的，併入UC024；需要私人郵件、客戶資料或會計寫入時另確認最小權限。原串無可核單次費用或正式合規驗收。
