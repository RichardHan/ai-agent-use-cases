# UC-066：Agent 用量越來越大？請它自己做一週用量稽核

- 情境：開發
- 標籤：排程、用量稽核、多代理、巡檢
- 網站標題：請 Agent 盤點自己一週的用量，找出最浪費的排程
- 一句話用途：用 Agent 自己的用量紀錄、排程執行紀錄與子代理清單，找出「醒來讀完全部背景、卻沒事可報」的排程和沒有標籤的子代理，只提改善建議，不直接改設定。
- 核心目標：在用量或額度變緊之前，弄清楚用量到底花在對話、排程輪詢、子代理還是瀏覽器任務，並排出值得先改的項目。
- 工具：Meta Muse（作者自述；稽核頁本身未寫產品名）；S-066C／D為Grok Bot多Bot團隊盤點
- 目標使用者：已經設了多個 routine／排程與子代理、想知道用量去向的進階使用者
- 首次收錄／最近查證：2026-10-15／2026-10-18 20:43（台灣時間）
- 證據狀態：`author-demo`（作者自述＋公開稽核頁）；本庫提示詞為 `designed`
- 是否獨立重現：否

## 輸入與預期輸出

- 輸入：Agent 可讀到的用量紀錄（每則訊息的輸入／輸出 token）、排程執行紀錄、子代理建立紀錄、上下文壓縮紀錄、目前方案的額度顯示。
- 輸出：一份稽核報告：每日用量、依代理類型分的用量、排程成功率、可疑的計數異常、最浪費的模式、建議修正與下次複查的指標；**不自動改任何排程**。

## 為什麼這個用法值得看

設了很多排程後，空跑可能是浪費來源，但不能預設它一定占最多；應實測區分長工作、協調與定期檢查。這個案例提供了一個可借用的稽核框架：先分「真的在工作」和「空跑」，再看子代理有沒有標用途，最後只拿兩三個指標下週複查。同時也示範了要先檢查數據本身合不合理（超過上下文上限的紀錄不能直接加總）。

## 建議操作流程（本庫設計，未實測）

1. 先問 Agent 它能讀到哪些用量與排程紀錄；讀不到就停，不要讓它猜數字。
2. 指定一段期間（例如最近 7 天）與時區，要求每日用量表與依代理類型的分組。
3. 要求先做**數據健全檢查**：超過上下文上限、明顯累計值、重複紀錄要另列，不混入總數。
4. 找空跑：輸入很大、輸出很小的排程執行；列出排程名稱、頻率、平均載入量。
5. 找沒標用途的子代理與已經不需要但仍在跑的排程。
6. 只產生建議與預估影響，**不自動修改、暫停或刪除排程**；你選定後再逐項改。
7. 一週後用同樣期間長度複查兩三個指標，確認改動有效。

## 可複製提示詞（原創設計，未實測）

請只讀你自己的用量與排程紀錄，對［起日］到［迄日］（［時區］）做用量稽核。先告訴我你實際能讀到哪些紀錄；讀不到的部分寫「無資料」，不要估算。請提供：①每日輸入／輸出用量與訊息數；②依排程、子代理、瀏覽器任務等類型分組；③數據健全檢查：任何單則輸入超過上下文上限或看起來是累計值的紀錄另列，不計入可信總數；④「輸入很大但輸出很少」的排程清單，附頻率與平均載入量；⑤沒有標用途的子代理與看起來已不需要的排程；⑥最多三項改善建議與下週要追蹤的兩個指標。不要修改、暫停、刪除任何排程或子代理，也不要更改方案或購買額度。

## 所需連接、權限與限制

- 只需要讀取 Agent 自己的用量與排程紀錄；不需要外部帳號。改排程、暫停 routine、升級或購買額度都要另外確認。
- 各產品可讀到的用量資料不同；作者的紀錄欄位（例如代理類型、壓縮紀錄）不代表 Grok Bot 或 ChatGPT dots 也有相同資料。S-066B另涉及Muse與Grok Bot郵件合併，但未證明Grok Bot可讀同樣的用量欄位。
- 用量數字依產品計價方式不同，不能直接換算成金額；作者的方案額度顯示方式不代表一般情況。
- 稽核報告可能列出排程名稱與用途，公開分享前先移除帳號、交易、人物等私人資訊。

## 驗收與可重現性

- 隨機抽 3–5 筆被列為「空跑」的排程執行，對照原始紀錄確認輸入／輸出量與內容。
- 檢查總數是否已排除被標為異常的紀錄，並看加總是否吻合每日表。
- 改動後同期間複查指標是否下降；沒有複查數據就不能說「已省下用量」。
- 本庫沒有重現；S-066A未取得修改後複查，S-066B只有作者報告的喚醒前後數，沒有原始日誌。
