# UC-074：事件喚醒後，重新讀取來源資料並核對結果

- 網站標題：量完體重就讓 dots 整理紀錄，收到事件後再核對數據
- 一句話用途：把裝置事件接到 dots，分清「收到通知」與「真正讀到資料」，避免漏報或重複處理。
- 情境：開發
- 標籤：實體裝置、事件觸發、驗收、隱私
- 工具：ChatGPT dots／自建 MCP／MCP Events／Secure MCP Tunnel
- 證據狀態：作者建置自述＋官方協定文件；未獨立重現

## 作者實際做了什麼

來源：[ほだぎ，Zenn，2026-10-09，日文](https://zenn.dev/hodagi/articles/a7db00426b6756)。已讀全文；未取得完整程式、執行日誌或獨立測試。

作者把 Eufy C1 體重計的 BLE 廣播交給 Ubuntu 小主機接收，存入 SQLite，再用自建 MCP 讀歷史。他報告 Webhook 回傳 HTTP 200、dots 也啟動，卻讀不到事件本文；於是改成「事件喚醒→MCP 讀取歷史→計算前後差值→通知」。這是作者當時的整合觀察，不能推定所有 dots 都讀不到事件內容。

## 官方支持與邊界

[OpenAI MCP Events](https://developers.openai.com/plugins/build/mcp-events)（英文，未標發布日，本次讀取）說明可用 dot 測試事件訂閱。2xx 僅表示收到 Webhook，後續非同步處理；事件可能亂序或合併成一次任務。應保留穩定事件 ID、限制重試、驗證簽章，並測試重複事件與停止訂閱。官方要求另驗證實際事件資料與回應，沒有保證作者整套裝置流程。

[Secure MCP Tunnel](https://developers.openai.com/api/docs/guides/secure-mcp-tunnels)（英文，未標發布日，本次讀取）需要可連到 MCP 的主機、隧道與執行用憑證。隧道權限和 ChatGPT 自訂 MCP 權限分開，依組織／工作區設定；不是每個帳號貼一段提示詞就能用。主機向外 HTTPS 連線仍涉及持續服務與資料傳輸。

## 可以怎麼試（本庫設計，未實跑）

先用雲端的虛構非個人測量資料做紙上驗收，不接真實體重計。設計資料表與事件 ID 的對照，將接收、喚醒、讀取、計算、送達分開記錄。事件到達後依唯一紀錄 ID 查回資料；若只能取得「最新兩筆」，須檢查期間是否又有新測量、事件是否亂序，不能把別次測量當成本次。

可直接貼用：

> 只根據我提供的虛構資料，設計事件驅動讀回的驗收方案，不建立服務或訂閱。列出事件 ID、紀錄 ID、發生時間、實際讀取時間、處理狀態及可核對輸出。分別推演重複、亂序、連續兩筆、歷史讀不到、訂閱過期和停止後又收到事件；收到 HTTP 200 不算工作完成。資料缺失就標缺失，不用舊值補造。本次只交付測試表和預期結果，不連接裝置、登入或上傳資料。

## 權限、費用及不適合情境

- 真實實作需要硬體附近的接收主機，純遠端雲端機器不能直接接收家中 BLE。此頁只研究，不要求使用者啟用自己的電腦。
- 真實體重紀錄是敏感資料；需先決定哪些欄位傳給哪個服務、取得明確同意並限制保留時間。不要公開健康資料、Webhook 目的地或簽章秘密。
- 持續憑證、服務設定與權限新增需另外核准；官方文件存在不代表已授權安裝。
- 本次未核完整帳號方案與總費用；需核 dots 可用性、主機運作、用量與隧道相關帳戶條件，不宣稱免費。
- 只做紀錄與算術驗收，不作診斷、醫療決策或安全關鍵即時警報。沒有長期可靠度、漏件率或多人身分辨識證據。
