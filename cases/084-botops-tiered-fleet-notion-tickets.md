# UC-084：BotOps 三層編制：一個總管收件開 Notion 工單，領域 Bot 派臨時工，固定節奏跑看房

- 情境：工作
- 標籤：多代理、Notion、排程、工單
- 網站標題：只跟一個「總管 Bot」說話，工作都變成 Notion 工單，再由領域 Bot 派臨時工去做
- 一句話用途：作者把 Grok Bot 艦隊分成 L1 總管（收件、開工單、回連結）、L2 領域負責人（家務、工作、寫作等）、L3 一次性臨時工與固定節奏執行者；交接靠 Notion 網址不靠聊天紀錄，預設安靜。
- 核心目標：Bot 一多就會淹沒在對話裡；用分層與單一真相來源（Notion）讓人只看工單、不翻 worker 對話。
- 工具：Grok Bot（多 Bot、頻道／swarm、Routines）；Notion（Projects／Tasks）；Cursor 雲端代理（由 L3 啟動）
- 分類／標籤：多代理營運／工單制度／例行排程
- 目標使用者：已經開了 5 個以上 Bot、側邊欄開始失控的重度使用者
- 首次收錄／最近查證：2026-10-16／2026-10-16 21:00（台灣時間）
- 證據狀態：`author-self-report`（作者部落格長文）；建議流程與提示詞為 `designed`；未重現
- 是否獨立重現：否

## 輸入與預期輸出

- 輸入：使用者對 L1 總管說一件事（例如「幫我找附合條件廚房的房子」）。
- 輸出：Notion Projects／Tasks 一筆工單與連結；L2 領域 Bot 開出 L3 臨時工（以 emoji 命名讓側邊欄好掃），多個 L3 時開 swarm 頻道並宣告認領、去重；完成後 L3 交回 L2、L2 更新 Notion、L1 只把工單網址丟給使用者。
- 作者例子：看房搜尋——總管平行派出多個偵察 L3 去不同房源網站（作者點名 Zillow、Redfin），逐筆看房源照片判斷廚房是否符合；值得看的才往上交。作者並描述固定節奏執行者（cadence runner）每天定時跑（本庫摘要時記錄為太平洋時間 9:00 與 18:00；請以原文為準）。
- 明確排除：作者說這不是產品公告也不是架構導覽；未公開完整 Bot 指令、成本與失敗率。

## 為什麼這個用法值得看

公開分享多半在講「我有幾個 Bot」，這篇講的是**交接與界線**：誰能開工單、誰能刪臨時工、結果放在哪裡。這是讓多代理可以長期維運的部分。

## 建議操作流程（本庫設計，未實測）

1. 先在 Notion 建 Projects 與 Tasks 兩個資料庫，欄位至少有：狀態、負責 Bot、來源網址、完成證據。
2. 建一個總管 Bot，指令只准：收件、建 Task、指派領域 Bot、回 Task 網址；不准自己做研究。
3. 依你的生活／工作建 2–3 個領域 Bot；每個寫明「可以開臨時工、必須把結果寫回 Task」。
4. 臨時工命名規則：emoji＋任務短名；完成後改成完成 emoji，由你每週清一次。
5. 需要多個臨時工的工作，由領域 Bot 開一個頻道並要求每個臨時工先宣告認領範圍，避免重複爬同一網站。
6. 例行工作（例如每天兩次看新房源）做成 routine，只在有符合條件的新結果時寫入 Task 並通知。
7. 一週後檢查：你是否還需要打開 worker 對話？若需要，代表交回格式不夠，回頭改 Task 欄位。

## 可複製提示詞（原創設計，未實測）

你是我的總管。從現在起，我交辦的每件事你都要：一、在 Notion Tasks 建一筆（標題、目標、完成條件、負責領域）；二、指派給對應的領域 Bot；三、只回我 Task 網址與一句話狀態。你不要自己做研究或瀏覽網站。領域 Bot 交回結果後，確認 Task 裡有證據連結才把狀態改成完成。沒有新發現時不要通知我。任何付款、送出表單、寄信給他人之前，先在 Task 裡列出確認項等我回覆。

## 所需連接、權限與限制

- 需要 Notion 連接；多 Bot 與頻道功能依方案與版本而異，請以官方文件為準。
- 看房等網站的使用條款可能限制自動瀏覽；本庫不建議大量爬取。
- 多 Bot 常駐與平行臨時工會快速消耗用量；作者未公開費用。

## 驗收與可重現性

- 你交辦一件事後，一則回覆內就拿到 Notion Task 網址。
- 完成的 Task 都有證據連結，你不需要打開 worker 對話就能判斷。
- 無新結果的例行執行不打擾你。
- 本庫未重現；S-084A 為作者自述。
