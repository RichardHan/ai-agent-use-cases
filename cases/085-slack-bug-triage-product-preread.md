# UC-085：Slack 問題回報先分流，雙週從發布紀錄、GitHub、Slack 彙整產品行銷預讀

- 情境：工作
- 標籤：Slack、分流、產品行銷、彙整
- 網站標題：讓 Bot 先接 Slack 的 bug 回報做初步分流，並每兩週整理一份產品行銷預讀
- 一句話用途：作者把 Grok Bot 放進團隊 Slack，先對 bug 回報做第一線分流；另外每兩週從版本發布說明、GitHub 與 Slack 討論彙整一份給產品行銷會議的預讀文件。
- 核心目標：減少工程師被零散回報打斷，並讓行銷會議前不必有人手動翻三個地方找「這兩週出了什麼」。
- 工具：Grok Bot；Slack；GitHub
- 分類／標籤：團隊協作／問題分流／週期彙整
- 目標使用者：小型產品團隊的 PM、產品行銷或工程主管
- 首次收錄／最近查證：2026-10-16／2026-10-16 21:00（台灣時間）
- 證據狀態：`author-self-report`（作者電子報）；建議流程與提示詞為 `designed`；未重現
- 是否獨立重現：否

## 輸入與預期輸出

- 輸入：Slack 頻道內的 bug 回報；兩週內的發布說明、GitHub 合併紀錄、Slack 討論。
- 輸出：每則回報的初步分類（重現資訊是否足夠、可能歸屬、是否重複）；雙週一份預讀（新功能、修正、值得對外講的故事）。
- 明確排除：作者未公開提示詞、分流準確率或預讀範例全文；本庫不推測。

## 建議操作流程（本庫設計，未實測）

1. 指定一個回報頻道；Bot 只在該頻道回覆，且只回「分流卡」：摘要、缺少的重現資訊、疑似重複的既有議題連結、建議負責人。
2. 不讓 Bot 自動開或關議題；建議由人按表情或回覆確認後再建。
3. 預讀做成 routine，每隔週同一時間跑：讀取期間內 GitHub 已合併 PR、發布說明與指定 Slack 頻道。
4. 預讀固定格式：可對外宣傳、只限內部、還在進行中三段；每項附原始連結。
5. 會議後把被採用的條目標記回去，下次彙整時避免重複。

## 可複製提示詞（原創設計，未實測）

每隔週一早上，整理過去 14 天的：GitHub 已合併 PR（指定 repo）、發布說明頁、以及 #product 與 #releases 頻道的討論。輸出一份產品行銷預讀，分成「可對外講」「僅限內部」「進行中」三段，每項一句話加原始連結。不確定能否公開的放進「僅限內部」並註明原因。不要在任何頻道發文，先把草稿私訊給我。

## 所需連接、權限與限制

- 需要 Slack 與 GitHub 連接；團隊方案的管理權限與稽核功能依方案不同。
- 預讀可能含未公開功能，對外前需人工審。
