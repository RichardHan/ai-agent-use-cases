# UC-096：正式服務異常時，先整理日誌與部署時間線

- 網站標題：網站出問題，先把錯誤日誌和部署時間對起來
- 一句話用途：把多台伺服器的異常整理成可追查的初判，避免一開始就盲目修機器。
- 工具：Grok Bot／Loki／Grafana／VPS；來源B：Grok Bot／Gmail／程式碼庫／資料庫／日誌／RabbitMQ／Jira（作者稱程式碼至工單皆只讀）
- 情境：開發
- 標籤：故障診斷、日誌、部署、驗收
- 證據：author-demo；作者實際使用自述，未獨立重現
- 查證日期：2026-10-16；2026-10-20 11:48 補來源B（V2EX 中文）
- 500 案例計數候選：實際使用；正式服務日誌初判，與程式 PR 審查、代理排程健康檢查分開

## 原作者實際做了什麼

作者管理三台 VPS，稱主要請 Infra Bot 分析正式環境 Loki／Grafana 日誌並監看部署。文章未附故障報告、修復紀錄、具體部署事件或改善時間；不宣稱自動修復已被驗證。

## 怎麼開始（整理者設計，未實跑）

1. 用去敏感化的日誌片段、部署清單及服務名稱對照表開始。
2. 指定故障時間窗、時區與正常比較時段，要求先列資料覆蓋缺口。
3. 將錯誤群組與部署事件排成時間線，保留來源行號，列可能原因及反證。
4. 人工確認後再決定修復；研究流程不需要 SSH 寫入、重啟、回滾或新增憑證。

## 可貼指令（本庫原創，未測）

只讀這些匿名日誌與部署樣本。輸出時間線、異常群組、首次與最後出現時間、樣本行號、可能影響範圍，以及支持或反對各假說的證據。把「剛好發生在部署後」與「已證明由部署造成」分開。資料不足請明說；不要連正式系統、重啟、回滾、修改防火牆或建立存取權。

## 驗收與限制

- 每項判斷要有可核對來源；日誌未收齊或取樣不完整，不可宣稱整體健康。
- 必須排除 Token、帳密、用戶識別和業務內容；不把正式日誌放入公開庫。
- VPS、日誌儲存與 Bot 用量可能分別計費，來源沒有總成本或節費證據。
- 官方說明各 Bot 共用帳號電腦、檔案與憑證，不能靠另建 Infra Bot 隔離權限。
