# UC-164：批次清理陳年工單時，停掉無關跨系統補讀

- 網站標題：只是關掉舊工單，為什麼Bot還在狂讀另一套系統？
- 一句話用途：作者清理舊Jira工單時，先前Zendesk補讀規則仍反覆運行；帳號暫停與請求數為作者轉述，未核個案根因。

- 標籤：工單、批次清理、限流、失敗
- 工具：Grok Bot／Atlassian MCP／Jira／Zendesk瀏覽器

- 查證日期：2026-10-17（台灣時間）

## 作者實際遇到什麼

英文Reddit作者VIDGuide先前讓Bot從Jira補讀Zendesk完整對話，並建立遇連結便補讀的規則。後來交辦關閉百餘張陳年工單，舊規則仍被套用；他稱卡住／限流後不斷重試，Jira工作結束後仍持續數小時，並轉述客服說收到大量請求、帳號被暫停。

上述請求量、持續時間及帳停因果未有日誌支持；沒有完整關單清單、解封或修復證據。原帖只顯示相對時間，精確日期未核。先前登入曾由本人驗證協助，不能說代理自主越過驗證。

## 可借用的預覽與停止設計（自設、未測）

1. 以合成工單明列要處理的精確ID、現況與目標狀態。
2. 區分本次必要資料與不必要的關聯連結；舊playbook不應自動擴大任務。
3. 在模擬限流、權限錯誤或清單不符時停止並回報，不持續重試。
4. 真正批次變更須另核工作流權限、通知及逐單結果；未核前維持預覽。

## 可貼指令（自設、未測）

只使用這份合成工單清單做預覽。列ID、目前狀態、目標狀態與缺欄；不要讀取Zendesk或任何關聯網址。模擬遇到限流／權限錯誤時，輸出停止原因及尚未處理清單。不要登入、改真工單或發通知，也不要延續過往補讀規則。

## 官方限制、費用與可用性

Zendesk官方API文件要求429後依Retry-After等待，也描述帳號異常流量限制；此API規則不能確診作者的瀏覽器事故。Jira官方批次轉移需要權限及符合工作流欄位，且可能通知追蹤者；作者未說用原生批次介面，不代填技術細節。原作者方案、費用及恢復成本未知。
