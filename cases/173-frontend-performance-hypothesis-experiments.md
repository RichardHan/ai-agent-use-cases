# UC-173：前端效能假設實驗與回退紀錄

- 網站標題：網頁改快了還是測量誤差？每次只改一個假設
- 一句話用途：以固定條件反覆量測前端修改，保留可追溯的改善與失敗回退，再整理共同技術。

- 工具：Grok Bot／Fable雲端環境／Lighthouse

## 原作者實作

jjcm在Hacker News自述，對約200個前端公開專案做迭代實驗並整理改善榜；後續明確說是用Grok Bot配置Fable雲端實例。Makefaster的網站資料及兩個公開fork PR可讀，但200是作者敘述的範圍，不能當200次成功或200個案例。

Excalidraw的公開PR採每輪一個假設，固定Lighthouse版本、冷／暖快取與行動模擬，至少三次取中位數；不足或退步即回退，連續失敗有停止條件。延後載入部分功能有保留，內嵌字型卻使LCP惡化而撤回。另一字型子集的改善落在測量離散範圍，且涉及版面位移，也未保留。PR與榜單的原始LCP基線不一致，不能拼成一個精確效益數字。

Shiori的另一公開PR有保留與回退紀錄，涉及登入頁與傳輸設定。兩PR均仍開啟、未合併，含代理生成標記；本庫未跑測試，實驗harness也未取得。樣本環境與正式CDN、語系、流量條件不同。

兩專案合併一個「假設、重複量測、回退與歸納」流程，不按專案數或改動數拆計；也不同於一般PR審查、內容稽核或可及性報告。

## 可參考步驟（自行設計，未執行）

1. 僅閱讀已授權的既有測量報表，記下工具版本、裝置、網路、快取、頁面與樣本數。
2. 將每次修改限制為可辨識假設，列出預期收益與功能／版面回歸風險。
3. 比較各次分布與中位數，保留異常與失敗，不只挑最快一次。
4. 若差異小於既有波動、條件不一致或功能受損，標未確定或建議回退，不自行改程式。
5. 跨專案歸納時保留情境，區分本機實驗室指標與真實使用者資料。

## 可貼指令（自行設計，未測）

請只讀我提供的合成效能報表和修改摘要，不執行程式、不建立雲端實例、不更改PR。逐輪列假設、條件、樣本數、分布、中位數、功能回歸和是否值得保留。條件不同或落在測量波動時標未確定。不要將未合併PR當已部署，不把Lighthouse結果當真實流量成效。整理可追溯的保留／回退理由及下一步需人核准的實驗。
