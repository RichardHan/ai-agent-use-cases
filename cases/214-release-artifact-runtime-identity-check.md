# UC-214：發布產物身分與切換後讀回驗收

- 網站標題：服務啟動了，怎麼確定跑的是剛發布的版本？
- 一句話用途：把程式版本、建置產物、依賴環境與實際運行位置連起來，避免「能開啟」被當成全部驗收完成。
- 工具：Meta Muse／Codex／Python
- 證據：B，作者實作與失敗修正自述；無公開部署日誌，未獨立重現。
- 分類：開發｜發布、版本、環境、驗收

## 作者實際做了什麼

作者讓 Muse 組織開發與發布、Codex 寫碼、另一模型審閱，關鍵動作由本人批准。他回報首次發布兩個既有服務，之後另作只讀檢查，確認服務運行、環境指向新版本及基本端點回應。

其中一個實際失敗是先建立 Python 環境再搬移，導致入口失效，後來改在最終位置建立。發布記錄對應原始碼提交、建置及檔案摘要，也保存切換前的真實環境指向。作者明說，真實業務驗收與正式環境回退演練仍未完成。

## 可以學什麼

這案的終點是「部署後實際運行的產物是否可追溯」，而非只看測試通過或網站可開。保存舊環境也不等於已證明能恢復。

Python 官方文件說明 venv 入口可能使用絕對路徑，環境一般不具可攜性；這支持失敗機制，不能驗證作者服務狀態。原文其他連線、憑證與權限操作不列為本案例教學。

## 只讀練習步驟（整理者自設，未實跑）

1. 準備虛構的兩份發布清單，包含原始碼版本、建置編號、產物摘要、預期環境及觀察到的運行環境。
2. 對照每個服務是否使用預期產物；區分版本字串相同與真正建置相同。
3. 標出缺少的摘要、互相矛盾的環境、未知的服務身分及未驗證的業務結果。
4. 以人工判定的錯誤清單驗收；不能只因端點回應成功就判整體通過。

## 可貼指令（整理者自設，未實跑）

只分析以下合成發布記錄，不連線、不執行命令或部署。逐服務比對預期提交、建置編號、摘要與觀察到的環境，列出相符、衝突及缺證。保留原始的上一版本記錄，不推測恢復路徑。分開基本可訪、正確建置、業務驗收及回退演練四種狀態。任何未提供的結果寫未驗證。
