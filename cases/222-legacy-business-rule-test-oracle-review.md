# UC-222：改寫舊系統前，檢查測試是否真的保留原規則

- 網站標題：測試全綠還不夠，先核它驗的是不是舊規則
- 一句話用途：把舊程式業務規則逐條對照新測試，將矛盾交給人回查，避免測錯還以為通過。

- 標籤：測試、舊系統、規則、驗收
- 分類：軟體測試
- 工具：Grok Bot／Cursor／Jev

## 原作者實際做了什麼

作者以Java及PL/SQL舊系統遷移情境建立測試框架。Cursor協助整理既有規則，Grok Bot分工建立跨儲存庫脈絡、測試及CI；另用Jev對照業務規則與測試的實際行為。

作者回報七條主張中五條得到支持、兩條有矛盾，涉及交易代碼對應與接近零時的重置。這些數量是作者報告，非本庫逐條驗證。作者仍須回到原程序決定理解或程式哪一方錯；Jev沒有替他修復。沒有修後全部通過或生產遷移完成證據。

## 可借鑑步驟

1. 把舊規則、原碼依據及預期結果固定成可追溯主張。
2. 建立測試時保留跨模組關係，不能只看單一儲存庫。
3. 分別檢查「程式跑通」與「測試在核對正確規則」。
4. 遇矛盾回查原規則及固定輸入的預期值，由人裁決後再驗收。

## 可貼指令（本庫自行設計，未執行）

> 只讀這份合成規則、舊程式片段及新測試。逐條列規則來源、固定輸入、人工提供的預期值、測試實際斷言及缺口。把支持、矛盾、無法判定分開；不要把另一模型的分數當正確性證明。缺預期值先標待核，不改原碼、不執行CI、不上傳真實帳本、不部署。

Jev官方說它輸出結構化判斷，並非替換Grok Bot底層模型或編碼代理。置信分數不等於客觀正確；數字與間接推論仍有限制，算術需獨立程式或已核預期值。作者使用版本未核，不能套用後來版本評測。

作者當時說Jev已回邀請制；目前帳戶資格、費用及全部工具成本未核。接入服務、傳送程式或憑證、CI及部署都需另外授權。本庫只讀公開原文，未接入或執行。

本案終點是保留舊業務語意的測試依據核對，不同UC005一般PR審閱或UC217硬體功能回歸；多個Bot及七條主張合計一案。
