# UC-255：既有長期記憶的版本合併與保護規則核對

- 網站標題：舊決定越存越多？先備份、分批核對，再合併過期記錄
- 一句話用途：作者的Grok Bot無法一次列出全部記憶，改成逐類小批核准；不保證完整匯出或可還原。
- 情境：開發
- 標籤：版本、合併、備份、驗收
- 工具：Grok Bot
- 證據狀態：B，作者實作與失敗自述；無原始備份或還原測試
- 查證日期：2026-10-17（台灣時間）

## 作者實作與結果

Thomas Licari與其Grok Bot Mary Ann整理仍在使用的過期、重複及互相替代記錄。作者說初次流程要求先完整備份，但800多筆記憶無法一次列舉，因此停在完整性檢查。

之後改按類別逐批提出、備份、由本人核准，報告11批處理60多筆舊記錄；看不到完整文字的項目保留。作者稱變快，但沒有計時比較。文章附的事後測驗與恢復設計，不等於已完成全部恢復驗證；原備份和逐項差異未公開。

## 參考步驟（本庫自行設計，未測）

1. 只對離線合成記錄工作，為每筆記錄保留ID、版本、來源與日期。
2. 標示不得弱化的約束；不確定或缺全文的項目保持原樣。
3. 分列重複、被新決定取代與仍有效記錄；不能單靠日期較新判定有效。
4. 每小批只提出舊文與新文差異，由人覆核，不直接改真正代理設定。
5. 用合成反例檢查是否漏掉例外與否定條件；未測恢復就明標未測。

## 可貼指令（自行設計，未測）

只讀這份合成版本記錄，找出重複或可能被後續決定取代的內容，列ID、來源、舊文、新文草稿與疑點。保護約束、例外及否定條件；缺全文就保留。不要操作任何真實記憶、改規則、刪檔或執行恢復。交一份待人工核准的差異表即可。

## 權限、費用與限制

- [官方Bot說明](https://docs.x.ai/grok-bot/bots)提醒記憶不能代替權威來源，重要工作須重查現行資料並明訂安全界線；沒有替此案例保證完整匯出或逐筆刪除能力。
- 作者未提供方案、費用及可重現成功率。原模板不是本庫實測，不能用它保證備份可還原。
- 真實記錄可能含個人與組織私密資料；公開示例只能用合成內容。實際資料更動須另有相應授權。
- 不應為了降低筆數而刪掉限制、責任或仍有效事項。
