# UC-283：把 dots 接上常用工作 App，實測 17 項任務與核准陷阱

- 情境：工作
- 標籤：驗收、權限、排程、故障診斷
- 網站標題：dots 能讀能寫，但「刪除／送出」可能不問你——先搞清楚核准出現在哪
- 一句話用途：作者花三天把 ChatGPT dots 接到 Gmail、日曆、Drive、GitHub、Slack、Notion、Jira、Outlook，實做約 17 項真實任務；讀寫多半成功，但發現「說刪就刪、說送就送」可能不出現確認畫面，且權限提示常在子對話，錯過就靜默失敗。
- 核心目標：用可核對的實測，標出 dots 在連接工作 App 時的能力邊界與操作風險，而不是只列功能廣告。
- 分類／標籤：工作自動化／權限設計／實測復盤
- 適用工具：ChatGPT dots／Gmail／Google Calendar／Drive／GitHub／Slack／Notion／Jira／Outlook／本機 Mac（ChatGPT 桌面當閘道）
- 目標使用者：準備把公司信箱與日曆交給 dots、需要先知道失敗模式的人
- 首次收錄／最近查證：2026-10-17（台灣時間）
- 證據狀態：author-demo。作者對照真實畫面與 `git log` 驗收；本庫讀取 DEV Community 全文，未重跑。
- 是否獨立重現：否。

## 輸入與預期輸出

- 輸入：已連接的真實工作帳號、具體任務指示（摘要、建刪日曆、寄信、Notion 頁、Slack DM、排程晨報等）。
- 輸出：各任務成功／失敗、耗時、作者如何核對；以及兩類風險紀錄——無確認畫面的刪除／寄送、子對話權限提示導致中止。
- 明確排除：不能外推所有租戶設定；作者也寫明部分項目未逐一核對內容正確性。

## 來源版本

### S-283A：uehara（DEV Community）（`author-demo`）

- 來源：[I Connected ChatGPT dots to Gmail, Calendar, Slack and Notion…](https://dev.to/uehara/i-connected-chatgpt-dots-to-gmail-calendar-slack-and-notion-to-see-what-it-can-and-cant-do-13md)，英文，標示 Posted on Oct 10（文內測試窗 2026-10-07–09）；本庫 2026-10-17 讀取。
- 條件：ChatGPT Pro（文內寫 $200／月）、真實工作帳號、以實際日曆／信箱／Notion／`git log` 核對，不盲信代理回報。
- 作者整理的重點結果（改寫，非逐字）：
  - 讀取與摘要多半可用：晨間摘要、一週 GitHub 摘要（提交數與自己數的 32 筆相符）、Drive 搜尋、Slack 摘要等。
  - 會依指示寫入：建立／刪除日曆事件、寄信、建立／刪除 Notion 頁。
  - 風險一：即使把日曆權限設成「變更前確認」，說「刪掉剛建的事件」仍約 30 秒內刪除且無確認畫面；寄信在說「送出該草稿」後也直接寄達。
  - 風險二：權限提示出現在側欄「子對話」。刪 Notion 頁時因外掛無刪除能力改走本機 Chrome，作者沒注意到子對話核准，約 21 分鐘後變成 aborted；主對話只剩一句未刪除。第二次開著子對話按允許後約 1 分 10 秒完成。
  - Slack DM 詢問今日剩餘行程：約 13 秒確認、81 秒回覆（以 Slack 時間戳測量）；回覆在執行緒裡，列表只顯示「1 reply」。
  - 平日 08:30 晨報排程：10/8 於 08:44 送達（晚 14 分鐘），內容看了全部 16 個日曆並去重。
  - 長任務（下載教材）總曆時約 2 小時，多數時間在等作者回覆存檔位置與是否填入購買信箱；Chrome 擋 ZIP 時代理未自行關閉防護。
  - 本機動作在對方系統裡常顯示為「使用者本人」操作（經 `codex exec-server --remote` 閘道）。
  - 費用：Credits 三天未變；用量在 Pro 週額度內，但畫面上看不到 dots 單獨用量。
- 未證實：其他帳號／地區是否同樣略過確認；子對話 UI 是否已改版。

## 建議操作流程

以下為本庫設計，未實跑：

1. 前兩天只用「草稿」「只讀」「不要變更任何事件」等否定句實測。
2. 把側欄「Needs approval」與子對話列入每次交接檢查清單。
3. 刪除、寄送、付款類動詞分開：先「起草」，你回「送出／刪除」再執行。
4. 排程任務記錄實際送達時刻，接受「可能遲到」，重要晨報另設備援。
5. 本機閘道操作等於以你的身分留下稽核軌跡；共用電腦勿開。

## 2026-10-18補充：同名新檔不等於原檔已追加

青島的[日文原作者測試](https://note.com/bright_dietes994/n/n7979fadb9471)（頁示2026-08-24 07:33，時區未核）以五張收據與預寫答案測試Grok Bot。作者發現報告「追加」時，實際是舊試算表改名、另建包含全行的新表；原文件身分並未維持。一次Drive讀圖失敗，改附件後讀到，最後合計與人工核算相符；過程曾漏讀付款方式，不能稱全欄始終正確。週期處理僅提案，未執行。

此為既有連接器操作與驗收邊界的補充，不另計案例。完整性驗收應另外比對文件識別碼、原連結與實際操作類型，不只看檔名和完成訊息（本庫建議，未測）。只保存公開實測結論，不收錄私人收據明細，也不將當時工具限制當現行規格。

## 2026-10-18補充：先核對核准觸發條件，不猜權限沒有繼承

mibrh 的[公開 GitHub issue #52714](https://github.com/openai/codex/issues/52714)（英文，2026-10-09）記錄 dots、委派工作與排程的控制比較：小檔都能完成；保持 JSON 資料相同、改變檔案大小時，是否出現核准提示不同。作者說成功寫入均讀回，並由本人觀察提示畫面。這不支持把所有失敗先歸因於委派或排程未繼承權限。

作者未證明內部機制、精確門檻、是否有意的安全保護或現版是否修復。本庫未重做測試，也不提供縮減／拆分請求以避開核准的做法；遇到核准要求應按要求處理。此為既有連接器核准驗收補充，不另計。

## 2026-10-22補充：先驗讀取範圍與既存產物，再判斷重試

上原正吉／chooser 的[日文原文](https://zenn.dev/chooser/articles/aico-001-tooling)（頁標2026-10-12，測試窗10月7至9日）提供兩項原案例未展開的驗收細節：初次行程摘要只讀主日曆，漏掉其他日曆的兩件事；改明確指定全部日曆後才涵蓋16個。教材下載遇到阻擋訊息後，代理又更正自己漏看已存ZIP，作者最後清點PDF、ZIP與MP3，與完成報告一致。日曆重新連接也沒有自行恢復已停工作，需再指示繼續。

以上仍是同一作者自述，不是三個新案例，亦非本庫重現。可參考的驗收順序（AI構想／未實測）：「先只讀核對要求範圍、實際讀取清單與已存在產物，再列缺項；錯誤訊息不直接等於產物不存在，連接恢復不等於工作已恢復。不要重複下載、改保護設定、刪檔或重新授權。」這些觀察不證明現行所有帳戶行為相同。
