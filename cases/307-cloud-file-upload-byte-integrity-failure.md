# UC-307：雲端檔案建立了，內容卻被截短

- 網站標題：PDF上傳完成後，還要核對內容完整
- 一句話用途：用原檔與目的檔大小、可讀性及小檔控制測試，辨別檔案已建立但傳輸內容損壞的失敗。
- 情境：工作
- 標籤：檔案交付、PDF、傳輸、完整性、失敗
- 分類／標籤：檔案交付、PDF、傳輸、完整性、失敗
- 工具：Grok Bot／Google Drive connector
- 證據狀態：B，原作者實跑及大小差異自述＋論壇回覆；未取得檔案或獨立重現
- 查證日期：2026-10-18（台灣時間）

## 作者實作與結果

Chris Farrugia（c17a）報告以Grok Bot的Drive connector建立約40–54KB的PDF時，目的檔曾少60 bytes，另有僅8 bytes或數KB的結果；小型測試PDF則成功。這是已實際上傳並比較結果的失敗，不只是推測大檔可能出錯。

同日deanrie（Dean Rie）回覆，當時將base64內容放入工具呼叫的路徑有已知可靠性問題，並提出其他交付方式。**未見原作者使用替代方式後驗收成功。** 十月另一位使用者的核准分類錯誤被要求分案，不能把相似錯誤訊息一律歸因於PDF傳輸。

## 可參考流程

以下為本庫設計的離線驗收，未執行，也非原作者逐字操作：
1. 使用無敏感資訊的自有測試PDF，保留原檔版本、byte數及雜湊。
2. 分開記錄工具回覆、目的檔存在、下載讀回、內容可解析四個階段。
3. 對合成測試紀錄比較原檔與讀回檔；檔名相同、檔案存在或操作沒有報錯都不等於內容相同。
4. 加入小檔正常、大檔截短、同大小但內容不同的反例；大小相同仍需內容驗證。
5. 一旦完整性不符，保留原件、標記失敗、停止擴大批次；不同路徑重試須符合既有權限，不能繞過拒絕。
