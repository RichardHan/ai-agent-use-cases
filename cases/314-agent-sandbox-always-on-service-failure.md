# UC-314：代理附帶的雲端電腦，部署成功後仍不適合作長駐主機

- 情境：開發
- 標籤：雲端環境、部署、可用性、失敗
- 網站標題：遠端助手裝好了，閒置後卻不回應：先驗證能否長時間運作
- 一句話用途：把一次連線成功與持續服務分開驗收，避免把代理的臨時工作環境當成有在線保證的主機。
- 核心目標：檢查在代理雲端環境部署的外接服務，閒置後能否持續回應；不符合需求就停止依賴它。
- 分類：雲端環境／服務生命週期驗收
- 工具：Grok Bot／Pi agent／Telegram／Cloudflare tunnel

## 問題、實作與具體結果

作者想知道Grok Bot附帶的雲端電腦能否取代常駐VPS。他讓Bot配置遠端連線，改用Cloudflare tunnel後自述成功SSH進入；再由Bot安裝Pi agent與擴充，作者自己完成設定，接上Telegram後能控制該雲端電腦。

其後作者報告，閒置大半日會休眠、一天以上會關機，因此放棄把它當24小時主機。這是**完成部署後的可用性失敗**，不是完全無法安裝，也不是已找到保活方法。

文中提出「定時傳訊、喚醒後看uptime」的驗法，但沒有逐次日誌；本庫未取得附圖，不能把敘述當完整測量或官方休眠門檻。不回應也可能有網路、程序或通道等原因，沒有原始紀錄不能獨立確定根因。

## 輸入與預期輸出

- 輸入：已去識別的服務需求、部署版本、觀測時間、請求與回應、已知程序狀態及重啟紀錄；不需帳號、通道位址或憑證。
- 輸出：分開列部署成功、指定時間有回應、無回應、狀態未知；判斷現有證據是否支持長時間運作需求。
- 單次成功不能推出全天候可用；喚醒後恢復也不能抹去中間的服務中斷。

## 可借鑑流程（本庫設計，未執行）

1. 先定義需要服務的時段、可接受中斷，以及供應商是否承諾該用途；沒有保證就明列風險。
2. 將部署驗收與持續可用性驗收分成兩張表，不以「可以連進去」作結。
3. 只分析已有的去識別紀錄；把觀測時間、環境是否閒置、服務回應及證據來源一併列出。
4. 不回應時，區分主機、程序、網路及訊息通道的未知，不直接把全部歸因於休眠。
5. 需求未達成就提出停止依賴或另選有適當保證環境的評估；不自行加入保活、重啟或繞過資源限制的機制。
