# UC-316：Slack 回報串裡，分流 Bot 去重、重現 Bot 附截圖，人在同一串修到合併

- 情境：開發
- 標籤：Slack、分流、多代理、驗收
- 網站標題：有人在 Slack 回報 bug：先讓 Bot 判斷是不是真問題、重現給大家看，人在同一個討論串裡指揮修好
- 一句話用途：把「回報 → 分流 → 寫規格 → 重現 → 修 → 審 → 合併」的接力，改成人和 Bot 在同一個 Slack 討論串裡一起處理；重現的做法和修正寫成技能，分享成全隊可用的 Team Bot。
- 核心目標：縮短一個 bug 從回報到合併的時間，同時避免重複回報開出一堆重複工單。
- 分類：工程協作／問題重現與修正
- 工具：Grok Bot（Team Bot、技能、雲端電腦）／Bot Development Kit（BDK，程式化 Bot）／Cursor Cloud Agents／Slack／Linear／GitHub（示範 repo 為 Grafana 開源專案）

## 建議操作流程（本庫設計，未實跑）

1. 先挑一種常重複的工作（例如「重現回報的 UI bug」），給一個 Bot 做，指定只用 repo 既有的開發／雲端代理環境，不碰正式環境。
2. Bot 做錯時用白話糾正，並要求存成技能（例如「一律在本機或指定環境重現，不用公開 demo 站」）。
3. 重現結果必須附截圖或可重跑的步驟；「我覺得是這個原因」不算重現。
4. 穩定後才分享成 Team Bot，接進回報頻道；修正 PR 仍由人審查與合併。
5. 每則回報都要回應的分流，若需要可預測行為，再考慮用程式化方式並建立評測集；評測通過率只代表那組題目。

## 可複製提示詞（本庫原創，未測）

請只處理這個 Slack 討論串裡的 bug 回報。先判斷：資訊是否足夠重現、是否和最近 30 天的既有回報重複（附連結）、可能屬於哪個 repo（附信心）。若要重現，只在我指定的開發環境或 repo 的代理環境進行，不連正式環境、不使用公開 demo 站；成功要附截圖與重現步驟，失敗要寫卡在哪裡。可以提出修正 PR 草稿，但不要合併、不要關閉工單、不要改權限或密鑰；把需要人決定的事列在最後。

## 所需連接、權限與限制

- 需要 Slack、程式碼庫與工單系統的連接；Team Bot 的外掛若以金鑰設定，所有隊友共用同一權限，要用最小權限的唯讀或服務帳號金鑰。
- Slack 頻道串共用一台電腦：重現時下載的資料、日誌或截圖可能被頻道內其他人看到。
- 合併、部署、關單與對外回覆客戶仍需人工核准；示範中的合併也是人在串中完成。
- 費用：Team Bot 的用量計在發問的隊友帳上（官方文件）；工作坊未提供單次修復的用量或成本。

## 驗收與可重現性

- 重複回報被合併到同一張單，而不是各開一張。
- 每次重現都有截圖或步驟，第二個人照著能看到同樣問題。
- 修正後由人確認原 bug、設計師提出的邊界情況都通過，才合併。
