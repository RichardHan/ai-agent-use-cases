# UC-322：多平台創作者數據每日採集：固定腳本零 token 抓取，代理只做檢查與彙整

- 情境：創作
- 標籤：每日、數據儀表板、瀏覽器自動化、用量
- 網站標題：每天早上自動抓各平台粉絲與閱讀數，抓取本身不花 token，代理只負責檢查和整理
- 一句話用途：作者自述讓 Grok Bot 每天早上收集自己在多個內容平台的粉絲與貼文數據，同步到 Notion 與儀表板；後來把抓取改成固定腳本（16 個頁面、約 2 分半、0 token），代理只在之後檢查與彙整。
- 核心目標：把「每天打開好幾個後台抄數字」變成固定時間的自動採集，並把耗用量高的模型判斷，跟可以寫死的抓取步驟分開。
- 工具：Grok Bot（作者在 10-12 回覆 @bot 的貼文中說明）／作者自製並公開的 web-access Skill（經本機 Chromium 瀏覽器操作）／Notion／作者自建儀表板；10-18 截圖中的對話介面未標示產品名稱。
- 分類／標籤：內容創作者成效數據採集與每日儀表板
- 目標使用者：同時經營公眾號、視頻號、X、小紅書等多個平台，每天要看成效的內容創作者
- 首次收錄／最近查證：2026-10-18（台灣時間）
- 證據狀態：author-demo。作者自述＋儀表板與對話截圖；技能程式碼公開。作者就是該 Skill 的開發者，貼文帶推廣性質。未獨立重現。
- 是否獨立重現：否

## 輸入與預期輸出

- 輸入：作者自己已登入的各平台後台或列表頁（本機日常瀏覽器的登入狀態）、要追蹤的指標（粉絲數、每日新增閱讀、單篇互動）、固定執行時間。
- 輸出：每天早上更新的數據（Notion 與儀表板）：粉絲總數與日增、昨日閱讀、近 N 日折線、「最近爆款」排行（平台、標題、互動率、漲幅）；另有執行紀錄可回查每次開了幾頁、用了多少 token。

## 建議操作流程

以下為本庫依來源整理的設計，未實跑：

1. 先列出要追蹤的平台與「只需要列表頁就拿得到」的指標；需要進詳情頁、會觸發驗證或違反平台條款的，不放進每日採集。
2. 第一次由代理陪同手動跑，確認每個頁面的欄位位置與數字口徑（累計或當日、是否含已刪貼文），寫成固定腳本。
3. 每天固定時間先跑腳本：只存原始數字與時間戳，截圖留本機作為證據，不送模型。
4. 半小時後再讓代理讀腳本輸出：比對前一天、標出缺值或異常跳動、更新 Notion／儀表板，失敗就明說哪一頁沒抓到。
5. 每週抽查一次：隨機挑一個平台，人工打開後台核對數字；並檢查運行紀錄的頁數與用量是否突然變多。

## 可複製提示詞

本庫原創設計，非原文：

> 請幫我設計一個每天早上的創作者數據日報，分成兩段。第一段在 7:00 跑固定腳本：只打開我列出的平台列表頁［平台與網址清單］，抓粉絲數、昨日閱讀與最近 10 篇的互動數，存成帶時間戳的 CSV，截圖只留在本機，不要送給模型分析。第二段在 7:30 由你讀 CSV：和前一天比較，標出缺值、口徑不一致或變化超過 30% 的項目，再更新我的 Notion 表格。任何一頁抓不到就寫「未取得」與原因，不可用前一天數字補。不要登入新帳號、不要按讚、留言、發文或修改任何平台設定。每次執行結束回報：開了幾頁、花多久、這次用了多少 token。

## 所需連接、權限與限制

- 讀取：本機瀏覽器的登入狀態會被代理沿用，等同把多個平台帳號交給自動化；建議用唯讀角色或另開專用瀏覽器設定檔，並確認平台條款是否允許自動擷取。
- 外部傳送：只寫入本人 Notion／儀表板；不對外發布數據。
- 用量：固定腳本可降低模型用量，但「檢查／彙整」那一段仍會耗用；本庫不推算費用。
- 第三方 Skill 會在本機執行程式並操作瀏覽器，安裝前需自行審查來源與權限。

## 驗收與可重現性

- 隨機抽一個平台，對照後台數字與儀表板是否一致，並確認時間戳是當天。
- 刻意讓一個頁面失效（例如登出），確認日報寫「未取得」而不是沿用舊值。
- 檢查運行紀錄的頁數與 token 是否與宣稱相符。
- 本庫未重現；只有作者自述、三張截圖與公開程式庫文件。
