# UC-324：每天收集公開障礙消息，逐件對官方狀態頁查核，再由雲端代理開 PR 更新資料庫

- 情境：開發
- 標籤：每日、資料庫、PR、來源查核
- 網站標題：每天早上把各大服務的當機消息整理進公開資料庫：先對官方頁面查證、去重，再開 PR 給人合併
- 一句話用途：作者自述用 Grok Bot 每天收集系統障礙新聞，再呼叫 Cursor Cloud Agent 開 GitHub PR；公開 PR 可見代理逐件對照官方狀態頁、排除重複、跑完整性檢查與測試後，由作者本人合併。
- 核心目標：讓一個公開的「障礙報告集」每天自動補上新事件，同時每筆都能追溯到官方來源，避免重複或憑新聞轉述入庫。
- 工具：Grok Bot（每日收集，作者自述）／Cursor Cloud Agent（實作與開 PR）／GitHub／SQLite／靜態網站（GitHub Pages）
- 分類／標籤：公開事件資料庫的每日維護與來源核對
- 目標使用者：維護公開資料集、知識庫或事件時間線的開發者與 SRE
- 首次收錄／最近查證：2026-10-18（台灣時間）
- 證據狀態：author-demo＋公開產物。Grok Bot 負責收集是前批記錄的作者自述，本輪原X 403後停止；PR內容、提交者與合併紀錄已重核。未獨立重現、未逐筆核對資料。嚴格去重視為UC-212的公共資料更新版本，本頁保留但不另計。

## 建議操作流程

以下為本庫依來源整理的設計，未實跑：

1. 定義固定收集窗口（例如前一天 07:50 到當天 07:50）與時區規則，讓每份摘要不重疊、不漏。
2. 收集端只產出「候選清單」：每件附服務名、時間、消息來源網址，不直接寫資料庫。
3. 實作端逐件打開官方狀態頁：能對上的才入庫；時間以官方為準並換算時區；官方沒寫的欄位留空，不從新聞轉述補。
4. 入庫前以來源網址與時間比對既有列去重；重複或無法確認的件列在 PR 說明的「排除」段。
5. 跑資料完整性檢查與既有測試，重產網站資料；開 PR 交人審查，人合併後才上線。
6. 每次合併前確認資料庫列數沒有異常減少，防止像 PR #36 說明那樣被舊快照覆蓋。

本庫原創設計，非原文：

> 每天 08:00（台灣時間）整理前一天 08:00 到今天 08:00 的公開服務障礙候選清單，每件列服務、開始時間、消息來源網址，交給開發代理。開發代理請逐件打開官方狀態頁或官方公告：只有能在官方頁確認的才加入資料庫，時間採官方紀錄並註明時區，官方沒寫的原因欄留空。依官方網址與時間檢查是否和既有資料重複；重複或查不到官方來源的放在 PR 說明的「排除」段並寫理由。完成後跑資料完整性檢查與現有測試，確認總列數只增不減，再開 PR 等我審查。不要直接推到主分支、不要自行合併、不要刪除或改寫既有資料列（除非附官方依據並在 PR 說明列出）。

## 所需連接、權限與限制

- 讀取：公開新聞與官方狀態頁。
- 寫入：GitHub repo 的分支與 PR；合併與網站部署需本人審查。建議代理不給主分支直接寫入權限。
- 二進位資料庫（SQLite）在 PR 中不易逐行審查，衝突時容易被舊版覆蓋；需另有列數或差異檢查。
- 收集端與實作端之間的交接、失敗重試與費用未公開。

## 驗收與可重現性

- 隨機抽 PR 中一件，打開官方網址核對時間與時區換算。
- 檢查被標為重複的件確實已在資料庫，且沒有同一事件被收兩次。
- 比較合併前後資料庫總列數，確認沒有意外減少。
- 本庫未重現；只讀了作者貼文、網站首頁、README 與 PR #36、#40 說明。
