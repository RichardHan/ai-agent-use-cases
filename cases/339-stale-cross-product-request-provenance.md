# UC-339：跨產品舊交辦重送，錯呈現為本人新訊息

- 網站標題：以前交辦過的工作，為什麼又像新要求一樣送到另一個Bot？
- 一句話用途：保留作者遇到的舊訊息跨產品重送失敗，提醒交辦時要保留原始來源、時間與是否仍有效，不能只看訊息出現在本人聊天欄。
- 情境：工作
- 標籤：跨代理、訊息來源、舊任務、失敗
- 分類：跨產品交辦的來源與時效驗收
- 工具：Grok Bot／grok.com／Grok Build

## 問題、實作與實際結果

作者原在Grok聊天／Build做過專案，後來舊訊息兩度送到Grok Bot，呈現得像剛由本人發出；告知忽略後仍再發生。他說收件Bot建立於舊專案完成之後，未處理過同類專案，且在自動化清單未見設定。

回覆者Colin將訊息來源指向跨產品連線，提出上游排程可能性。作者最後發現專案文件寫有未來工作安排，並要求暫停該專案。這只支持「重送失敗已發生、本人提出處置」；不能證明排程是根因、腳本實際執行、停用已生效，或重送此後消失。

## 可重用驗收步驟（本庫設計，未執行）

1. 用合成資料列出原始交辦時間、有效期限、原收件者、目前收件者、轉送時間與轉送原因；未知欄位不能猜補。
2. 分開「同一人以前說過」「仍然有效」「這次確實送給此代理」三項。舊文字被重新投遞，不自動取得新的執行效力。
3. 將過期、已撤回、來源不明及收件者不符的交辦放入待確認區，不由模型自行恢復專案。
4. 以同一訊息重送、延遲到達、專案暫停後再到達及正當的新確認四組合成事件，檢查是否保留來源並避免重複處理。
5. 若真實系統日後獲准修復，需分別核上游不再產生、傳輸不再重送及下游不再執行；單一聊天中的「已停」不是三層驗收。

## 可貼指令（本庫原創、未測）

請只分析我提供的虛構跨產品交辦紀錄，做一份來源與時效驗收表。逐筆列原始作者、來源產品、原始時間、轉送時間、原收件者、目前收件者、有效期限、撤回狀態及缺少的證據。把舊交辦、重送、明確的新確認分開；來源不明或授權時效未知就標待確認，不恢復任何工作。另用四組合成事件檢查重送、延遲、暫停後再到達與新的明確確認。不要登入帳號、讀取私人聊天或專案、建立或刪除排程、改檔、發訊息、啟動Bot或執行任何外部操作。

## 去重

只計跨產品傳送時丟失舊交辦的來源／時效語意一條失敗流程。不同UC-273既定目標能否持續執行、UC-329預期中的對話接力重啟恢復、UC-312把第三方環境聲誤認為本人待辦，以及UC-313已執行外部工作的停止對帳；不按重送次數、產品端或猜測原因拆案。
