## 原作者的實作與結果

作者先成功封存一個由dot建立的電腦任務，之後授權繼續調查；dot選擇向同一任務發後續訊息。新回合開始，任務卻仍在封存清單，讀取其目標又因封存狀態被拒。作者比對事件與執行狀態，並非只看到側欄未刷新。

這是「新交辦受理、執行啟動、封存狀態、目標存取」未一致的實際觀察。繼續調查有使用者授權；不能改寫成未授權執行，也不能推論封存的官方契約必然等於禁止所有後續動作。作者提出應明確拒絕或顯式恢復的期望，不是已完成修復。

## 可重用步驟（本庫設計，未執行）

1. 用合成事件建立狀態表，分開記錄人工意圖、任務受理、執行回合、封存標記及功能是否可用。
2. 每次狀態變更都核對同一匿名任務與事件順序；側欄、成功回覆與執行事件不可互相替代。
3. 遇到「已封存但在執行」或「恢復成功但功能拒絕」就標矛盾，先保存去識別證據，不反覆送交辦測試。
4. 復原規則需由產品明確說明；若要實測，另取得授權並用無外部副作用的測試任務，核對啟動前後各層狀態。
5. 驗收應同時涵蓋明確恢復成功、仍封存時拒絕新工作，以及拒絕時沒有偷偷啟動回合；未知路徑保留未知。
