# UC-386：小額交易機器人一夜虧損：Bot 唯讀拉日誌把損益拆成四桶，抓出繞過帳本的市價單，再寫成附驗收條件與回滾的修正規格

- 情境：開發
- 標籤：故障診斷、損益對帳、交易機器人、驗收
- 網站標題：自己寫的交易程式半夜莫名虧錢？讓 Bot 先把損益拆清楚、找出「說不出原因」的那筆，再交一份可驗收的修正計畫
- 一句話用途：英文作者 Blake La Pierre 自述，他用約 5 美元跑自寫的加密貨幣造市程式，某晚 5.5 小時帳戶從 4.85 變 3.71 美元；凌晨 3 點負責交易程式的 Grok Bot 從程式 API 拉狀態、以唯讀連線讀伺服器日誌，把損益拆成「價格、價差收入、手續費、無法解釋的缺口」四桶，查出兩條市價單路徑繞過帳本、輪替過於頻繁，並寫出含檔名行號、每項驗收條件、試跑與 24 小時小額實測門檻的修正規格。作者公開程式與全部規格檔，也承認自己沒照 Bot 的上線計畫走，之後又修了多輪。本庫未重現，不構成投資建議。
- 核心目標：把「運氣不好」變成可核對的數字：先讓損益可對帳，再找根因、寫可驗收的修正；涉及錢的動作由本人決定。
- 工具：Grok Bot（作者的「交易程式狀態」Bot，與其他 Bot 共用 Linux 雲端電腦）／作者自寫的 Node.js 造市程式（Coinbase、Kraken）／伺服器日誌唯讀連線
- 分類／標籤：開發／交易程式事後檢討／損益對帳與修正規格
- 目標使用者：自己寫自動化交易、記帳或扣款程式，需要讓代理幫忙查帳差異與寫修正規格的開發者
- 首次收錄／最近查證：2026-10-20 17:40（台灣時間）批次
- 證據狀態：`author-demo`（作者自述實測）：Substack 第一人稱長文＋公開 GitHub 倉庫中的修正規格（本輪以 GitHub 公開 API 讀取第一份規格全文與規格目錄）。損益數字為作者與 Bot 報告的數字，本庫未接觸交易帳戶。本庫流程與提示詞為 `designed`。
- 是否獨立重現：否

## 輸入與預期輸出

- 輸入：交易程式的狀態 API、伺服器日誌（唯讀）、成交紀錄、當晚起訖權益與轉出到「存錢帳戶」的金額。
- 作者描述的輸出：損益四桶表、根因說明（附事件次數與時間）、限價成交品質分析、以及一份依優先順序排列的修正規格（每項列檔案與行號、要改什麼、驗收條件），外加上線計畫：重播當晚成交 → 試跑 → 24 小時小額實測、通過門檻後才加資金。

## 來源版本

### 來源A：〈Debugging a $4 Trading Bot: It Made Money on the Spread and Still Lost〉（Substack「Agent of One」，英文）

- 作者：Blake La Pierre；Bot 的身分見同作者系列首篇（每個 Bot 都是 Grok Bot 助理，詳見 [UC-385](385-kdp-puzzle-book-sat-verified-phone-checklist.md) 來源C）。
- 原始網址：[Debugging a $4 Trading Bot](https://blakelapierre.substack.com/p/debugging-a-4-trading-bot-it-made)，2026-10-18 07:53 UTC（台灣時間 15:53，Substack 公開 API 的發布時間）。
- 原文語言：英文。
- 取得內容（翻譯改寫）：
  - 10 月 3 日美西 21:26 到 02:57，帳戶 4.85→3.71 美元；扣掉轉進存錢帳戶的 0.415 美元，實際約 −0.73 美元（−15%）。
  - 約凌晨 3 點，交易 Bot 從程式 API 拉狀態、以唯讀連線讀日誌，拆成四桶：價格 −0.31、價差收入 +0.32、手續費 −0.27、缺口 −0.47。作者：「最大的一桶是錢不知道去哪，那就是要追的。」
  - 根因一：輪替出場與新幣種「種子買入」兩條路徑直接下市價單，沒經過訂單登記，成交從未入帳（當晚 144 筆市價賣、17 筆市價買）；儀表板因此顯示吃單手續費為 0。根因二：每 60 秒輪替、沒有最短持有與遲滯，5.5 小時 306 次輪替，某幣進出 58 次、期間卻上漲 31%。
  - 同時檢查限價成交：232 筆中位數離中間價 85 個基點、手續費 35 個基點，成交後價格沒有不利漂移——「核心策略有優勢，周邊全在漏」。
  - 修正規格：最短持有 30 分鐘、出場遲滯、每 15 分鐘最多換一檔、每小時最多 4 次、輪替週期改 5 分鐘；出場改走只掛單的退場佇列、市價單預設關閉、不賣零碎部位；所有訂單入帳並使用交易所實際手續費；庫存上限永遠生效。上線計畫要求重播當晚成交確認缺口等於市價單、試跑，再以約 3.70 美元實跑 24 小時，門檻為「0 筆市價單、缺口 ≤ 成交額 2%、輪替少於 25 次、庫存 ≤45%」。
- 作者報告結果：第一個修正在診斷後約兩小時（美西 05:05）提交，到 06:48 共 165 筆成交、0 筆市價單，根因一解決。但作者在 06:27 就存入 10 美元、跳過自己的上線計畫，之後一天內規格寫到 v9：存款被當獲利、修正後又把短暫估值跳動誤記為入金、庫存超限導致所有買單為 0 而卡死、某出場因小數位數錯誤失敗 1,008 次等。10 月 7–10 日約 68 小時、1,353 筆成交：價差淨賺 +11.54 美元、庫存價格變動 −20.82 美元。10 月 11 日停用此程式，改寫成另一種造市模型。
- 失敗點／缺口：作者自承每次修正把問題推到別處；「做市賺錢、抱貨虧更多」的結論是作者自己的數字。

## 建議操作流程

本庫設計，未實跑（參考作者「Steal this」）：

1. 先讓損益「有一桶叫做說不出原因」：價格、價差、手續費、殘差分開算；殘差超過門檻就警報。
2. Bot 只拿唯讀權限：狀態 API、日誌、成交紀錄；不碰下單金鑰與資金移轉。
3. 根因報告必須附事件次數、時間與日誌出處；同時檢查「哪部分其實運作正常」，避免整套砍掉。
4. 修正寫成規格：每項有檔案位置、改法、預設值、驗收條件；並寫上線計畫（重播 → 試跑 → 小額實測 → 通過才加碼）。
5. 每一版規格開頭放狀態表：完成／部分／缺／退步，各附證據。
6. 入金、出金明確記錄，不讓程式從現金跳動自行推斷。
7. 本人決定何時上線與加碼，並照計畫走（作者的教訓）。

## 所需連接、權限與限制

- 唯讀日誌與狀態 API 足以做事後檢討；修正程式可在另一個分支或試跑環境，正式上線由本人執行。
- 交易所金鑰與資金移轉權限不交給 Bot；作者的規格也寫明不提交機密。
- 小額實驗只能驗證程式邏輯，不代表策略可獲利；本頁不是投資建議。
- 作者的結果顯示即使根因找對，狀態與帳務錯誤仍會一再出現；要預留多輪修正。

## 驗收與可重現性

- 四桶加總等於期間權益變化（扣除明確記錄的轉帳），殘差有門檻與警報。
- 報告中的每個次數與金額可在日誌中找到對應紀錄。
- 修正規格的每項都有可量測驗收條件；刻意注入一筆未登記成交時警報會觸發。
- 小額實測依計畫時長完成，門檻全部達成才加資金。
- 本庫未重現、未接觸交易帳戶；文章與規格數字為作者自報。
