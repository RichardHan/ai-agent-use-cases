# UC-390：工單系統每天開一張「核對新模型」工單，Bot 團隊改資料開 PR，沒有新東西就只刷新時間戳

- 情境：開發
- 標籤：每日、多代理、資料維護、PR
- 網站標題：讓工單系統每天派一張「有沒有新模型」的工，Bot 團隊查證後開 PR，沒新東西就只改更新時間
- 一句話用途：中文作者 diudiuu（V2EX）把公開的 GPU 推論速度計算器的模型資料維護交給 Grok Bot 開發群：Linear 每天自動產生一張循環工單，Lead Bot 把工單丟進群組，Dev 依倉庫 AGENTS.md 查官方公開設定檔、改資料開 PR；沒有新模型就只刷新資料快照時間戳。公開倉庫可看到逐日 PR 與 PR 內的查證紀錄。本庫未重現。
- 核心目標：讓「每天看各大廠有沒有發新開源模型、把參數正確收進資料庫」這種小而重複、但要逐項查證的維護工作，不靠人每天記得，也不靠 Bot 自己輪詢。
- 工具：Grok Bot（Lead／Dev／QA／Ops 四個 Bot 共用一個開發群）／Linear（循環工單）／Cursor Cloud Agent（實際寫碼與開 PR，PR 內文帶 Cursor Agent 標記）／GitHub
- 分類／標籤：開發／資料維護／多代理分工
- 目標使用者：維護一個需要定期跟進外部資料（模型、價格、規格）的小型公開專案，想把每日核對交給代理、但要保留可追溯紀錄的人
- 首次收錄／最近查證：2026-10-20 20:40（台灣時間）
- 證據狀態：`author-demo`（作者自述實測）：V2EX 原帖（作者流程說明）＋公開 GitHub 倉庫的已合併 PR（逐日核對結果與查證來源寫在 PR 內文）。PR 由 Cursor Cloud Agent 產生；Grok Bot 在其中的派工角色只有作者自述。本庫提示詞為 `designed`（自行設計未實測）。
- 是否獨立重現：否

## 輸入與預期輸出

- 輸入：Linear 專案裡一張每天自動產生的循環工單（作者的工單名改寫為「更新大廠開源模型與參數」）；倉庫內的維護規範 AGENTS.md（新增模型 SOP：以官方 config.json 為準、不取行銷宣稱值、量化與蒸餾版本不重複收錄等）。
- 輸出：每天一個 PR。有新模型時新增模型資料檔並更新計數；沒有時只更新資料快照時間戳。PR 內文列「結論、入庫項目與來源連結、核對過但未入庫的項目及理由、驗證步驟」。

### 來源A：diudiuu〈分享浅浅尝试用 Grok Bot 创建数字员工自动开发流程〉（V2EX，中文）

- 作者：diudiuu；原文語言：簡體中文；V2EX 頁面顯示 2026-09-11 發布（精確時刻未取得），2026-09-12 有作者補充。[原帖](https://www.v2ex.com/t/1241365)，本輪以網頁讀到主文與 16 則留言。
- 作者流程（翻譯改寫，非逐字）：
  1. 一個開發群就是一個專案，群裡固定四個 Bot：Lead、Dev、QA、Ops。建群第一件事是讓四個 Bot 各自學習自己的職責（職責與專案技術棧事先寫在 Linear）。
  2. 兩種任務來源：一次性任務由作者在 Linear 建 Issue 或在群裡直接說；每日任務是 Linear 的循環工單。
  3. Lead 只負責把新 Issue（標題＋連結）丟進群組，不自動認領、不亂派、不輪詢；要指派時由作者在群裡說「派給 Dev／QA／Ops」。
  4. Dev 依倉庫 AGENTS.md 改資料、開 PR；QA 依 Issue／PR 測試、留步驟與截圖；Ops 負責建置、部署、回滾並留命令與日誌。
  5. 作者寫明的「硬規矩」：循環由 Linear 自己推，不讓 Grok Bot 定時去撈；有新模型就改資料開 PR，沒有就只改更新時間戳。
- 作者自述的限制：全程用 Cursor Cloud Agent 寫碼，沒有試過 Claude Code 或 Codex；這只是簡單的開發流程 demo。
- 留言中的反對意見（改寫）：有人認為多 Bot 群聊浪費 token、上下文會亂，單一代理加子代理就夠；作者回應這是為了「多專案、每天很多 PR、沒空逐一看」的情境。本庫並列兩方看法，不判定哪種架構較好。

## 建議操作流程（本庫設計，未實測）

1. 先寫一份倉庫內的維護規範：資料來源優先順序、哪些欄位必須從官方檔案逐項核對、哪些情況「不收」、讀不到來源時要寫明而不是推測。
2. 讓工單系統（不是代理自己）每天產生一張核對工單；代理只在收到工單時工作。
3. 每張 PR 固定三段：結論（新增／無新增）、入庫項目逐欄附來源、核對過但未入庫的項目與理由。
4. 「沒有新東西」也要留下一筆可查的紀錄（例如只改時間戳的 PR 或工單留言），讓人分得出「今天查過、沒有」與「今天根本沒跑」。
5. 合併前由人看結論與來源連結；涉及計算邏輯的改動拆成另一張工單，不和資料更新混在同一個 PR。

## 可複製提示詞

（本庫原創設計，未實測；不是作者原文。）

> 你負責處理今天的「外部資料核對」工單。請只讀以下來源清單［來源］，找出［時間窗口］內新發布、符合 AGENTS.md 收錄條件的項目。每個欄位都要附官方來源連結；讀不到官方檔案時寫「無法核對」，不要用第三方數字或推測補上。輸出一個 PR 草稿：①結論（新增幾項／無新增）②入庫項目與逐欄來源 ③核對過但未入庫的項目與理由。沒有新項目時只更新資料時間戳，並在 PR 寫明「已核對、無新增」。不要修改計算邏輯；若發現邏輯問題，另開工單說明。不要自行合併。

## 所需連接、權限與限制

- 需要工單系統、代碼倉庫（建分支、開 PR）的權限；本案作者另用 Cursor Cloud Agent 寫碼。合併權限建議留在人手上。
- 外部來源可能需要登入（例如 gated 模型倉庫）；代理讀不到時應記錄，不應繞過存取限制。
- 多 Bot 群聊會累積上下文與用量，留言中已有人質疑成本；本庫未核實際用量。
- 不適用於需要判斷數字是否「合理」而沒有官方來源可對照的資料。

## 驗收與可重現性

- 連續一週，每天都有一筆可查的紀錄（新增 PR 或「無新增」PR／留言），且日期與工單編號對得上。
- 隨機抽一個新增項目，逐欄點開來源，數值與 PR 寫的一致。
- 隨機抽一個「未入庫」項目，理由可由來源驗證（例如權重確實未釋出）。
- 本庫未重現；只讀了公開 PR，沒有看到 Linear 工單或 Bot 群組內部畫面。
