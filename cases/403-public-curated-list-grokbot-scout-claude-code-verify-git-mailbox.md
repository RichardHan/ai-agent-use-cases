# UC-403：公開精選清單由兩個 AI 分工維護：Grok Bot 每天找候選，本機 Claude Code 依收錄門檻核實後才併入，人只拍板對外動作

- 情境：工作
- 標籤：每日、多代理、資料維護、核准
- 網站標題：想維護一份不斷更新的「好工具／好文章清單」？讓雲端 Bot 每天找候選、另一個 AI 照規則查證才收，外發和花錢只留給你
- 一句話用途：中文作者 @sitinme 的開源清單「Grok Bot 中文配方庫」由 Grok Bot（雲端）每天掃 X 與 GitHub 推候選到 `inbox/`，本機 Claude Code 每 2 小時一輪用 `gh api` 核實、去敏、寫短評並唯一負責改 README，兩者只透過 Git 裡的 `.collab/` 留言檔與任務板溝通；對外發文、star／fork、刪除、改公開設定一律等作者本人。協作紀錄與逐輪回執公開在倉庫。
- 核心目標：讓「找料」與「把關」分給不同代理，避免同一個代理既推薦又自己收錄；用明文收錄門檻、暫緩清單和停機條件，讓每天的更新可追溯、可審。
- 分類／標籤：內容策展／跨代理分工／Git 非同步交接／收錄門檻
- 目標使用者：維護 awesome list、資源索引、案例庫等需要每天增補又要求查證的人
- 工具：Grok Bot（雲端電腦、每日 routine「X 雷達」）／Claude Code（作者本機，`/loop` 定時輪詢、`gh api` 核實）／GitHub（公開倉庫、`.collab/` 留言與任務板、link-check CI）
- 首次收錄／最近查證：2026-10-21 11:47（台灣時間）
- 證據狀態：`author-demo`（作者自述＋公開倉庫中的協作協定、任務板、水位檔、留言回執與提交紀錄已讀）；本頁可複製提示詞為 `designed`
- 是否獨立重現：否

## 輸入與預期輸出

- 輸入：X 與 GitHub 上的新倉庫、模板、教學；倉庫內的收錄門檻（CONTRIBUTING）、任務板（`TASKS.md`）、暫緩清單（`recheck.md`）、雙向留言檔（`to-claude.md`／`to-grok.md`）。

## 建議操作流程（依來源整理）

1. 先寫明收錄門檻（例如活躍度、授權、與主題直接相關），並規定不符時是「不收」還是「暫緩到某日再查」。
2. 定好分工：找料的代理只寫候選檔與留言；查證的代理唯一可以改正式清單；對外動作只有人能做。
3. 用 Git 倉庫當交接信箱：任務板是唯一事實來源，留言只追加、不改對方內容，每則以時間＋署名開頭。
4. 查證端每輪先拉最新、檢查有沒有新訊號，沒有就不做事；記下水位（處理到哪則留言、連續閒置次數）。
5. 寫停機條件：連續閒置幾輪、最多跑幾輪或幾小時、碰到需要人決定的事就停。
6. 每輪回執逐項寫「收／不收／暫緩」與引用的規則條款，讓人事後能抽查。

## 所需連接、權限與限制

- 查證端需要對倉庫的寫入權；找料端最好只能寫自己的檔案或分支（來源是靠約定，不是技術強制）。
- 兩個代理同時改同一份檔案會互相覆蓋；來源的實際事故就是一方在另一方的工作目錄提交。
- 公開倉庫內不要寫入金鑰、收入數字、內部路徑或可識別個資（來源的 CONTRIBUTING 與每份配方末尾都有這項自查）。
- Claude Code 的 `/loop`、Grok Bot 的 routine 都會消耗各自的用量；來源以「只在白天跑」「無訊號不做事」控制。

## 驗收與可重現性

- 隨機抽 3 個「收」的項目，用回執中引用的門檻條款自己再查一次，結果應一致。
- 確認正式清單的每次修改都出自查證端，且有對應回執。
- 故意讓候選檔連續三輪沒有新內容，確認查證端會進入休眠並留言，而不是自己去找料。
