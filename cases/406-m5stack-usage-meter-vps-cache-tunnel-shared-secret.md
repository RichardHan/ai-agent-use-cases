# UC-406：做一台桌上「用量表」小螢幕：Bot 團隊一夜設計、隔天接上，裝置只問自己的伺服器，伺服器有人問才去查且快取 5 分鐘

- 情境：開發
- 標籤：裝置、用量、權限邊界、驗收
- 網站標題：想在桌上隨時看到 AI 每週額度用了多少？讓 Bot 團隊幫你做一台小螢幕用量表：登入資訊只放在自己的伺服器，有人問才查、查一次快取幾分鐘
- 一句話用途：日文作者 cbot 的 Grok Bot 團隊（主任、開發、設計、調查、宣傳、部落格 Bot）依本人一句「想用 M5Stack 顯示 Grok Bot 用量」，約 13 小時（含睡覺）做出 M5Stack Core2 用量表：設計 Bot 先交三版預覽給本人選、開發 Bot 寫自租 VPS 上的中繼（裝置來問時快取過期才去查、加鎖只查一次、失敗不連打）、經 Cloudflare Tunnel 對外並以標頭密語擋外人；最後依本人挑錯改成「已用％＋Bot／聊天分項＋重設日與剩幾天」的 v2。全文由 Bot 撰寫、本人提供點子與核可。**取用量的方式是非官方、未公開的內部介面，作者明說規約上有灰色地帶、隨時可能失效，文中刻意不提供細節。** 作者自述，本庫未重現。
- 核心目標：在小裝置上常駐顯示額度，又不把帳號登入資訊放進裝置、不讓對外端點被人連打而害帳號出事。
- 分類／標籤：硬體整合／用量可視化／中繼伺服器安全
- 目標使用者：有 ESP32／M5Stack 等小螢幕與一台自己的 VPS，想做常駐狀態顯示的進階使用者
- 工具：Grok Bot（多 Bot 團隊，分工主任／開發／設計／調查／宣傳／部落格）；M5Stack Core2（ESP32）；作者自租 VPS；Cloudflare Tunnel；作者另參考開源工具 omp（oh-my-pi）的取用量方式（非官方）
- 首次收錄／最近查證：2026-10-21 14:40（台灣時間）
- 證據狀態：`author-demo`（作者自述實作，文章由作者的 Bot 撰寫，附 v1／v2 畫面圖；文中註明部分畫面是在 PC 上以相同繪圖程式碼繪製，不是實機照片）；本頁可複製提示詞為 `designed`
- 是否獨立重現：否

  1. 10/20 23:32 本人提出需求，並要求「接上之前先給我預覽畫面」。主任 Bot 同時派給開發（先查資料從哪來）與設計（黑底預覽多案）。
  2. 23:39 開發回報找不到官方自動取得用量的方法，提議手動輸入；本人回「手動輸入就作廢」。主任起初限制「不用非官方 API」，向本人說明「非官方窗口、自負風險」與「等官方」二選一；本人表示他用 omp 取用量一直沒問題，決定採用與 omp 相同的方式。**Bot 團隊在文中明說這不是官方路線、規約上灰色、隨時可能壞，並刻意不寫可照抄的細節。**
  3. 架構：裝置不直接查 xAI，中間放一台 VPS——登入資訊不進裝置；非官方介面變了只需改伺服器；不論裝置問幾次，都由伺服器控制查詢頻率。
  4. 00:28 本人提出「裝置來問時，若沒有 20 分鐘內的快取才即時查、否則回快取」。開發改掉常駐計時器，加入「同時被問只由一方去查（加鎖）、失敗後一段時間內不重查」；自動測試 25 項通過。之後本人說 1–5 分鐘也可以，改為快取 5 分鐘；裝置每 15 分鐘來問一次。
  5. 早上本人問最終設計，三個 Bot 都推 A 案（大數字）；調查 Bot 另依本人引用的貼文提出版面點子，文中坦承這些點子沒有影響到設計。
  6. 09:43 本人問對外要不要用 Cloudflare Tunnel；主任贊成（VPS 不必開連接埠、自帶 HTTPS、可在 Cloudflare 端限流）。本人要求「加個密碼參數」，開發改成放在請求標頭而不是網址（網址易留在紀錄），網址帶密語反而直接拒絕；密語不對時伺服器絕不去查 xAI。
  7. 本人先說 VPS 自己弄、隨後改請 Bot 代勞；主任確認「只在作業期間給 sudo、做完拿掉」後，開發部署專用設定與服務（不碰 VPS 上原有的其他 Tunnel），驗證「無密語被拒、網址帶密語被拒、正確密語回傳％」後移除 sudo。密語只存在 VPS 檔案，從未出現在聊天；移除 sudo 後 Bot 自己也讀不到，由本人自行取用貼進 PC 設定。
  8. 燒錄卡關：本人 PC 上路徑含日文導致建置失敗→改在 Bot 的電腦建置、PC 只負責燒錄；裝置一直 OFFLINE→本人發現 Wi-Fi 是 5GHz（ESP32 只支援 2.4GHz），改用 2.4GHz 熱點後仍離線→開發加詳細日誌發現熱點沒發 DNS（0.0.0.0），改為取不到時用公共 DNS 才連上。11:32 本人回報可用。
  9. 11:36 本人挑錯：沒有 Grok Bot 的感覺、大字寫「剩餘」但條狀圖下寫「已用」不一致、要重設日與剩幾天、要看 Bot 與聊天各用多少。設計 Bot 承認是自己的設計錯誤，11:39 交 v2 全改成「已用」、分項堆疊條、不用官方商標只借風格；開發在 PC 上跑同一套繪圖碼與設計稿疊圖比對（誤差半像素內），測試增至 51 項；12:20 前後燒錄並比對完成，本人評「完美」。

## 建議操作流程（依作者做法整理；非官方取數部分本庫不提供、不建議照做）

1. 先決定資料來源是否有官方方法；若只有非官方方法，先向本人說明風險並讓本人決定，必要時寧可等官方（作者的主任 Bot 起初就是這樣設限）。
2. 把登入資訊與查詢邏輯放在自己的伺服器，裝置只拿已整理好的數字。
3. 伺服器採「有人問才查＋短時間快取＋加鎖＋失敗退避」，讓外部被問幾次都不會放大成對服務商的連打。
4. 對外用 Tunnel 而不開連接埠；以請求標頭帶共享密語，密語錯誤時不觸發任何外部查詢。
5. 給 Bot 伺服器權限時，只在作業期間開、驗證後立即收回，並請它回報「無密語／錯密語／正確」三種結果。
6. 先在 PC 上用同一份繪圖碼產生畫面，與設計稿比對後再燒錄；裝置離線時顯示 OFFLINE 與資料時間。

## 所需連接、權限與限制

- 需要一台自己管理的伺服器與 Tunnel 帳號；Bot 部署時要暫時的管理權限，作者的做法是作業期間才給、完成即收回。
- **非官方介面風險**：作者使用未公開的內部窗口取用量，Bot 團隊在文中明說可能違反規約、可能失效；本庫不收錄其方法，也不從本案推定任何官方用量 API 存在。
- 帳號登入資訊放在伺服器上，伺服器若被入侵即等同帳號外洩；本案未公開其保護方式。
- ESP32 只支援 2.4GHz Wi-Fi；有些熱點不發 DNS（作者實際遇到）。
- 多 Bot 團隊一夜作業會消耗用量；作者未給數字。

## 驗收與可重現性

- 裝置上的％要與官方設定畫面顯示的用量對照（作者的調查 Bot 也這樣提醒本人）。
- 對端點分別送「無密語、網址帶密語、錯誤密語、正確密語」四種請求，只有最後一種回傳數字，且前三種不觸發外部查詢。
- 短時間內連續請求多次，確認對服務商的實際查詢只有一次。
- 拔掉網路確認裝置顯示 OFFLINE 與資料時間，而不是假裝仍是最新值。
- 本庫未重現。
