# UC-412：把Podcast一集的逐字稿交給dots，由它挑重點、找縮圖、編成note文章並發布，再發一則X宣傳

- 情境：創作
- 標籤：播客、逐字稿、note、發布
- 網站標題：錄完Podcast還要寫整理文？把逐字稿交給dots，它挑重點、找縮圖、改寫成可讀文章後發到note，連宣傳貼文都發了
- 一句話用途：日文作者 Kai（@kai_ishimine__，沖繩 Podcast「Okinawa Echoes」主持人之一）說他只把一集的文字稿交給 ChatGPT dots，dots 自己挑出段落、找縮圖、寫成文章、投稿到 note，並用節目帳號發了一則介紹貼文；那篇 note 文章公開可讀，文首有「依逐字稿編輯、保留原意」的說明。作者自述，本庫未重現。
- 核心目標：節目做完後，把「逐字稿→可讀的整理文章→發布→宣傳」這段雜事交給代理，人只負責錄音與事後檢查。
- 分類／標籤：Podcast 後製／內容再利用／發布
- 目標使用者：有固定節目（Podcast、廣播、直播）、想每集都有整理文章但沒時間寫的創作者
- 工具：ChatGPT dots（作者在 X 自述；文章本文只說是 ChatGPT Pro 方案）／note／X
- 首次收錄／最近查證：2026-10-21 20:50（台灣時間）
- 證據狀態：`author-demo`（作者 X 自述＋公開產出：note 文章與節目帳號的宣傳貼文）；dots 實際操作畫面、權限設定與人工修改幅度未公開；本頁可複製提示詞為 `designed`
- 是否獨立重現：否

## 輸入與預期輸出

- 輸入：一集節目的逐字稿；節目名稱、YouTube／Spotify／Apple Podcast 連結；（作者未說明）可用的縮圖素材來源。
- 輸出：一篇 note 文章（導言、「這集想傳達的事」三點摘要、依段落分小標的對話整理、文首編輯聲明、文末收聽連結與標籤）；一則 X 宣傳貼文附文章連結。

## 建議操作流程（本庫依來源整理）

1. 先只做「逐字稿→文章草稿」：要求保留說話者原意、標出刪減處，不加入節目沒講的事實或數字。
2. 草稿中的價格、方案名稱、日期等事實，要求附「逐字稿第幾段」或標「錄製時說法」。
3. 縮圖只用自己的節目素材或可商用素材，記下來源。
4. 發布與宣傳先設成「需要我核准」；跑順幾集後，再決定是否讓代理直接發。
5. 每集發布後，對照一次文章與逐字稿，抽查3處引述。

## 可複製提示詞（本庫原創設計，未實跑）

> 這是我們節目第{N}集的逐字稿（附件）。請寫一篇 note 文章草稿：導言{150}字內、「這集想傳達的三件事」、依話題分段的對話整理（保留說話者名稱與原意，只刪口頭禪與重複），文首加一句「本文依逐字稿編輯」的說明，文末放收聽連結{連結}。不得加入逐字稿沒有的數字、價格或事實；價格與方案名稱一律標「錄製時」。另外起草一則{140}字內的 X 宣傳貼文。縮圖只從{我的素材資料夾}挑。全部完成後先給我看，不要發布；我回「發布」後才投稿 note 並發文。

## 所需連接、權限與限制

- 需要讓代理能登入 note 與 X（屬對外發布）；建議逐篇核准，至少保留發布前預覽。
- 逐字稿可能含來賓或第三方的私人資訊，交給代理前先刪。
- 文章屬於節目衍生內容，若有來賓，需確認對方同意文字化發布。
- dots 方案與可用地區依 OpenAI 公告；本頁不推定 Grok Bot 或 Muse 有相同發布動作。

- 確認文首編輯聲明、收聽連結都在；縮圖來源有紀錄。

## 2026-10-22補充：輸入成功不代表草稿已保存，單一路徑恢復不等於全面恢復

日文作者ねこめし的[10月17日公開紀錄](https://note.com/neko_messy/n/nb5f7f7c8063c)描述另一篇文章的保存失敗，不是Kai原案例事故：雲端能開清單、輸入既有測試草稿，卻未存下；10月15日23:57日本時間把空測試稿重開後仍為0字，並非原有稿件被刪。10月17日本機路徑依序通過既有稿重開、新稿保存、核准後公開及正文／圖片／設定核對，當天雲端仍失敗。重啟與更新發生在恢復之前，但因果及MXC錯誤根因未證。全文已讀，作者說文章由AI整理、人類終審；本庫未重現。

[note官方說明](https://www.help-note.com/hc/ja/articles/63256649152793)，頁面標2026-10-15更新，明示雲端瀏覽器不屬建議／支援環境，列出建立頁停載及草稿保存失敗。這支持可用性限制，不能診斷作者根因，也不能否定其他路徑的已公開產出。不同作者的成功與失敗併入同一內容發布流程，不另計案例。

可貼指令（本庫AI構想／未實測）：只審查我提供的匿名發布紀錄，分列文字輸入、保存、重新開啟仍存在、新稿保存、核准及公開後讀回；每項保留環境與時間。不要把畫面有字當保存成功，不把單一路徑成功當全面恢復；不登入、不發布、不重試失敗操作、不改用未授權電腦。若只准雲端，列明限制並停在可交付草稿。

本補充沒有核實成本或今日帳戶資格，亦不要求開放個人電腦。原稿、圖片授權與對外發布仍需分別確認。

## 2026-10-22補充：舊編輯頁覆蓋人工新稿，與保存失敗是兩種事故

[おかわり@YouTubeもおかわり的Libecity原文](https://library.libecity.com/articles/01M4FD64F8C40YMBY22RQYWTK7)，日文，2026-10-12發表、10-14更新。已讀公開全文及兩則評論，圖像細節未驗。作者自述在dots雲端讀GitHub作業說明，把短測試文與一張圖存成非公開草稿，設定後約12分鐘並由本人確認非公開；沒有明確關閉再重開的內容核對，不能寫成公開發布或完整保存驗收。

同文記錄另一個風險：雲端仍開著舊編輯頁，未核對人工最新改稿便保存，覆蓋新內容。作者後來另用只有本人修改、有版本歷史的Google Docs保留母稿；沒有已復原、衝突檢查通過或後續不再發生的證據。15篇系列仍在準備，雲端改善原因只是作者假說。這不是Kai原案例事故，也不是前段note空稿保存失敗；併同一文章流程，不增加案例數。

可貼指令（AI構想／未實測）：只用我提供的匿名版本紀錄，列出母稿版本、編輯頁載入時間、最近人工修改與保存後重開證據。母稿比編輯頁新、版本未知或有人仍在編輯，就只列差異並停止，不覆寫、不發布。以合成稿測試正常保存、人工先改稿、舊頁晚保存三種情境，保留各自預期及實際結果；不能用「非公開」當作不會覆蓋的保證。

上述指令未在任何產品執行，不保證dots自帶版本鎖；雲端與Docs各需既有適當權限，實際方案與費用未核，不授權登入或變更分享。
