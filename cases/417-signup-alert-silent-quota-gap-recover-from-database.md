# UC-417：報名通知信悄悄停了：讓Bot比對報名數找出缺口，追到寄信額度上限，再直接從資料庫補回名單

- 情境：工作
- 標籤：故障診斷、報名、通知、對帳
- 網站標題：課程報名通知突然不來了也沒報錯？讓Bot數報名人數找出中斷的那段，查出是免費寄信方案每天100封上限，再從網站資料庫把漏掉的人補回來
- 一句話用途：英文作者 @Texas_Twins_Dad 用免費寄信服務收課程網站的報名通知，某天達到每日100封上限後通知靜默停發；他的 Grok Bot 在統計報名數時發現中間有缺口，追到是每日上限，並且不升級方案、改從網站資料庫直接撈出報名紀錄補齊，作者稱646人報名、0人遺漏、0元額外花費。單則作者自述，本庫未重現。
- 核心目標：不要只靠「通知信」當報名紀錄；以網站資料庫為準，定期和通知數對帳，通知管道失靈時能發現並補救。
- 分類／標籤：營運監看／通知管道故障／名單對帳
- 目標使用者：用免費或低額寄信服務（交易型郵件 API）發報名、訂單通知的個人或小團隊
- 工具：Grok Bot／Resend（免費方案，每日100封上限，作者所述）／作者的課程網站資料庫（類型未說明）
- 首次收錄／最近查證：2026-10-22 08:46（台灣時間）
- 證據狀態：`author-demo`（單則 X 自述，無截圖、日誌或資料庫畫面）；本頁流程與提示詞為 `designed`

## 輸入與預期輸出

- 輸入：網站資料庫的報名紀錄（唯一真實來源）、通知信的送出紀錄或收件匣通知數、寄信服務的方案上限。
- 輸出：每個時段「資料庫報名數 vs 收到通知數」的對照，缺口所在時間範圍、推定原因與證據；補齊後的完整名單（只交本人，不對外寄送）。

## 建議操作流程（本庫設計，未實跑）

1. 先指定唯一真實來源：網站資料庫（或報名表後台）的報名紀錄，而不是通知信。
2. 請 Bot 以唯讀權限每天（或活動期間每幾小時）比一次：資料庫新增筆數 vs 同時段收到的通知數。
3. 數字對不上時，列出缺口時間範圍與缺的筆數，再查寄信服務的寄送紀錄與方案上限，回報推定原因與證據，不要直接改設定或升級付費方案。
4. 需要補發確認信或通知時，先交名單與草稿給本人核准；寄出量要考慮上限，避免再次撞牆。
5. 長期改法（由本人決定）：通知只當提醒，名單一律從資料庫匯出；或為通知管道設「今天寄送量接近上限」的警示。

## 可複製提示詞（本庫原創設計，未實跑）

> 以{報名資料庫／後台}為準，唯讀比對{日期範圍}每{N}小時的新增報名數與我收到的報名通知數。對不上就列出缺口時段、缺幾筆，並查{寄信服務}的寄送紀錄與方案上限，說明最可能的原因和你看到的證據。把缺漏的報名者整理成名單交給我，只包含姓名與報名時間等必要欄位。不要寫入資料庫、不要改寄信設定、不要升級付費方案、不要寄信給任何報名者；需要補寄時先給我草稿與名單等我核准。

## 所需連接、權限與限制

- 讀資料庫通常需要連線字串或管理後台登入，屬高敏感權限；建議只開唯讀帳號，憑證放在 Bot 的安全機密欄位，不貼進對話。
- 報名者個資（姓名、電子郵件）只供本人使用；不要讓 Bot 把名單寄給第三方或公開。
- 「不升級就解決」是作者情境；若通知是報名者收到的確認信，漏寄可能需要補寄，這是對外動作，需本人核准。
- 作者未報告 Bot 用量與費用。

## 驗收與可重現性

- 用測試環境或假報名資料，人為讓通知管道停發一段時間，確認 Bot 能指出正確缺口時段與筆數。
- 抽查補回名單與資料庫筆數一致、無重複。
- 本庫未重現；646／0 為作者自述。
