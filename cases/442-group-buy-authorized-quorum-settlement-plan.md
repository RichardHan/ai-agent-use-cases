# UC-442：群聊團購先核保留款與最低量，再核准同一版本的沙盒結算

- 網站標題：群組裡說要買，不等於已授權保留款
- 一句話用途：作者以 Grok Bot 協作建立團購原型，將合成聊天意向、實際沙盒授權與最低成團量分開，依精確計畫核准部分請款或解除保留。
- 情境：開發
- 標籤：團購、狀態機、沙盒、核准、冪等
- 工具：Grok Bot（開發與測試協作）／Gemini（原型聊天解析）／PayPal Sandbox／Python
- 證據狀態：B 級作者實作自述＋公開原碼及沙盒結果；本庫未執行、未獨立重現，不是正式營運或真實付款成果。
- 查證日期：2026-10-23（台灣時間）

## 問題與作者實際流程

Tipping Point 的作者 sai error（GitHub whhhh1500）處理群聊團購中的加購、取消、代訂與模糊承諾。原型把聊天解析為有型別事件，再由確定性規則維護份數；只有已授權保留款的份數才計入最低成團量，不能把「我可能要」當付款承諾。

作者自述 Grok Bot 寫了大部分程式、測試、合成聊天與文件，並協助執行沙盒買家流程。部署後的聊天解析使用 Gemini，不能把它說成 Grok Bot 原生付款功能。專案目前只在本機運作、未公開部署，三組聊天均為虛構。

結算先產生包含結果、幣別與逐筆動作的計畫雜湊；核准的雜湊不符就拒絕執行。達最低量依最終級距部分請款，未達則解除保留。原碼為每個動作產生可重用請求識別碼，但這不等於已證明所有故障情境永不重複扣款；逐筆錯誤仍須追蹤，不能把整批當成功。

## 具體結果與反例

- 作者的沙盒筆記記錄部分請款成功；對已完成請款與已解除授權再操作時，收到相應錯誤；太早重新授權也遭拒。這是作者記錄，不是本庫重測。
- 作者稱 151 項自動測試通過。聊天評估的 7/7 僅限三組合成聊天中完成的模型呼叫；429、503、逾時後的規則備援不可混算為模型全通過。
- 較弱模型曾把份數分給錯誤的人，接地檢查拒收；姓名括號附註又曾造成誤拒，只對特定格式調整。不能因此推論真實多語言群聊皆可靠。
- 示範的襪子團購數字是沙盒／合成情境，沒有真實營收、節省或銀行入帳證據。

## 操作步驟（本庫設計，未實測）

1. 只用虛構聊天，列出確定購買、可能購買、代訂、增量與取消的事件，以及需要人工釐清的歧義。
2. 分別建立意向份數與模擬授權份數；增量不得沿用不足額的授權。
3. 以模擬資料計算最低量與價格級距，產生逐筆部分請款／解除保留計畫，不實際呼叫金流。
4. 讓核准綁定精確計畫版本；份數、幣別或動作改變即要求重核，不沿用舊核准。
5. 規劃重試、部分失敗、逾期、重複事件與取消競爭的驗收；分開記每筆結果，不用整批完成標籤掩蓋失敗。

## 可貼指令（原創設計，未實測）

請用六則完全虛構的團購聊天示範確定購買、可能購買、代訂、取消及加量。輸出事件、意向份數、模擬授權份數、最低成團量與逐筆模擬結算計畫。核准必須綁定同一版本；改動後舊核准失效。列出重試與部分失敗測試，但不要執行程式、登入、建立帳戶、呼叫 API 或操作真實付款。無法判斷的聊天標待人工確認。

## 官方支持、權限與費用限制

PayPal 官方區分授權保留與實際請款，通常授權期 29 天、最初 3 天為 honor period；這不是保證請款成功。部分請款涉及帳戶條件。官方亦明示沙盒授權不會在第 29 天自動過期，不能靠等待沙盒時間宣稱正式逾期處理已驗收。

作者限制活動在 72 小時內是專案設計，不是所有 PayPal 授權的有效期限。正式環境、地區／商家資格、費用、退款與消費者義務均未在本輪核完；模型費用亦未核。任何正式金流、憑證與客戶聊天都需另行授權及專業驗收。公開程式碼或作者測試不等於官方認證。
