# UC-444｜新版本上線後，把功能完成消息回給原提問者

- 網站標題：新功能完成後找回原提問者
- 一句話用途：以已發布版本的變更紀錄對照歷史需求，先產生可追溯的個別回覆草稿，而不是向全部用戶廣播。
- 情境：工作
- 標籤：產品回饋、版本更新、需求追蹤、人工核准
- 分類：B｜作者實作自述，未獨立重現
- 適用工具：Grok Bot；不得泛化為 Muse 或 ChatGPT dots 已驗證功能。
- 查閱日期：2026-10-23，Asia/Taipei

## 問題與作者實際結果

ArtShooter雪峰經營 iPad 應用，想把散落社群的功能需求留存，等功能完成再通知原提問者。9月12日文章自述以 Grok Bot 處理小紅書留言並按 changelog 找人回覆，達到預期；但展開大量留言慢、定位單一留言困難，且擔心帳號風控。9月20日後續文章描述實際做法：收集指定貼文留言或私訊，版本更新時找出相關需求、擬稿，經本人確認才發送。

這是作者自述的使用結果，不是本庫實測。未公開逐筆配對、送達紀錄、完整性量測或省時數據；不能推定全部留言皆收齊、回覆零錯誤或平台允許自動化。前文另用帳號的做法僅記為風險背景，不建議用來規避平台限制。

## 可以學習的流程

以下是整理者重新設計的安全實作順序，未實測，不是作者逐字操作：
1. 先用虛構或已合法匯出的回饋資料，保留來源識別碼、需求內容、可見範圍與處理狀態。
2. 僅以已發布的版本說明為功能完成依據。計畫、測試版及部分支援不得寫成已對所有人開放。
3. 將每則需求配對到明確版本條目；不確定、相似但未解決、已回覆或沒有合法聯絡方式者分開列。
4. 產生原提問者專屬草稿及依據，交本人逐項審核。練習止於草稿，不登入或傳送。
5. 真正對外回覆須另核平台條款、資料使用權與發送授權，並以實際結果確認，不把草稿當送達。

## 可貼指令（AI 構想／未實測）

只讀我提供的虛構回饋清單及已發布 changelog。建立「回饋識別碼、原需求、對應版本與證據、是否完整解決、草稿、待核事項」對照。對尚未發布、部分解決、功能名稱相似或來源不明者不要寫完成通知。相同回饋與版本只列一次；沒有來源連結就明說，不生成假的留言網址。先交草稿及人工驗收清單，不登入、爬取私訊、發送、付款或改權限。

## 驗收與反例（整理者設計）

- 合成測試包含已解決、部分解決、只在計畫中、重複留言及已通知五類；後四類不能混入可直接發送清單。
- 驗收對象是版本與需求的可追溯配對，不是回覆數量。
- 來源中途讀取失敗必須顯示覆蓋缺口；不能聲稱完整盤點。
- 本庫未執行上述測試，也未操作作者帳戶或聯絡其用戶。
