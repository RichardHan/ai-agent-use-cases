# UC-456：小網站不架後台：Muse 改 Markdown、推到 GitHub，自動建置成靜態頁

- 情境：工作
- 標籤：網站、GitHub、發布、權限
- 網站標題：店家或社區小網站不想養 WordPress？用一句話請 Muse 改 Markdown，推到 GitHub 後自動變成靜態網頁
- 一句話用途：日文作者 oosawak 把網站內容全部放成 GitHub 上的 Markdown，push 後自動轉 JSON、產生靜態 HTML，以 GitHub Pages 公開；日常「寫一篇」「改版面」「把 Facebook 貼文變成文章」都用話請 Muse 做。作者自述已有多個示範站與一個統合入口在運作，並公開 MIT 版建置程式；Muse 實際操作畫面與權限設定未公開，本庫未重現。
- 核心目標：把網站公開端「不跑任何程式」，降低外掛與伺服器漏洞的攻擊面，同時讓不懂 Git 的人也能用自然語言維護內容。
- 分類／標籤：網站維護／內容發布／代理協作
- 目標使用者：只需公告、文章、介紹頁的小店、社區、個人作品站維護者
- 工具：Meta Muse／GitHub（倉庫、Actions、Pages）／作者的 [oosawak/markdown-cms](https://github.com/oosawak/markdown-cms)（MIT）；Facebook（作者自述貼文轉文章的入口）
- 首次收錄／最近查證：2026-10-26 08:52（台灣時間）
- 證據狀態：`author-demo`（作者自述＋公開示範站與公開倉庫）；部分入口標明是構想；本頁提示詞為 `designed`
- 是否獨立重現：否

## 輸入與預期輸出

- 輸入：使用者口頭／文字需求（「用這段文字建一篇文章」「版面改成這樣」「把這則 FB 貼文變成文章」）、GitHub 上的 Markdown 正本。
- 輸出：Muse 更新的 Markdown 提交 → 自動建置 → GitHub Pages 上的靜態頁。

## 建議操作流程（本庫依來源整理＋自行設計，未實測）

1. 先用不重要的測試倉庫與 Pages 網址開始；只給代理這一個倉庫的寫入權，不給整個帳號。
2. 把「新增文章」「改版面」分成不同請求；每次請代理先回報要改的檔案清單與差異，人確認後才提交。
3. 提交後檢查建置是否成功、公開頁是否出現預期內容；失敗就請代理回報建置記錄，不要讓它反覆重推。
4. 從 Facebook 等社群轉文章時，只轉自己的貼文；圖片、他人留言與肖像先人工確認可公開。
5. 需要留言、會員、付款、預約時，不要硬塞進靜態站，改接外部服務並各自另核權限。
