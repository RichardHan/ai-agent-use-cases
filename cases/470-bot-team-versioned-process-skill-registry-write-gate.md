# UC-470：多個 Bot 共用 CRM 與記帳系統：每個業務流程只有一份版本化技能，Bot 簽收最新版才准寫入

- 情境：開發
- 標籤：多代理、版本、核准、MCP
- 網站標題：十幾個 Bot 寫同一套 CRM，規則越跑越歪？在自建工具伺服器加「流程技能登記」：沒確認最新版就不能寫入，改規則要像 PR 一樣送審
- 一句話用途：英文作者 @malmaladei 有十來個 Grok Bot 透過自建 MCP 伺服器連到自己的 CRM、外聯與記帳工具；為了避免「流程漂移」（有的 Bot 照上月規則、有的自己發揮），他在伺服器內加了技能登記：每個業務流程只有一份帶版本的技能，Bot 必須登記並確認目前版本，寫入工具才接受呼叫；Bot 只能以差異提案改流程，關鍵流程須本人核准才上線。作者自述，無截圖；本庫未重現。
- 核心目標：把「每個 Bot 用哪一版流程」變成伺服器端強制、可稽核的事實，而不是靠提示詞自律。
- 分類／標籤：多代理治理／流程版本控制／寫入權限閘門
- 目標使用者：已讓多個代理寫入同一套內部系統（CRM、記帳、預約）的小團隊或個人經營者
- 工具：Grok Bot（多 Bot、技能、routine）／作者自建 MCP 伺服器（CRM、外聯、記帳）
- 首次收錄／最近查證：2026-10-29 08:51（台灣時間）
- 證據狀態：`author-demo`（單則長文自述；伺服器程式與流程頁未公開）
- 是否獨立重現：否

## 輸入與預期輸出

- 輸入：每個業務流程的現行技能（例如登錄潛在客戶、歸檔收據、安排追蹤）與版本號；各 Bot 的登記與確認紀錄；Bot 提出的修改差異。
- 輸出：寫入工具的放行／拒絕；「哪個 Bot 跑哪一版」的流程頁；待本人核准的流程修改。

## 來源版本

### 來源A：@malmaladei（X，英文）

- 原帖：[x.com/malmaladei/status/2115455350849577424](https://x.com/malmaladei/status/2115455350849577424)，2026-10-28 14:47 UTC（台灣時間 22:47）；X API 讀長文全文，無附圖。
- 取得內容（翻譯摘要）：
  1. 每個業務流程只有一份帶版本的技能：怎麼登錄 lead、怎麼歸檔收據、怎麼排追蹤。
  2. Bot 必須先登記並確認目前版本，寫入工具才接受它的呼叫。
  3. Bot 可以提出改善，但只能是差異（像 pull request）；關鍵技能的新版本要本人核准才生效。
  4. 有一頁顯示每個 Bot 正在用哪一版。
  5. Grok Bot 端的技能與 routine 視為流程的「本機安裝」，登記處是唯一真實來源；技能更新後，跑該 routine 的 Bot 在下一次寫入前取得並確認新版。
- 作者觀點：代理系統的可靠度更多來自版本、核准、稽核紀錄這類「無聊的治理」，而不是更聰明的模型。
- 缺口：伺服器實作、確認機制（如何驗證 Bot 真的讀了新版）、被拒次數或錯誤率都未公開。

## 建議操作流程（本庫依來源整理＋設計，未實測）

1. 先挑一個會寫入的流程（例如登錄 lead），寫成單一技能檔並給版本號。
2. 在寫入工具前加檢查：呼叫附帶的版本號不等於現行版本就拒絕，並回覆要先讀哪一版。
3. Bot 的修改建議只收差異檔，本人核准後才升版；升版後觀察所有 Bot 第一次寫入是否帶新版號。
4. 每週看流程頁：有沒有 Bot 長期停在舊版、被拒寫入的次數。

## 可複製提示詞（本庫原創設計，未實跑）

> 在寫入 CRM 之前，先讀〔流程技能名稱〕目前的版本號與內容，在呼叫寫入工具時附上這個版本號。如果工具回覆版本過舊，停止寫入、重新讀取最新版、在回報中說明差異，再重試一次；第二次仍被拒就停下並通知我。想改流程時，只寫出建議的差異與理由，不要自行修改技能。

## 所需連接、權限與限制

- 需要能修改自建 MCP 伺服器；Grok Bot 官方未提供這種伺服器端版本閘門，這是作者自建。
- 確認版本只證明 Bot 宣稱讀了新版，不保證執行正確；仍需抽查寫入結果。

## 驗收與可重現性

- 可驗收：拿舊版號呼叫寫入工具應被拒；升版後各 Bot 的確認紀錄與流程頁一致。
- 作者無公開程式或紀錄；本庫未重現。
