# UC-489：雲端 VM 與自家 DMZ 裡的 VM 各能開哪些網站？實測 12 站並分「到得了／登得進／自動操作得完」三層，寫成清單規定代理開工前先查

- 情境：開發
- 標籤：雲端電腦、瀏覽器自動化、資安、規則檔
- 網站標題：代理在雲端開不了 Amazon、note 登不進去？先量好每個網站在哪個環境能用，寫成清單讓代理每次照著選
- 一句話用途：日文作者 satouyoshiaki 讓 Muse 做瀏覽器工作時，常在「這個環境打不開」卡住。他從 Muse 的雲端 VM（資料中心 IP）與家中 N100 小主機上 Proxmox 的 Ubuntu VM（住宅 IP，放在與家用網路隔開的 DMZ）對同樣 12 個網站實測：雲端 VM 連 Amazon.co.jp 與點數站在 SSL 交握逾時，其他回 200；但 200 不等於能用——note 在雲端 VM 登入兩次被限流，Colab 因瀏覽器沒有 Google 登入而無法執行，X 在家中 VM 用 headless 瀏覽器回 403、只有桌面工作階段的有頭模式能用。他把結果整理成「哪站用哪個環境」對照表，並寫進代理的作業規則：用新網站前先查表選環境、發現新限制當場補進清單。作者自述實測（2026-11-01），本庫未重現。
- 核心目標：把每次碰壁後的臨場試錯，換成事先量好、代理每次開工都會讀的環境選擇依據；同時讓家中代理環境出事時影響不到家人的設備。
- 分類／標籤：代理執行環境選擇／網站可用性實測／家用網路隔離
- 目標使用者：同時有雲端代理環境與自架機器、讓代理做購物、發文、筆記本等瀏覽器作業的進階使用者
- 工具：Meta Muse（雲端 VM＋作業規則／記憶）／自家 Proxmox VE 上的 Ubuntu VM（4 核、12GB、200GB）／NEC IX2215 路由器 ACL（DMZ）／Tailscale＋SSH；作者說此環境主要用 Muse 與 Codex
- 首次收錄／最近查證：2026-11-03 09:00（台灣時間）
- 證據狀態：`author-demo`（作者兩篇 Qiita 自述：12 站實測表、三層差異實例、網路構成圖與實機照片）；本頁提示詞為 `designed`
- 是否獨立重現：否

## 輸入與預期輸出

- 輸入：要讓代理使用的網站清單；兩個（或更多）執行環境；每站「到達／登入／自動操作」的實測方法。
- 輸出：一份到達性清單（每站在各環境的三層結果與建議環境），放在代理每次工作都會讀的位置；作業規則中的「先查表、新發現就補表」兩條。

### 來源A：satouyoshiaki／Qiita（日文）— 到達性清單

- 原始網址：[AI エージェントの作業環境ごとに「開けるサイト」が違ったので、到達性リストを作って使い分けることにした](https://qiita.com/satouyoshiaki/items/1ce9475f671250cab6d6)
- 發布：2026-11-02 09:19 JST（台灣時間 08:19）；原文語言：日文；實測日 2026-11-01。
- 取得內容（翻譯摘要）：
  1. 兩個環境：Muse VM（主工作場所，瀏覽器也在這裡，出口是資料中心 IP）；家中 VM「kaguya-home」（住宅 IP）。
  2. 以 Python urllib＋一般瀏覽器 User-Agent 從兩邊 GET 同樣 12 站並記錄狀態碼：Amazon.co.jp 與モッピー在 Muse VM 交握逾時、家中 VM 可達；X、note、Qiita、GitHub、楽天、Colab、AliExpress、Google／YouTube／Instagram 兩邊皆 200。作者另以瀏覽器確認 Amazon 在雲端被擋，推測是對資料中心 IP 的限制。
  3. 三層要分開記：到達（頁面開得了）、登入（該 IP／工作階段能否驗證）、自動操作（自動化能否做到底）。實例：note 兩邊都 200，但 Muse VM 登入兩次被「稍後再試」擋下，家中 VM 用 Google 登入可進到草稿編輯；Colab 只有家中 VM（以複製桌機實際 Chrome 設定檔啟動的方式）可執行；X 家中 VM headless 為 403，雲端端帳號本身受限、不使用。
  4. 對照表：Amazon／X／note／モッピー／Colab→家中 VM；Qiita／GitHub／楽天／AliExpress→皆可。並把「用新網站前先參照清單選環境」「新發現的限制隨時追加」寫入代理作業規則——代理換工作階段就會失去脈絡，不能靠「應該記得」。

- 作者報告結果：上述構成已在運作，附網路構成圖、Proxmox 主控台與主機照片（位址已遮蔽）。
- 失敗點／缺口：12 站只是單日單次 GET；登入與自動操作層只有個別實例，沒有整表；未說明代理遵守「先查表」規則的實際頻率或漏查事件；DMZ 文章未附 ACL 設定原文（見作者前一篇）。

## 建議操作流程（依來源整理）

1. 列出代理會用到的網站，從每個環境實測一次到達（狀態碼／逾時）。
2. 對需要登入或自動操作的網站，再分別測登入與自動化能否做到底；只記事實，不從 200 推論可用。
3. 整理成「網站→建議環境→已知限制」清單，放在代理每次都會讀的檔案。
4. 在作業規則加兩條：開工前先查清單；碰到新限制就補清單並回報。
5. 若要用住宅 IP 的自架環境，先把它和家人的設備隔開，管理入口限縮到本人裝置。

## 可複製提示詞（本庫原創，未實跑）

> 依 `［清單檔路徑］` 決定這次要在哪個環境開 ［網站］。若清單沒有這個網站，先在［環境A］與［環境B］各做一次：①GET 首頁記錄狀態碼或錯誤、②（若需要）嘗試登入但遇到驗證碼或限流就停、③記錄自動操作是否能完成［具體動作］。三層結果分開寫進清單，附日期，然後告訴我建議用哪個環境；未經我同意不要重試登入超過［1］次。

## 所需連接、權限與限制

- 實測登入可能觸發網站的限流或帳號風控；登入嘗試要設上限並由本人決定是否繼續。
- 自架環境用住宅 IP 繞過資料中心 IP 限制，仍須遵守各網站條款。
- 家中代理環境應與家用網路隔離；作者的 ACL 與路由器型號只是一例。
- 不推定其他代理產品的雲端環境有相同的封鎖清單；結果隨時間與網站政策改變，需定期重測。

## 驗收與可重現性

- 可驗收：清單每列都有日期與三層結果；代理在新網站開工前的對話或記錄能看到它先查表；碰到新限制後清單有更新。
- 本庫未重現。
