## 來源版本

### 來源A：@pjlbrunelle／X 文章（英文）

- 原始網址：[How to use a Grok Bot agent for daily QA and user testing](https://x.com/pjlbrunelle/status/2119194193100951742)，2026-11-07 22:24 UTC（台灣時間 2026-11-08 06:24）。原文語言：英文；本庫以 X API 讀取文章正文。另由 @DavidSmallx 於 2026-11-08 [轉介](https://x.com/DavidSmallx/status/2119362920270446810)。
- 取得內容（翻譯摘要）：
  - 設定＝一個 Routine＋幾個 Skills＋三個連接器。Routine 是觸發器，存的提示是「做一個新應用、本機與 Cloud 都跑、把壞掉的歸檔」。Skills 教代理認識產品；runbook 定義完成：真的應用、兩個環境、公開重現、工單、Slack 報告。
  - Slack 一則摘要＋每個新問題一串；Jira 每個新故障一張單，只有真的修好或復發才留言；GitHub 放別人可 clone 的公開庫，也是輸入（每天讀最新版本說明，可把當天應用對準剛上線的內容）。
  - 另有兩個小 Routine：同日稍晚的補跑檢查，只在當天沒跑完時介入；每週一重建工作點子清單，避免一直做同一題。
  - 當日實例：Pixeltable 0.7.24 修了 iterator 與 UDF（GitHub #1913）。代理升級後做了提琴工坊應用：試奏錄音依靜音切段、口述筆記走 WhisperX、標籤清單展開成每標籤一列，並在同一表上做幾次 schema 變更。本機與 Cloud 都可用，#1913 的修正符合說明；首次 Cloud 建立約 20 分鐘（映像要拉 torch），之後刪除託管資料庫。作者說範例庫累積到 50 個應用。
  - 當天抓到三個事前不會寫單元測試的問題：不同長度清單展開並要求忽略錯誤時，仍可能拋原始錯誤並丟掉整批（含有效列），Cloud 上只顯示通用代理錯誤；在既有資料上加計算欄位，只要有一列出錯，schema 更新就可能被拒並稱不支援（該路徑沒有 on_error）；schema 變更被拒時，CLI 建議的 force 旗標仍會失敗。
  - 判定修好的規則：用全新應用重測已知問題，不是重讀舊筆記；連續多個早上都沒復發才算修好。作者舉例時區錯誤某天因託管資料庫剛好在對的時區而「看似消失」，隔天又出現。
- 作者報告結果：每天有新應用與 Slack 摘要；三個新問題被找出。工單與重現庫內容本庫未逐一核對。

## 建議操作流程（依來源整理）

1. 連接團隊既有的聊天、工單與程式碼工具（作者用 Slack、Jira、GitHub）。
2. 寫 Skills：產品怎麼用、常見陷阱、怎樣算一份好的錯誤回報；再寫 runbook 定義「完成」。
3. 建一個排程 Routine，提示寫「工作」而不是點擊步驟；可讓它先讀最新版本說明。
4. 每次挑一個真實使用者會做的工作（不是功能名稱），做出完整應用，在使用者實際會用的環境跑。
5. 新故障：公開重現＋工單；已知問題：在新應用上重跑，不是重讀。Slack 只發摘要與分串。
6. 跑完拆掉不需要的資源；加一個補跑檢查與每週重建題庫的小 Routine。
7. 連續多日未復發才標記修好。

## 所需連接、權限與限制

- 需要 Grok Bot Routine 與 Slack／Jira／GitHub 連接；對外公開的重現庫要先確認不含機密或客戶資料。
- 每天建立雲端資源有費用與用量；作者的 Cloud 首建約 20 分鐘。Routine 每次都耗用量，週末也跑要先估算。
- 「補跑檢查」與「週一重建題庫」是作者的做法；排程是否準時、漏跑會不會被發現，仍要人看。
- 此做法是補充 CI，不是取代；不推定 Muse 或 ChatGPT dots 有同樣的 Routine＋Skills 組合。

## 驗收與可重現性

- 可驗收：每天 Slack 有摘要；新問題有可 clone 的重現與工單；已知問題的狀態只在新應用重測後才變；暫時資源有被清掉。
- 本庫未重現，未開啟作者的重現庫或工單。
