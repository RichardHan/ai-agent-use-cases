# UC-523：一人經營多客戶外展業務：Grok Bot 幕僚長＋每客戶一個 Bot＋有意願回信即觸發的回覆 Bot，送出前一律人工核准

- 情境：工作
- 標籤：多代理、銷售、Slack、核准、每日
- 網站標題：替多個客戶做外展開發，Bot 一多就亂？只跟一個幕僚長 Bot 說話，每個客戶一個專屬 Bot，對方回信有意願時自動起草回覆、等人核准
- 一句話用途：英文作者 @MichLieben介紹團隊 GTM 工程師 Louis 的設定：在 Grok Bot 上跑 1 個幕僚長＋約 20 個 Bot 服務多個客戶。幕僚長負責分派、每天早上送簡報（會議、到期任務、通話中答應過的事），並讀 Fireflies 通話紀錄；每個客戶一個 Bot（作者寫 9 個），各有自己的 Slack、Instantly 工作區與通話紀錄；Instantly 把潛在客戶標成「有意願」時以 webhook 交給該客戶的回覆 Bot，在 Slack 貼出公司評分與建議回覆，由人核准、修改或作廢；平日 18:00 回報各客戶數據。共用大腦是一個 GitHub 倉庫，每客戶一個資料夾加技能資料夾。作者自述，本庫未重現。
- 核心目標：讓一個人管理多個客戶的外展流程，同時把對外發送、發文與花費都放在人工核准和上限後面。
- 分類／標籤：多 Bot 組織／客戶隔離／Webhook 觸發
- 目標使用者：替多個客戶做冷郵件或 LinkedIn 外展、已在用 Instantly 與 Slack 的小型代理商或顧問
- 實作門檻：工具串接
- 工具：Grok Bot（多 Bot、排程、webhook）／Slack／Instantly／Fireflies／GitHub／Claude Code（作者寫搭配 ColdIQ MCP 做名單與文案重活）／Clay CLI
- 首次收錄／最近查證：2026-11-13 09:00（台灣時間）
- 證據狀態：`author-demo`（作者轉述同事的實際設定；X 長貼文附一張圖片（本庫未看）並稱完整設定與每個 Bot 的首則訊息在所引長文中，本庫只讀貼文、未讀長文全文）；貼文結尾導向一篇長文，帶推廣性質
- 是否獨立重現：否

## 輸入與預期輸出

- 輸入：各客戶的 Slack 頻道與 Instantly 工作區、通話錄音（Fireflies）、GitHub 上的客戶背景與技能檔。
- 輸出：每天早上給負責人的簡報；每通電話後的摘要與下一步；有意願回信時 Slack 上的公司評分＋建議回覆（待核准）；平日 18:00 各客戶的寄送數、回覆數、正向回覆數（先給 Louis 核准）；每日貼文草稿（人選定後才發）。

- 取得內容（翻譯摘要）：
  1. 幕僚長：Louis 只跟它說話，常在散步時用手機語音。它把每個要求轉給對的 Bot 並回報；每天早上送簡報；聽 Fireflies 的通話紀錄，掌握每個客戶的背景。作者建議從它開始。
  2. 客戶營運：每個客戶一個 Bot（他的設定有 9 個），各自有 Slack、Instantly 工作區與通話歷史：接 Slack 上的客戶需求、每通電話後寫摘要與下一步、把 15–45 天沒回應的名單放進新活動。因為「每個 Bot 看得到你連接的所有 App」，每個 Bot 的第一則訊息都寫明它只能碰哪些連接。
  3. 專家 Bot：一個「GTM 工程師」Bot 替所有客戶建名單；重活（名單、文案、爬蟲）交給 Claude Code 搭配 ColdIQ MCP，Grok Bot 只檢查品質——作者說 Grok Bot 自己也做得到，但有時很耗用量，所以讓它專心調度。
  4. 回覆 Bot：Instantly 收到有意願的回信 → webhook（「Lead is marked as interested」）送到該客戶的回覆 Bot → Bot 在 Slack 貼出公司評分與建議回覆 → Louis 或客戶核准、修改或作廢。一客戶一 Bot，越用越懂該客戶的買家。
  5. 回報 Bot：每個平日 18:00 給每個客戶一份回顧（寄送、回覆、正向回覆），先給 Louis 核准。
  6. 內容團隊：策略 Bot 每天起草貼文、寫作 Bot 模仿 Louis 的語氣、LinkedIn 助理處理其餘；由 Louis 選要發哪篇。曾有 LinkedIn Bot 自行發出整篇貼文（發現後立刻刪除），所以「發布貼文」一律設成先詢問。
  7. 大腦是 GitHub 倉庫：每客戶一個資料夾＋技能資料夾，所有 Bot 都從這裡讀；Louis 說沒有它產出「相當沒用」。
  8. 防護：對外送出前要人工核准；在 Bot 第一則訊息寫用量上限（例如驗證或補齊信箱最多 10,000 點數）；替答應試用的潛在客戶建的免費名單有上限（約 10 家公司、每家 15 個驗證信箱）。組織圖是先用 Grok Bot 兩週後，請它提出的最佳配置。

- 缺口：各 Bot 的實際首則訊息在長文中（本庫未讀）；webhook 如何把 Instantly 事件送到指定 Bot、權限設定畫面未見。

## 建議操作流程（依來源整理；本庫未實測）

1. 先建幕僚長 Bot，只負責收需求、分派、晨間簡報；再建共用的背景倉庫（每客戶一個資料夾）。
2. 每個客戶一個 Bot；第一則訊息寫明它只能用哪幾個連接、只服務哪個客戶、點數上限是多少。
3. 把「有意願回信」這類事件用 webhook 交給對應客戶的 Bot：只產出評分與建議回覆貼到 Slack，送出由人按。
4. 每日回報與貼文草稿都先給人看；任何「發布」或「寄出」權限設成先詢問。
5. 兩週後回顧：哪些 Bot 很少用、哪些重活改交給較省用量的工具。

## 可複製提示詞（本庫依來源改寫，未實跑）

> 你是「客戶 A」專屬的回覆 Bot。你只能使用 Slack 的 #client-a 頻道與 Instantly 的客戶 A 工作區，不得讀取或使用其他客戶的資料。收到有意願的回信時：①依倉庫 clients/a/ 的背景，給這家公司 1–5 分並寫一句理由；②起草一封回覆；③貼到 #client-a 等待核准。任何情況下都不要自己寄出、不要改活動設定；本月驗證或補齊信箱的點數超過 2,000 時停止並通知我。

## 所需連接、權限與限制

- 作者指出每個 Bot 都看得到所有已連接的 App：客戶隔離靠指示而非系統權限，跨客戶資料外洩風險要自己評估，必要時分帳號。
- 冷郵件、LinkedIn 自動化與名單補齊涉及個資與各地法規、平台條款；寄送前人工核准是作者明寫的防線。
- 作者曾遇到 Bot 自行發布貼文；發布、寄信類動作一律設成先詢問。
- 本案只涉及 Grok Bot；不推定 Meta Muse 或 ChatGPT dots 有相同的多 Bot 與 webhook 設定。

## 驗收與可重現性

- 可驗收：測試用的「有意願」事件只產生 Slack 草稿、沒有寄出；客戶 A 的 Bot 被問到客戶 B 時拒絕；點數上限到達時停止。
- 本庫未重現；作者未公開實際數據。
