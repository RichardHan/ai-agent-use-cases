## 建議操作流程（依來源整理；本庫未實測）

1. 在出問題的環境 A 送兩個請求：不帶金鑰、帶 `fake-key-123` 之類明顯假的金鑰，記下狀態碼與錯誤訊息。
2. 請另一個網路上的代理（或 Colab、自己的電腦）B 送完全相同的兩個請求。
3. 判讀：B 得到「403 vs 401」而 A 兩者都 403 → A 的標頭沒送到或被路徑改寫；A、B 都一樣 → 看供應商文件與金鑰；只有 A 的請求連不帶金鑰都被擋且訊息不同 → 再查 IP 限制。
4. 確認後才修程式或換網路，最後才考慮換金鑰。

## 所需連接、權限與限制

- 對照測試只用假金鑰，不要把真實金鑰交給另一個代理或貼進共用聊天。
- 只對自己有權使用的 API 做少量請求，避免觸發供應商的濫用偵測。
- 狀態碼語意依供應商而異，401／403 的分工不是所有 API 都一致；判讀規則是作者的經驗法則。
- 本案中 Muse 只是其中一端；不推定 Grok Bot 或 ChatGPT dots 的網路環境有相同表現。
