# UC-546：Slack 以專家和批判代理交叉檢查資安調查

- 情境：開發
- 標籤：資安、多代理、事件調查、失敗復盤
- 網站標題：資安代理說沒有問題時，讓另一個角色檢查證據與盲點
- 一句話用途：Slack 安全工程團隊將事件調查拆成主任、領域專家與批判角色，將可信發現和時間線交回主任繼續追查。
- 核心目標：減少單一代理過早下結論，讓分析師能查看推論與工具證據。
- 分類／標籤：資安／SOC／多代理調查
- 目標使用者：維運事件調查工具的資安工程師
- 實作門檻：進階開發
- 工具：MCP／Slack 自建調查服務
- 首次收錄／最近查證：2026-11-20
- 證據狀態：`official`（Slack 工程師第一手報告；非獨立測試）
- 是否獨立重現：否

## 來源版本

[Slack Engineering：Streamlining Security Investigations with Agents](https://slack.engineering/streamlining-security-investigations-with-agents/)，Dominic Marks，2025-12-01，英文。團隊初始單提示詞原型會跳到沒有充分質疑的結論；後改用各自調用模型的 Director、Access／Cloud／Code／Threat 專家與 Critic，Critic 檢查工具結果與證據，再組裝時間線。作者公開一份編修後報告：原警報所涉命令屬正常監控，但批判角色注意到專家漏掉祖先程序命令列中的憑證暴露；團隊轉交服務負責人處理。

## 建議操作流程（依來源整理；本庫未實測）

1. 從警報出發，分領域蒐集可追溯資料，記錄每次工具調用。
2. 批判角色審查主張與依據，彙整時間線；主任據此選擇繼續調查或結案報告。
3. 分析師檢視原始工具輸出、矛盾與未覆蓋處，再決定後續處置。

## 所需連接、權限與限制

來源以 MCP 暴露部分資料源，正式服務有佇列、工作者與可檢視調用的儀表板。結構化輸出也可能失敗、作弊或產生幻覺；作者沒有提供該例的整體偵測率或獨立對照試驗。報告經編修，不能拿單一成功案例代表所有調查。工具權限與記錄保存應遵循最小權限及敏感資料政策。

## 驗收與可重現性

用已知答案的去識別警報檢查每項結論是否有實際工具結果與可讀時間線；本庫未重現或驗證服務表現。

## 去重與版本紀錄

只收錄一個 Slack 調查系統，不將專家角色或範例事件拆成多案；與 [UC-545](545-cisco-live-soc-tier2-mcp-investigation.md) 的活動現場跨封包調查是不同團隊與系統。
