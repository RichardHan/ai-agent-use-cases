# UC-547：Figma 讓資安代理回查舊警報並提出修補草稿

- 情境：開發
- 標籤：資安、事件調查、知識庫、人工覆核
- 網站標題：警報再響時先找舊調查，再讓代理提出可審查的修補草稿
- 一句話用途：Figma 安全團隊自述把歷史警報與工程師調查紀錄接到代理，查詢身分、端點和日誌，必要時建立草稿 PR。
- 核心目標：減少值班人員重複蒐證並保留可審查的處置脈絡。
- 分類／標籤：資安／SOC／事件知識庫
- 目標使用者：管理企業安全警報與修補流程的工程師
- 實作門檻：進階開發
- 工具：Panther／Tines／Slack／AWS Bedrock／Amazon Kendra／Snowflake／Okta
- 首次收錄／最近查證：2026-11-20
- 證據狀態：`official`（Figma 安全工程團隊第一手自述；非獨立測試）
- 是否獨立重現：否

## 來源版本

[Figma：How we secure Figma’s internal systems with agents](https://www.figma.com/blog/how-we-secure-figmas-internal-systems-with-agents/)，Matthew Sullivan、Brad Girardeau，2026-07-29，英文。團隊把 Panther 警報及 Slack／Asana 上的人工調查脈絡索引，Tines 依意圖路由至具有限定工具的代理；子代理可查 Snowflake 日誌，代理可建立修補 PR。作者舉出服務帳號反覆觸發警報、代理找到既有草稿 PR 和討論脈絡的例子。團隊自報複雜警報解決時間約減少 70%、值班通知減少 20%；未提供樣本、測量方法與獨立驗證，不應視為保證。

## 建議操作流程（依來源整理；本庫未實測）

1. 取得新警報與相關歷史調查，區分個案先例、全域行為規則與結構化狀態。
2. 指派限定工具的代理查閱身分、端點和資料湖，產生附證據的調查。
3. 有必要時提出 PR；團隊以確定性步驟把代理 PR 設為草稿，由人審查。

## 可複製提示詞（本庫設計，未實測）

> 請比較［去識別新警報］與［授權、去識別且遮蔽憑證的歷史案例］，區分個案先例和可能適用的規則，附上每項引用及不同點。若資料不足請標待查；提出修補草案但不要寫入系統、建立或合併 PR，交由資安人員覆核。

## 所需連接、權限與限制

需要安全資料及模型服務授權；來源指出員工敏感資訊、公開頻道與工具權限都要以確定性控制保護。作者曾把所有教訓放入行為記憶而導致不希望的覆寫，後來區分先例與規則。草稿 PR 不代表修補已合併；來源的降級與自動化措施不應直接搬到其他環境。
