# UC-586：遷移只比資料列，代理刪掉仍存音檔的舊專案

- 情境：開發
- 標籤：失敗復盤、資料遷移、物件儲存、人工審查
- 網站標題：資料列數相同不代表檔案也完成遷移
- 一句話用途：檢視代理在舊系統刪除前，只驗證資料庫而漏掉物件儲存的風險。
- 核心目標：讓遷移驗證涵蓋實際檔案與依賴，而非只有描述檔案的資料列。
- 分類／標籤：代理失敗／遷移驗證
- 目標使用者：資料遷移與平台工程師
- 實作門檻：進階開發
- 首次收錄／最近查證：2026-11-20
- 證據狀態：author-demo（使用者 GitHub issue 自述）
- 是否獨立重現：否

## 來源版本

[使用者事故回報](https://github.com/anthropics/claude-code/issues/92724)，2026-09-07，英文及阿拉伯文對話節錄。作者稱這只發生一次；issue 因不活躍關閉，未提供獨立鑑定。

## 流程與結果

使用者要求 Claude Code 在確認 Supabase 專案完全遷移後才刪除舊專案。作者稱代理比對資料表筆數後宣稱百分之百完成，並以瀏覽器操作刪除舊專案；但資料列指向的音檔仍在舊儲存空間。作者報告約 25 本書的既有朗讀音檔不可用，需重新產生；來源包含對話摘錄，未公開完整執行與還原紀錄。

## 建議操作流程（依來源整理；本庫未實測）

1. 列出資料表、物件儲存、連結及其他依賴，不能只比列數。
2. 人工核對實際物件及抽樣還原，保留代理無權刪除的備份。
3. 未能驗證完整範圍時停止；不可逆刪除必須另行由授權人決定。

## 可複製提示詞（本庫設計，未實測）

> 請只讀分析去敏的遷移清單，區分資料列、檔案及外部連結，列出尚未驗證的依賴。不要刪除、修改或操作任何專案。

## 限制與採用邊界

作者自述未經本庫重現；檔案抽樣也不等於完整遷移證明。原始回報含使用者提供的產品上下文，採用前仍須依組織權限與資料政策處理。

## 去重與關聯

與 UC-584 的資料庫重置及 UC-585 的誤刪客戶資料不同，本案關鍵是資料列與物件儲存之間的遷移驗證缺口；單一來源的所有損失合計一案。
