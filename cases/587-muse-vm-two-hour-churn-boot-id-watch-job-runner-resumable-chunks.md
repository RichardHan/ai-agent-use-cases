# UC-587：Muse 的雲端電腦約每 2 小時整台換新：先用 boot_id 實測壽命，再把長工作改成「看得到狀態、可續跑」的小段

- 情境：開發
- 標籤：雲端電腦、長時間任務、斷點續跑、監控
- 網站標題：代理的雲端電腦會無預警重開、跑到一半的影片算繪就消失？先量出多久換一次，再用狀態檔、鎖與分段算繪讓工作被打斷也能接著做
- 一句話用途：日文作者 mryo0826 在 Qiita 自述：他的 Meta Muse 工作 VM 約每 2 小時連同執行中的程序整台被替換（家目錄保留），於是每 5 分鐘比對 `/proc/sys/kernel/random/boot_id` 記錄每一代的壽命，再把長工作改由自寫 job-runner 啟動、以 DONE／FAILED／RUNNING／LOST 判斷狀態，影片算繪切成 10 秒一段、已完成段落跳過，進度寫進工作日誌。
- 核心目標：在無法控制、也不知道原因的環境重置下，讓長時間工作不再白跑，並且能被偵測、從中斷處接續。
- 分類／標籤：代理執行環境／韌性設計／長任務
- 目標使用者：讓 Muse（或其他代理）在雲端電腦跑算繪、批次轉檔、資料處理等長工作的人
- 實作門檻：進階開發
- 工具：Meta Muse（工作用 Linux VM、hook）／bash（flock）／Python、Pillow／FFmpeg；作者另以 Claude Code 做主要開發、以 GitHub 信箱倉庫與 Muse 往來
- 首次收錄／最近查證：2026-11-20 09:30（台灣時間）
- 證據狀態：`author-demo`（作者自述實測＋觀測腳本與 job-runner 節錄、壽命分布圖；完整觀測紀錄未公開）
- 是否獨立重現：否

## 輸入與預期輸出

- 輸入：一台會不定期整台換新的代理工作 VM；需要跑數十分鐘以上的工作（例如 1,857 張影格的直式短影音算繪）。
- 輸出：每一代 VM 的換新時間紀錄；長工作的狀態檔（完成／失敗／執行中／遺失）；可只補做缺漏段落的分段成果；僅在疑似 LOST 時才通知本人。

## 來源版本

### 來源A：mryo0826／Qiita（日文）

- 原始網址：[Muse の VM は約2時間で入れ替わる（実測と対策）](https://qiita.com/mryo0826/items/c05efd7ac228fe85ab44)，2026-11-19 21:47 JST（台灣時間 20:47）；原文語言：日文。本庫以 Qiita 公開 API 讀全文。作者註明文章大部分由 Muse 撰寫、作者校訂。
- 作者的整體分工（背景）：主要開發由 Claude Code 負責，Muse（免費帳號）負責對外投稿與平台手續；兩者用 GitHub 上的「信箱倉庫」往來，Muse 每天固定檢查 2 次。作者另公開實踐指南 [aidd-practice-guide](https://github.com/mryo0826/aidd-practice-guide)。
- 取得內容（翻譯摘要）：
  1. **先量再設計**：hook 每 5 分鐘讀 `boot_id`，與上次保存值不同就把偵測時間、新舊 ID、依 uptime 回推的開機時間追加到工作日誌。
  2. **實測結果**：2026-11-17 22:28 至 11-18 23:06 約 24.6 小時出現 14 代，壽命中位數約 116 分鐘（最短 33、最長 165）；凌晨無人使用時也會換。追記：至 11-19 17:13 累計 28 代、42.8 小時，中位數 113 分鐘，但 11-19 早上集中出現 2、6、9 分鐘的極短世代。5 分鐘輪詢可能漏算更短的世代。
  3. **會消失／會保留**：保留家目錄下所有檔案；消失的是執行中程序、`/tmp`、系統區的變更（apt 套件、`/usr` 下的修改）。實際損失是一支算繪到一半的短影音。
  4. **對策一：用 job-runner 啟動長工作**：全域鎖確保重工作一次一支（拿不到回 BUSY）、每個工作再一把鎖防重複啟動；結束碼先寫暫存檔再改名（原子寫入）。判斷規則：有結束碼且為 0 並有成果 → DONE；非 0 → FAILED；無結束碼但鎖還在 → RUNNING；無結束碼也無鎖 → LOST。
  5. **對策二：切小段**：算繪切成 10 秒一段，已完成的段落核對長度後跳過，只補畫缺的，最後再接合。
  6. **對策三：連續性放在檔案**：工作現況以帶時間的小筆記追加到工作日誌；VM 換新本身不通知（太常發生），只有工作疑似 LOST 才通知。
  7. **延伸**：因系統區變更會消失，作者把工具改裝到家目錄並建工具台帳、每週自動檢查新版與安全更新、有差異才回報；同樣 240 張影格的算繪由 24.2 秒（Python 3.12＋Pillow）降到 11.1 秒（Python 3.15＋pillow-allsimd），切換前確認輸出逐位元組一致；實驗性 JIT 則實測無效、不採用。
- 作者報告結果：數字僅限作者單一帳號、2026-11-17～19 的觀測；換新原因平台未公開，作者也不知道。

## 建議操作流程（依來源整理；本庫未實測）

1. 先請代理在自己的 VM 放一個每 5 分鐘比對 `boot_id` 的小腳本，記錄一到兩天，算出壽命分布再決定工作要切多小。
2. 列出「會消失」與「會保留」的位置，所有狀態、工具與成果改放家目錄。
3. 長工作一律經 job-runner 啟動：鎖、結束碼原子寫入、成果檔路徑，四種狀態由檔案判斷，不靠代理記憶。
4. 把工作切成短於最短常見壽命的小段，每段完成即落地並可驗證（長度、雜湊）。
5. 只在 LOST 時通知本人；恢復時從日誌與狀態檔接續，不從頭重跑。

## 可複製提示詞（本庫原創，未實跑；改寫自來源流程）

> 你的工作電腦可能不定期整台重開，只保留家目錄。先寫一個每 5 分鐘比對 /proc/sys/kernel/random/boot_id 的檢查，變了就把時間與新舊 ID 追加到 ~/worklog/vm-boots.md，跑 24 小時後告訴我壽命中位數與最短值。之後所有超過 10 分鐘的工作都經由一支啟動腳本執行：用 flock 防重複、結束碼先寫暫存檔再改名、依「結束碼／鎖」判斷 DONE、FAILED、RUNNING、LOST；工作要切成能單獨驗證的小段，已完成的段落跳過。只有 LOST 時才通知我，不要因為重開本身打擾我。不要把任何密碼或權杖寫進腳本檔。

## 所需連接、權限與限制

- 只在代理自己的工作 VM 內執行；不需要連接本人帳號。
- 換新頻率是作者帳號、特定日期的觀測，平台未公開規格，可能隨時改變；不推定 Grok Bot 或 ChatGPT dots 的雲端電腦有相同行為。
- 系統套件會隨換新消失，安全更新要另設檢查流程。

## 驗收與可重現性

- 可驗收：換新紀錄的時間與 uptime 回推一致；故意中斷後，狀態判為 LOST 且重跑只補缺段；最終成果與一次跑完的成果逐位元組一致。
- 本庫未重現。
