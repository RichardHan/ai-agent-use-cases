# UC-588：讓 Muse 參加 8 小時的 ISUCON 效能調校賽：自備量測工具與當日手冊，Muse 量測、分析並派工給程式代理，一次只改一件，成敗由人看細項與多次量測判斷

- 情境：開發
- 標籤：效能調校、資料庫、量測、多代理
- 網站標題：把網站效能調校交給 AI 代理也要先量再改：比賽當天由 Muse 收集日誌、找最慢的 API 與 SQL、交給程式代理實作，每次只改一項並重測，分數跳動 ±2000 時不看單次分數
- 一句話用途：日文 Qiita 帳號 Oursship（文章署名後端工程師 H）自述：ISUCON 2026（規則允許 AI 分析與產生程式碼）中，量測、分析、實作與部署大多交給 Meta Muse，實作多由 Muse 指派 Antigravity CLI 完成，本人只做方針判斷與跑基準測試；分數由 3,197 提升到當日最終 23,728（官方成績 22,038，856 隊中第 460 名）。
- 核心目標：在時間有限的效能調校中，用 AI 加快實作與彙整，同時不讓「看起來合理但沒依據」的改動和分數雜訊主導判斷。
- 分類／標籤：效能調校／代理分工／量測驅動
- 目標使用者：想讓代理參與網站或資料庫效能改善、又需要自己保留判斷權的後端工程師
- 實作門檻：進階開發
- 工具：Meta Muse（雲端 VM、SSH、檔案與指令）／Antigravity CLI／Codex（作者嘗試但在 Muse VM 內無法用於實作）／gh／作者自製 Go 工具 isucon-kit／PostgreSQL

## 輸入與預期輸出

- 輸入：比賽提供的既有網站與 3 台伺服器；事先準備的量測工具與當日手冊；給 Muse 的專用 SSH 金鑰（只在伺服器登錄公開金鑰）。
- 輸出：基準分數與瓶頸排行；一次一項的改動與對應分數、細項；重開機後仍可重現的最終設定。

## 來源版本

### 來源A：Oursship（署名後端工程師 H）／Qiita（日文）

- 原始網址：[ISUCONを Muse にやらせてみた：計測と実装を任せた8時間の記録](https://qiita.com/Oursship/items/5cce61a710e3c702e5ff)，2026-11-19 15:10 JST（台灣時間 14:10）；原文語言：日文。本庫以 Qiita 公開 API 讀全文。比賽日期為 2026-10-31。工具倉庫：[yuuzin217/isucon-kit](https://github.com/yuuzin217/isucon-kit)。
- 取得內容（翻譯摘要）：
  1. **事前準備**：自製 Go 工具 isucon-kit（收集存取日誌與慢查詢日誌、統計最慢的 API／SQL、保存基準測試歷史以便和上次比較）；寫好當日手冊（量測步驟、部署步驟、重開機後改動是否仍在的重現性清單）。前一天在 Muse 的 VM 裝好工具並以練習資料跑完「收集→統計→報表」。
  2. **日誌交接兩案**：A 案 Muse 從自己的環境 SSH 到比賽伺服器直接收集與統計；B 案由本人取出日誌交給 Muse 只做分析。當天採 A 案；SSH 金鑰由 Muse 新建、只把公開金鑰登錄到伺服器，本人的金鑰不交出。依規則不把基準測試中的運算外移。
  3. **當日方針**：先不改任何東西量出基準與最大瓶頸；改動一次一項、每次重測、只保留有效的；最後確認重開機後改動仍在。
  4. **過程**：Muse 依量測結果提出快取＋索引等組合（3,197→4,589→8,712，畫像查詢平均 531ms→2.8ms）；解除整表鎖並統一 3 台程式（9,040）；之後連續三次下降，但**未改程式重跑**得到 10,148 → 認知單次分數會跳 ±2,000，改以各功能回應與 DB 統計＋多次量測判斷；後段把篩選與排序移到 DB 端、分段輸出等，到 20,101、23,269；Muse 盤點出 21 處上鎖位置，判定真正要改的只有 1 處。最高 26,116 再跑只有 21,074～22,772，未採用，最終以 23,728 定案。
  5. **卡關**：Codex 在 Muse VM 內缺少執行所需元件而無法用於實作；VM 會定期重開，使執行中的 Antigravity CLI 中斷（作者當時不知道 VM 會重開）；gh 事後改為 PAT 方式。
  6. **作者結論**：先量測、把「哪個功能／哪條 SQL 花幾秒」的數字交給 AI，假說才會準；把施策切成一件一件交給程式代理；成敗由人用數字判定。反省：太依賴 AI、對架構與資料庫理解淺，天花板也來得早，下次要先畫架構圖與 schema、分清楚交給 AI 與自己掌握的範圍。
- 作者報告結果：最終 23,728（官方 22,038、第 460 名／856 隊），作者自評為中段平凡成績。

## 建議操作流程（依來源整理；本庫未實測）

1. 事前把量測、部署、重現性檢查做成工具與手冊，並在代理環境實地跑過一次。
2. 給代理專用的新金鑰，只在目標伺服器登錄公開金鑰；不交出自己的金鑰。
3. 先量基準與瓶頸排行，再讓代理提出改動；每項改動附預期影響與回退方式。
4. 一次只套一項、部署、重測；同一設定至少跑兩次，以細項判斷，不看單次分數。
5. 收尾前重開機驗證所有改動仍在，再定案。

## 可複製提示詞（本庫原創，未實跑；改寫自來源流程）

> 這是限時的效能調校。你只能用你自己新建的 SSH 金鑰連到我登錄過公開金鑰的伺服器。先不要改任何東西：收集存取日誌與慢查詢，列出最花時間的前 5 個 API 與 SQL 和各自總耗時。之後每次只提出一項改動，寫明預期影響、怎麼回退，等我同意再交給程式代理實作與部署。每項改動後同一設定跑兩次基準，回報分數與各功能回應時間、DB 統計的差異；兩次差距大於 2,000 時不要下結論。結束前列出重開機後要確認的設定清單。

## 所需連接、權限與限制

- 需比賽或自有測試伺服器的 SSH 存取；只用代理專用金鑰，賽後撤銷。
- 必須遵守比賽規則（本次規則允許 AI 分析與產生程式碼、禁止運算外移）；正式服務請改在測試環境進行。
- 代理 VM 會不定期重開（見 UC-587），長時間執行的程式代理可能中斷；不推定 Grok Bot 或 ChatGPT dots 有相同環境與工具。

- 可驗收：每一項改動都能對回量測數字與兩次以上的基準結果；重開機後分數維持；未經同意的改動為 0。
