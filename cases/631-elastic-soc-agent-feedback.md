# UC-631：Elastic SOC 以舊結案紀錄回饋警報代理

- 情境：工作
- 標籤：資安、SOC、多代理、人工覆核
- 網站標題：資安警報參考歷史結案，再交分析師檢查
- 一句話用途：Elastic 內部 SOC 將規則指引與歷史人工結案原因交給多代理流程，改善警報調查摘要。
- 核心目標：讓代理結論附上下文與歷史錯誤線索。
- 分類／標籤：資安／SOC／警報調查
- 目標使用者：資安分析師與 SOC 工程師
- 實作門檻：進階開發
- 工具：Elastic Agent Builder／Elastic Workflows／Slack
- 首次收錄／最近查證：2026-11-21
- 證據狀態：official（Elastic 員工對自家 SOC 的第一手報告）
- 是否獨立重現：否

## 來源版本

[Elastic Security Labs：Inside Elastic's agentic SOC](https://www.elastic.co/security-labs/blog/alert-triage-agentic-soc-self-correcting-agents)，Maggie Musquez，2026-08-25，英文。團隊以其生產環境為產品使用場景，自報將代理結論與分析師結案原因比對的正確比例由 60% 提至 92%。

## 流程與結果

流程取得偵測規則調查指引、員工風險資訊與同規則近 30 日結案紀錄；模式代理整理歷史、調查代理查詢證據、摘要代理彙整後寫入案例與 Slack。分析師可檢查並結案，也可記錄錯誤供後續警報參考。原文所稱正確是與分析師結案理由一致，不等同獨立真值或偵測率；文章未完整交代樣本量和前後期間可比性。

## 建議操作流程（依來源整理；本庫未實測）

1. 在授權範圍取得警報、規則指引與歷史結案，限制員工資料用途。
2. 將模式、證據及建議分開呈現，保留查詢結果供分析師核對。
3. 人員決定結案或升級，並記錄錯誤；避免單憑歷史多數判斷新威脅。

## 限制與採用邊界

這是供應商自身部署自報，非獨立測試；前後變動不能證明單一因素造成改善。分析師結案也可能出錯，歷史意見可能造成自我強化。原文稱無工具代理可避免注入覆寫，但不應據此推定其輸出不受惡意輸入影響。本庫未重現。

## 去重與關聯

同一生產流程的三個代理不拆成三案；可對照 UC-630 的大學工單實驗與 UC-632 的活動 SOC。
