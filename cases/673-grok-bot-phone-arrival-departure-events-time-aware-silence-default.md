# UC-673：手機「抵達／離開」事件叫醒 Grok Bot：同一地點依時段做不同的事，對不上規則就一律不出聲

- 情境：生活
- 標籤：位置、webhook、通知減量、每日
- 網站標題：讓 Bot 知道你剛進超市、剛離開公司：午休自動改 Slack 狀態並 rebase PR、進超市推購物清單、進健身房調重量；其餘地點一律安靜
- 一句話用途：英文作者 Marcel Marais（自製 iPhone 位置紀錄 App Timeline 的開發者）在部落格自述，把手機每次「抵達／離開某地點」的事件經 webhook 送給 Grok Bot；Bot 依「地點＋時間＋筆記與行事曆」判斷該做什麼——平日 12:18 離開公司就把 Slack 改成午餐中並 rebase 兩個 PR、重跑不穩的 CI；週五進超市時依隔天行事曆的聚餐推一份購物清單；進健身房讀上次筆記與恢復數據、調高臥推重量並暫停 Slack。第一週「每到一處都幫忙」太吵，改為短短幾條具體規則＋「沒有高把握對上規則就什麼都不發」，一週 34 個停留點只剩 6 則通知。
- 核心目標：用位置事件取代「我得先打字說明我在哪」，同時把誤報壓到使用者還願意讀通知的程度。
- 分類／標籤：事件觸發／情境感知通知／靜默預設
- 目標使用者：已有位置紀錄工具（Timeline、OwnTracks、Home Assistant、iOS 捷徑等）且想讓 Bot 主動處理小雜事的人
- 實作門檻：工具串接
- 工具：Grok Bot（webhook 觸發）／Timeline（作者自家 App，含 webhook 與 MCP 伺服器）／Slack／GitHub／Google Calendar／Notion／Google Health；作者稱 OwnTracks、Home Assistant 或捷徑腳本也能送同類事件（本庫未核）
- 首次收錄／最近查證：2026-11-22 09:10（台灣時間）
- 本次增補查證：2026-11-24 08:55（台灣時間）；只核新增來源B，未重驗全案。
- 證據狀態：`author-demo`（作者部落格自述約一個月的使用；有互動示意圖但無原始 routine 文字或事件日誌；作者是位置 App 開發者，有推廣自家產品的利害關係）
- 是否獨立重現：否

## 輸入與預期輸出

- 輸入：手機端解析好的「停留點」事件（地點名稱、抵達／離開、時間），不送原始 GPS 軌跡；Bot 可讀的行事曆、筆記、健康數據。
- 輸出：符合規則時的少量動作（改 Slack 狀態、rebase 自己的分支、重跑 CI、購物清單、健身重量建議、Notion 小結、調燈）；不符合規則時不發任何訊息；每個叫醒 Bot 的事件都留一份傳遞紀錄。

## 來源版本

### 來源A：Marcel Marais／Timeline 部落格（英文）

- 原始網址：[Grok Bot symbiosis](https://timeline.place/guides/grok-bot-symbiosis)，頁面標示 Updated 2026-11-21；經 [Hacker News 投稿](https://news.ycombinator.com/item?id=50594515)（marcelmarais，2026-11-21 23:03 UTC，台灣時間 2026-11-22 07:03）發現；原文語言：英文。本庫讀公開全文。
- 取得內容（翻譯摘要）：
  1. 幾週前把手機的抵達／離開事件接進 Grok Bot（作者已有自家 App 的 webhook 與 MCP 伺服器）。
  2. 第一週把每個 `stop.arrived` 都轉給 Bot、只寫「到哪都幫忙」：4 分鐘買藥換來 140 字打氣文、中午回家拿耳機被問「準備休息了嗎」、室內定位漂移翻出三個月前的燈泡筆記，差點整套關掉。
  3. 改成幾條具體 routine，最後一條硬規則：停留點若沒有以高把握對上任何規則，就不輸出、不傳訊。仍轉送所有停留點（好讓 Bot 認得沒存過的超市或陌生城市機場），但一週 34 個停留點中 28 個零通知。
  4. 同一地點靠時間判斷意義：12:18 離開公司＝午餐（改狀態、rebase、重跑 CI）；18:35 離開＝下班，不再碰程式碼；13:15 回家多半是忘了充電器。
  5. 界線：可兩秒內復原的準備工作可自動做（Slack 狀態、草擬回覆、rebase 自己的功能分支、記錄訓練、調燈）；寄信給別人、合併到 main、花錢仍等本人按。不用位置事件開門或開玄關燈（偵測有數分鐘延遲）。只讓解析後的停留點與筆記離開手機，保留每個觸發事件的 payload 紀錄，可一鍵撤銷。
- 作者報告結果：通知從一週三十多則降到五六則後才重新開始讀；暫停 webhook 兩天時明顯感到少了它。無量化準確率。
- 缺口：沒有公開 routine 原文、規則清單全文、事件 payload 範例；健身重量調整與購物清單的品質僅為作者描述。

### 來源B：Marcel Marais／Timeline 部落格（英文，2026-11-24 08:55 補）

- 原始網址：[How footsteps cut my Grok Bot quota burn by 50%](https://timeline.place/guides/footsteps-instead-of-cron)，頁面標示 Updated 23 Nov 2026；經 [Hacker News 投稿](https://news.ycombinator.com/item?id=50619675)（2026-11-23 21:33 UTC，台灣時間 2026-11-24 05:33）發現；原文語言：英文。與來源A同一作者（位置 App 開發者，有推廣自家產品的利害關係）。本庫讀公開全文。
- 取得內容（翻譯摘要）：
  1. 問題：作者只用 Grok Bot 處理生活與工作雜事，但 15 分鐘 Slack／郵件急件檢查、20 分鐘 GitHub CI 監看、30 分鐘包裹與餐廳候位瀏覽器檢查、每小時總檢查，一週叫醒 VM 近 600 次；多數時候「沒事可做」仍耗每週額度，週四 15:20 就用完。
  2. 改法一：抵達／離開事件取代一半的輪詢——抵達公司時跑一次訊息摘要、午餐回來再補一次；中午 `stop.left` 時做 rebase 與 CI 清理；超市、健身房、機場的準備改成抵達才觸發，取消每小時總檢查。
  3. 改法二：仍需輪詢的（無 webhook 的訂位網站、包裹追蹤）改成「租約」：webhook 不直接叫醒 Bot，而是由 VM 上的小端點把目前地點、模式（office／home／travel／away）與到期時間寫進 `/state/presence.json`，寫檔不耗 token。每個輪詢只在對應租約有效時跑：在公司時 Slack 急件與 GitHub CI 每 45 分鐘、離開即關；在家 08:00–22:30 瀏覽器類每 2 小時；健身房或外出時完全不輪詢；抵達機場或換時區時改跑航班與鐵路監看。
  4. 關鍵：「不要叫醒 LLM 只為了查你在哪」。第一版在提示詞裡加「先呼叫位置工具，不在公司就停」幾乎沒省到，因為開一輪代理、載入系統提示與 MCP 結構描述本身就耗額度。改由 cron 先跑一支 shell 包裝腳本，用 `jq` 檢查 `presence.json` 的地點／模式與到期時間，不符就以 0 token 結束；GitHub 工作再加一層 `gh pr list --author @me --json statusCheckRollup` 預檢，全綠就不叫醒模型。
  5. 文末附一段給 Grok Bot 的設定提示詞（建 Standard Webhooks 端點、更新 presence 檔、用零 token gate 包住所有 cron、公司與家裡租約、只在抵達／離開時跑一次性 routine 並對不符的停留點保持安靜）。
- 作者報告結果：一週背景喚醒從 568 次降到 274 次（少 52%），週日晚上仍剩 42% 額度。
- 仍有的問題（作者自述）：手機沒電收不到 `stop.left`，只能靠 4 小時到期與 20:00 強制關閉；在家或咖啡店工作要手動輸入切換 office 模式；iOS 停留偵測有數分鐘延遲；臨時請 Bot 盯的價格或訂位若沒加到期時間會一直輪詢。正式環境告警與付款失敗應直接用推播 webhook，再由 Bot 依 presence 決定立刻打擾或留到早上。
- 缺口：數字為作者單週自報，無原始紀錄；包裝腳本與提示詞為作者公開範例，本庫未實跑。

## 建議操作流程（依來源整理並由本庫補成步驟；未實測）

1. 先只存 3–5 個常去地點（公司、家、超市、健身房），用手機端工具把「抵達／離開」送到 Bot 的 webhook；只送地點名稱與時間，不送連續 GPS。
2. 為每條規則寫清「地點＋時段＋要做的事＋可用的工具」，例如「平日 11:30–13:30 離開公司：Slack 狀態改午餐至 13:15，rebase 我自己的開放分支」。
3. 加一條總規則：沒有高把握對上任何規則時，不做事、不傳訊。
4. 把動作分兩類：可快速復原的可自動做；對外寄送、合併 main、付款只做草稿並等核准。
5. 每個觸發事件記一行（時間、地點、對上的規則或「無」、做了什麼），每週看一次誤報再調規則。

## 可複製提示詞（本庫原創，未實跑；改寫自來源流程）

> 之後你會收到我手機送來的「抵達／離開」事件（地點名稱＋時間）。只照下面這幾條規則行動：［規則1：地點、時段、動作］……。如果事件沒有以高把握對上任何一條規則，就什麼都不做、也不要傳訊息給我。能在幾秒內復原的事（改 Slack 狀態、rebase 我自己的分支、記筆記）可以直接做；寄信給別人、合併到 main、花錢一律先給我草稿等我說好。每個事件都在「位置事件紀錄」記一行：時間、地點、對上的規則或「無」、做了什麼。

## 所需連接、權限與限制

- 位置屬高度敏感個資：只送解析後的地點名稱，不送原始座標與軌跡；隨時可撤銷 webhook。
- 位置偵測有數分鐘延遲，不適合開門、開燈等需要即時的動作。
- 若目的在省額度，位置判斷要放在模型外（cron 前的 shell gate 讀狀態檔），寫進提示詞讓模型自己查位置仍會耗掉一整輪（來源B）。
- 規則不明確時誤報會讓人習慣性滑掉通知，連有用的也被忽略；靜默預設是此流程的關鍵。
- 不推定 Meta Muse 或 ChatGPT dots 有同樣的事件觸發方式。

## 驗收與可重現性

- 可驗收：一週停留點中有通知的比例；每則通知是否對應某條規則；可復原／需核准的動作是否分開；事件紀錄是否完整。
- 本庫未重現。
