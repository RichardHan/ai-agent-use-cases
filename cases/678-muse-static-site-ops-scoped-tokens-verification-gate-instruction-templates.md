  3. 六種指示：(a) 專案宣告；(b) 分工（交給 Muse：製作、驗證、部署、寫文與發文、告知、例行互動；不交：付款、建帳號與設密碼、方針決定）；(c) 驗證關卡（只公開通過的；數值計算對照權威測試資料；測試期望值不可由主體程式產生，而要用另寫的規則模型比對；用自動遊玩或模擬先找「卡死、到不了」的情況；畫面與實機呈現另外確認，測不到的老實回報）；(d) 動工前四問（有沒有搜尋需求、能不能寫成故事、能不能短期做完、結果是否因人而異而想分享），不滿足就附理由建議不做；(e) 回報（每次發布短報、每週總結、數字只寫實測）；(f) 失敗規則（隔一段時間只重試一次，不行就報告並停止；「處理成功」與「實際上線」分開確認；失敗手順記下來）。
  4. 踩坑表：Cloudflare 主控台被 Turnstile 擋 → 初設由人在瀏覽器做；GitHub SSH 被代理伺服器擋 → 改 Contents API；X 發文 403 → 隔一段時間重試一次，不行就交人手動；Qiita 短時間連續新增被限 → 間隔、等 10 分鐘再開一次；push 後 404 或舊內容 → 預期 1–4 分鐘建置反映，分開看 push 成功與上線；Web Analytics 標籤看不到 → bot User-Agent 不會被插入，要用實瀏覽器 UA 確認。

## 建議操作流程（依來源整理；本庫未實測）

1. 人建立專用帳號、網域與私有倉庫，接好 Git 連動部署。
2. 發 token：倉庫寫入只限單一倉庫內容；分析只給唯讀；經保管功能交給代理，並請代理列出實際權限。
3. 依序送出專案宣告、分工、驗證關卡、選題四問、回報格式、失敗規則六段指示。
4. 第一件作品照「動工前四問 → 實作 → 驗證關卡 → 部署並確認上線 → 回報 URL → 寫文與告知」跑一次。
5. 之後每週看總結，調整方針。

## 所需連接、權限與限制

- GitHub token 有單一倉庫寫入權，等於能改網站內容；作者以短效期、單一倉庫限縮。Cloudflare token 只讀分析。
- 代理代為在 note／Qiita／X 發文屬對外公開行為，作者在方針內授權免逐件核准；採用者應自行決定是否保留逐件核准。
- 平台的 bot 判定與發文頻率限制會擋下代理，失敗規則只重試一次以免觸發更多限制。
- 不推定 Grok Bot 或 ChatGPT dots 有相同的連接方式。
