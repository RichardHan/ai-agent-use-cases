# UC-686：讓 Grok Bot 當「外圈」：替每秒做 7 次決策的快速代理整理戰術目錄、標註真實對局、建評測集並補新戰術（以《任天堂明星大亂鬥 DX》為例）

- 情境：開發
- 標籤：多代理、評測、驗收、遊戲
- 網站標題：快的代理負責即時出招，慢的 Grok Bot 負責看錄影、寫標註、跑評測、補新招：用格鬥遊戲示範「狀態由程式算、動作從目錄挑、失敗變評測」的改善迴圈
- 一句話用途：英文作者 Ryan Perry 在個人部落格自述，用 Cursor Agent SDK 搭配 Jev 擴充跑內圈決策代理（作者文中每秒約 7.38 次決策、中位 95.5 ms），讓它在《Super Smash Bros. Melee》對 9 級 CPU；外圈交給 Grok Bot：上網研究各角色戰術並做成角色專屬的戰術目錄、重看對局寫標註、從真實紀錄建評測集並離線跑評測、調整代理直到分數上升，評測卡住時回到實戰找漏掉的情境並寫新戰術，新戰術須通過評測（必要時加實機演練）才進目錄。
- 核心目標：讓高速但能力有限的代理靠「確定性狀態＋已測試的戰術目錄＋由失敗累積的評測」持續變好，而不是靠更長的提示詞。
- 分類／標籤：代理評測迴圈／快慢雙層代理／戰術目錄
- 目標使用者：在做需要快速決策的代理（遊戲、即時控制、軟體工廠）並想建立評測與改善迴圈的開發者
- 實作門檻：進階開發
- 工具：Grok Bot（外圈：研究、標註、建評測、跑評測、寫新戰術）／Cursor Agent SDK＋Jev 擴充（內圈決策）／Super Smash Bros. Melee（模擬器環境，作者未在文中公開設定細節）
- 首次收錄／最近查證：2026-11-24 08:55（台灣時間）
- 證據狀態：`author-demo`（作者部落格自述，附決策紀錄、對局結束畫面數據與前後對照影片；原始碼與評測集未公開）
- 是否獨立重現：否

## 輸入與預期輸出

- 輸入：遊戲每一影格的原始數值（座標、速度、傷害%、殘機、動作狀態）；角色的招式影格資料；真實對局錄影與紀錄；作者自己的教練筆記（可選）。
- 輸出：由程式計算的型別化狀態（雙方狀態、離台邊距離、對手攻擊幾格後命中、哪些招現在打得到）；角色專屬戰術目錄（如 `laser_poke`、`recover_safe`、`approach_jab`）；標註過的評測集與分數；通過評測後新增的戰術（如 `recover_marth_under_jump_out`）。

## 來源版本

### 來源A：Ryan Perry／個人部落格（英文）

- 原始網址：[Grok Bot Taught My Jev Agent to Play Smash Bros](https://ryanperry.io/post/grok-bot-taught-my-jev-agent-to-play-smash-bros)，頁面標示 Published November 23, 2026；經 [Hacker News 投稿](https://news.ycombinator.com/item?id=50621336)（2026-11-23 23:54 UTC，台灣時間 2026-11-24 07:54）發現；原文語言：英文。本庫讀公開全文。
- 取得內容（翻譯摘要）：
  1. 分工：Grok Bot 維護外圈並改善評測；Cursor Agent SDK＋Jev 跑內圈代理——輸入是確定性計算出的狀態，輸出是從確定性戰術目錄中挑一個。
  2. 狀態由程式算：最初直接傳遊戲截圖，代理每次都得先從像素判斷位置。改成程式把每一影格整理成型別化狀態，包含截圖給不了的「對手攻擊還有幾格命中、我哪一招現在打得到、有沒有雷射飛來、對手是否在防禦」。問題從「圖裡發生什麼」變成「Falco 的 f-smash 11 格後命中，選哪個戰術？」；同一影格永遠得到同一狀態，所以每個決策都能事後重播與評測。
  3. 戰術目錄：一開始讓代理選每個按鍵，效果差。改由 Grok Bot 上網研究各角色戰術與連段，做成角色專屬的戰術目錄；代理只挑名稱，程式把名稱轉成搖桿與按鍵輸入。作者稱此後角色明顯變強，因為同情境反應一致。
  4. 評測：Grok Bot 重看對局、在每個時刻標出正確戰術（或作者自己指導一局、把筆記交給 Grok Bot）；從真實紀錄建評測集（例如所有「Falco 在刺拳距離內先打中 Fox」的影格）；評測不用開實機，直接呼叫實戰同一個 `decide()` 比對標註。
  5. 處理失分：Grok Bot 較慢但較靈活，負責決定怎麼處理錯誤——爬坡式調整代理並重跑同一組評測（近身組從約 54% 升到 96%，作者註明該組是被調校過的，不算獨立證明）；評測不再進步時，回到實戰找評測沒涵蓋的情境並寫新戰術，新戰術須過評測、有時加實機演練才進目錄。
  6. 實例：Marth 被打到台下就會死；改寫後的回復戰術通過所有離線評測，但實機從同樣的台下起點演練仍失敗——離線評測集根本沒有那種影格。Grok Bot 新增 `recover_marth_under_jump_out`（弧線能繞過台底時先跳出再上 B），經實機演練驗證後多數情況能回台，該演練之後固定在正式對局前執行。
- 作者報告結果：一局 Fox 對 9 級 Falco 中，606 次決策有 605 次及時送達、中位 95.5 ms、p95 127.5 ms、每秒 7.38 次；該局仍以 0:1 殘機落敗。作者把同一結構類比到軟體工廠：狀態（失敗測試、型別錯誤、diff）、目錄（遷移、升版等已測腳本）、評測（真實失敗變標註案例）、外圈（較慢較靈活的代理）。
- 缺口：沒有公開程式碼、評測集、Grok Bot 的指示或 routine 原文；勝率只有零星數字；遊戲環境與輸入注入方式未說明。「Jev」的身分與能力以作者描述為準，本庫未查證。

## 建議操作流程（依來源整理並由本庫補成步驟；未實測）

1. 先把環境狀態寫成程式：從原始資料算出型別化狀態，盡量把「快要發生什麼」也預先算好，確保同一輸入永遠得到同一狀態並存檔。
2. 請外圈代理（此例為 Grok Bot）研究領域知識，整理成有名稱的動作目錄；每個動作由程式執行，不讓內圈代理直接逐鍵操作。
3. 把真實紀錄交給外圈代理標註「此時正確動作」，建立離線評測集；評測呼叫與實戰相同的決策函式。
4. 每次改代理或目錄都重跑評測；明確區分「被調校過的評測組」與獨立驗證組。
5. 評測不再進步時，請外圈代理回看實戰失敗、找出評測沒涵蓋的情境，寫成新動作與新評測案例；新動作必須通過離線評測並在相同起點的實機演練中驗證，才併入目錄。

## 可複製提示詞（本庫原創，未實跑；改寫自來源流程）

> 你是外圈改善代理。資料夾〔紀錄路徑〕有內圈代理的決策紀錄與對局結果，〔目錄路徑〕是目前的動作目錄，〔評測路徑〕是標註評測集。請：1）找出最近 N 局失分或失敗的時刻，判斷評測集是否已涵蓋同類狀態；2）已涵蓋就調整代理並重跑評測，回報分數變化，並註明該組是否被調校過；3）未涵蓋就新增評測案例，再提出一個新動作（名稱、觸發條件、程式步驟）；4）新動作在通過離線評測與一次相同起點的實機演練之前，不得寫入正式目錄。最後列出改了哪些檔案與尚未驗證的地方。

## 所需連接、權限與限制

- 需要可程式化讀取狀態、注入輸入的環境；本來源未說明遊戲環境的取得與設定方式。
- 離線評測通過不等於實戰有效：來源中的實例正是離線全過、實機仍失敗；需保留實機或沙箱演練關卡。
- 在被調校過的評測組上的分數不能當獨立證明（作者本人也註明）。
- 不推定 Meta Muse 或 ChatGPT dots 能扮演同樣的外圈角色或能接同類 SDK。

## 驗收與可重現性

- 可驗收：同一影格是否得到相同狀態；評測集是否來自真實紀錄並附標註；每個新動作是否有離線評測與實機演練紀錄；分數報告是否區分調校組與獨立組。
- 本庫未重現。
