# UC-707：讓 Muse 把 1,900 則 Instagram 收藏分進 15 個主題集合：只准「新增」不准刪改、每 50 則停下等人說「下一批」，並用反向翻頁找回漏掉的貼文

- 情境：生活
- 標籤：整理、社群、人工確認、核對
- 網站標題：收藏爆量不想手動分類：Muse 依投稿者規則＋內文例外分批歸類，誤分類最多只是「多放一個集合」
- 一句話用途：日文作者 hiroomi0910 在 Qiita 自述，把超過 1,900 則、多半未分類的 Instagram 收藏交給 Muse：先盤點總數與既有集合，另建名稱明確的新集合（從 10 個逐步增至 15 個），每批 50 則依標題文字、hashtag、投稿者與 AI 摘要分類並加入集合，每批回報分項與保留清單，等人說「下一批」才繼續；兩天 35 批後取得的 1,714 則全處理完，1,445 則已分類、269 則保留。
- 核心目標：在大量個人資料上讓代理做批次整理，但把傷害上限壓到「多放一個集合」，並用實際成員而非畫面計數驗證。
- 分類／標籤：個人收藏整理／分批人工確認／只新增的安全設計
- 目標使用者：社群收藏、書籤或稍後閱讀清單堆積成百上千筆、想交給代理分類的一般使用者
- 實作門檻：工具串接
- 工具：Meta Muse（經 Meta 帳號中心連結的 Instagram 操作）／Instagram
- 首次收錄／最近查證：2026-11-25 08:40（台灣時間）
- 證據狀態：`author-demo`（作者 Qiita 自述並附結果與流程圖；文末註明文章由 Muse 撰寫、人編輯）
- 是否獨立重現：否

## 輸入與預期輸出

- 輸入：自己的 Instagram 收藏（開始時 1,911 則，既有 8 個集合共 760 則分配）；分類主題的初步清單。
- 輸出：15 個名稱明確的新集合（如「想去的店・美食」413、「料理・食譜・備餐」412、「出遊・活動・旅行」129）；每批的分類 JSON；`PROGRESS.md` 進度紀錄；附理由的保留清單。

## 來源版本

### 來源A：hiroomi0910／Qiita（日文）

- 原始網址：[【Muse活用法】Instagramの保存投稿約1,900件をMuseに整理させた話](https://qiita.com/hiroomi0910/items/6e59ccd8b548ac4e06d1)，2026-11-24 13:37 JST（台灣時間 12:37）；原文語言：日文。本庫經 Qiita 公開 API 讀全文。
- 取得內容（中文摘要）：
  1. 選 Muse 是因與 Instagram 同屬 Meta，不想再多接一個代理。作者描述 Muse 透過 Meta 帳號中心連結的帳號、以專用指令（CLI）取得收藏、建立集合並加入貼文；不是自動點瀏覽器，也沒把密碼交給 AI，連結可在帳號中心隨時解除。
  2. 安全規則：完全不動既有集合（不刪、不改名、不改內容）；不從收藏刪任何東西，只往新集合「加入」；不一次做完，每批 50 則、每批前插入人的確認；沒把握的不硬分，附理由列入「保留」。
  3. 不先設計完美分類：先建 10 個，主題累積到一定量再加（例如處理過 900 則後才建「美容・彩妝・保養」），最後 15 個。
  4. 每批流程：游標翻頁取 50 則 → 依標題文字、hashtag、投稿者、AI 摘要分類 → 加入集合（受 API 限制每 20 則一段）→ 以集合數量驗證 → 記進進度紀錄並回報分項與保留清單 → 人說「下一批」才繼續。分類用「投稿者規則＋內文例外」（例：食譜作者的貼文預設歸料理，但談清潔劑的歸打掃），純關鍵字比對會漏掉這類例外。
  5. 坑一：新到舊翻到最後一頁（`has_next_page: false`）只拿到 1,664 則；改舊到新再掃一次，多找到新到舊從未出現的 50 則，聯集 1,714 則；改頁大小 50→20 雙向重掃無新增，確定上限 1,714，約 195 則 API 始終不回傳（原因作者不斷定）。每頁名義 50 則實際有時 48、49 則，所以用實測不重複筆數管理進度。
  6. 坑二：加入後集合計數（`collection_media_count`）幾乎沒增加，但實際取成員確認已在集合裡——計數可能不算影片類或反映延遲，要用「計數＋實際成員」雙重驗證。坑三：標題被空格拆字的貼文會漏掉關鍵字分類，以投稿者規則與目視補救。
- 作者報告結果：兩天 35 批＋回收作業；1,714 則全處理，1,445 則分入 15 集合，269 則保留（只有照片、只有引導文字等），約 195 則取不到；進度檔讓中斷後可接續。
- 缺口：Muse 的實際指示與分類規則檔未公開；Instagram 連結功能與 CLI 的存在與範圍是作者描述，本庫未查官方文件。

## 建議操作流程（依來源整理並由本庫補成步驟；未實測）

1. 先盤點收藏總數與既有分類，決定「既有的完全不動、只新增」。
2. 先建少量名稱明確的新集合，主題累積到一定量再加，不預先建空集合。
3. 每批固定筆數：取資料 → 分類（投稿者規則＋內文例外）→ 加入 → 以實際成員驗證 → 寫進度檔並回報分項與保留清單 → 等人確認下一批。
4. 翻頁到底後再反向掃一次比對不重複筆數，差額記為「取不到」，不要假設翻到底就是全部。
5. 進度以實測不重複筆數計，進度檔放可續跑的位置。

## 可複製提示詞（本庫原創，未實跑；改寫自來源流程）

> 請整理我的〔服務〕收藏。規則：既有分類不得刪除、改名或移動內容；不得刪除任何收藏；只能把項目「加入」新分類。每批 50 則：依標題文字、標籤與投稿者分類，沒有把握的列入保留並寫原因；加入後以分類的實際成員確認，而不是只看計數；把本批結果寫進 PROGRESS.md，回報各分類筆數與保留清單，然後停下等我說「下一批」。全部翻完後，請反向再掃一次並回報兩次的不重複筆數差異。

## 所需連接、權限與限制

- 需要代理能以你的帳號讀收藏並建立分類；連結後代理能存取大量個人資料，作者以「只新增」與分批人工確認降低風險，不代表沒有隱私影響。
- 平台 API 可能不回傳部分項目（本例約 195 則），計數欄位也可能不準。
- 不推定 Grok Bot 或 ChatGPT dots 能操作 Instagram 收藏。

## 驗收與可重現性

- 本庫未重現。
