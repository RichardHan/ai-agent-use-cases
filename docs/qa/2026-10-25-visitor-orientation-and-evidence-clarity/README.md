# 2026-10-25 詳情頁目標讀者與結構化指引、語意化憑據解讀與行動步驟閱讀層級升級

## 決策與方案取捨

1. **方案 B：卡片快速洞察與首頁情境篩選即時連動加固（未採用）**
   - 在結果列表卡片上增加更多工具與適合對象摘要，並重新設計首頁情境與痛點標籤的雙向過濾連動。
   - 取捨：卡片資訊過密會在 320px/390px 窄手機上造成高度參差不齊或卡片過長；且若點開案例後仍維持原本折疊隱蔽、單薄概覽的詳情頁，無法解決訪客「點進去看不懂適不適合我、不知道下一步該怎麼做」的核心瓶頸。
   - 結論：不採用。

2. **方案 A（採用）：詳情頁結構化閱讀與可採用下一步升級**
   - **目標讀者與痛點識別**：從案例 Markdown 頁首精確解析「目標使用者」與「核心目標」，在詳情頁直觀呈現「適合對象」與「核心目標」，讓初訪讀者一秒判斷自己是否適用，降低試錯成本。
   - **語意化憑據解讀（Proof Note）**：定義完整的 `PROOF_DEFINITIONS`（涵蓋官方自報、作者報告／示範、公開資料核讀、模板／文件核讀、尚待查證），並在詳情頁警語下方提供誠實清晰的語意說明（例如：「社群作者公開分享的操作紀錄與示範，尚未取得獨立代碼庫驗證」），兼具桌面 hover tooltip 與無障礙閱讀。
   - **結構化入門建議與避坑指南**：將原隱蔽在 details 中的入門建議升級為語意清晰的 `.guidance-grid` 雙卡片（「🚀 怎麼開始」與「⚠️ 要注意什麼」），清楚標示「整理者設計，非實測結果」，建立誠實且具體的行動指引。
   - **手機視口工具列與卡片緊湊度優化**：調整手機端 `.detail-toolbar` 內邊距與間距，釋放頂部視野；採用 `minmax(min(240px,100%),1fr)` 與小螢幕單欄排版，徹底杜絕 320px/390px 視口水平溢出，全按鈕嚴格維持 >= 44px 觸控無障礙標準。

目標讀者：第一次造訪尋找 AI 應用解法並評估能否在自己工作中採用的工作者（工程師、產品經理、知識工作者、個人創作者）。
不處理範圍：不修改 Markdown 原始案例內容或重新分類 447 篇歷史案例；不引入外部框架、cookies、追蹤器或認證。

## 問題證據與實測數據

1. **走訪與可讀性缺陷證據**：
   - 修改前走訪 UC-005、UC-281、UC-313 等案例：詳情頁的「怎麼開始」與「要注意什麼」預設折疊隱藏在 details 中，訪客只看見一句話用途，看不到具體步驟與避坑注意；頂部僅有簡短的「作者報告／示範」badge，新訪客難以理解可信度邊界與驗證狀態。
   - Markdown 原文中的「目標使用者：同時維護多個網站或 App...」在前端未被解析呈現，讀者無法第一時間掌握適用對象。
2. **獨立審查反饋與針對性修正**：
   - 審查指出「模板／文件核讀」定義過於絕對（不宜稱「非真實環境運行結果」，因部分模板案例附有真實測試紀錄）；已修正為「基於開源模板、規格書或文件梳理，文件列出功能不代表已實測完成」，符合歷史案例事實。
   - 審查指出在未指定角色的 `span` 上使用 `aria-label` 違反 ARIA 規範；已全面移除 generic span 上的 `aria-label`，改以原生 `title` 及可見的 `.detail-proof-note` 提供完整可訪問性。
   - 審查指出 320px 窄螢幕下 `.guidance-grid` 原有 `minmax(240px,1fr)` 會因內部空間僅約 208px 造成潛在溢出；已修正為 `minmax(min(240px,100%),1fr)` 及小螢幕單欄排版。
3. **無障礙與視口量測**：
   - Axe-core 4.13.0 自動化掃描：首頁 0 違規、搜尋 0 違規、詳情頁 0 違規。
   - 桌面 1440×900、手機 390×844、極窄螢幕 320×568 實測：`scrollWidth <= innerWidth`，水平溢出 0px。
   - 工具列按鈕與互動元素尺寸全數維持 >= 44px 觸控標準。
4. **測試回歸**：
   - 全套測試由 290 項擴充至 295 項全數通過（`node --test tests/*.test.cjs`）。
   - 全站 JavaScript 語法檢查（`assets/*.js` 與 `tests/*.cjs`）0 錯誤。

## 三種具體情境走查紀錄

1. **情境一：任務導向檢索與詳情閱讀（PR 審查與程式碼驗證）**
   - 訪客想了解「AI 怎麼幫忙審查 PR 或做程式碼檢查」，從首頁點選「PR 審查」或輸入「PR」。
   - 結果清單即時顯示 205 筆收錄，點選 UC-005「讓 AI 寫功能，再找另一個 AI 挑問題」。
   - 詳情開啟：頂部看到「作者報告／示範」，下方即時解讀「社群作者公開分享的操作紀錄與示範，尚未取得獨立代碼庫驗證」；「可以幫你做什麼」下呈現明確任務目標；展開入門建議看見具體開始步驟與建立 PR 不等於功能完成的警示；Escape 精確返回原卡片。
2. **情境二：靈感抽卡與目標讀者精準判斷（多代理流水線）**
   - 訪客在首頁點選「寫程式與修問題」（開發），點擊「抽一張靈感」抽到 UC-281。
   - 點擊「看看怎麼用 →」進入詳情：頂部明確列出「適合對象：同時維護多個網站或 App、願意用多套代理分工的開發者」與「核心目標：把產品構想、實作與視覺驗收拆成可交接的代理流水線」；讀者立刻能對號入座評估是否契合自己的需求。
3. **情境三：邊界與異常狀態探索（空結果痛點恢復與分享連結直達）**
   - 訪客輸入不存在的字詞，頁面呈現 6 個高頻痛點標籤（日報、發票、PR、除錯、旅遊、比價），可一鍵重新定向結果。
   - 測試分享案例直鏈 `?case=UC-001`：頁面載入後自動開啟對話框，點選「複製案例連結」正確更新並提供剪貼簿操作。
   - 測試不存在編號 `?case=UC-999`：呈現「找不到這個案例」友好提示，保留原搜尋條件，並可點擊回到搜尋。
