## 問題與證據（修正前，正式站 2026-11-08）

第一次到訪的人不會先知道工具名稱，通常直接輸入一句日常說法。實際在正式站抽樣 20 句日常問題（不帶篩選），**12 句顯示 `0 / 509`**：

| 查詢 | 修正前 | 站上是否已有這些詞 |
| --- | --- | --- |
| 客戶抱怨 | 0 | 客戶 100、抱怨 4 |
| 合約到期提醒 | 0 | 合約 36、到期 27、提醒 124 |
| 回覆客戶信件 | 0 | 回覆 206、客戶 100、信件 39 |
| 檢查錯字 | 0 | 檢查 329、錯字 8 |
| 安排旅行 | 0 | 安排 39、旅行 36 |
| 一直退貨 | 0 | 一直、退貨 44 |
| 回覆訊息 | 0 | 回覆 206、訊息 135 |
| 帳單看不懂 | 0 | 帳單 57、看不懂 6（兩詞從未同篇出現） |
| 員工請假、發票對獎、想省錢、看不懂的帳單 | 0 | 無完整覆蓋的詞（維持 0 才是誠實結果） |

根因：`tokenize()`（`assets/app.js`）把一段連續中文視為**單一詞**，`filterEntries()` 對每個詞要求字面子字串命中並以 AND 串接，因此整串複合詞沒有任何一篇逐字包含就回傳 0。前幾輪補的空結果救援（`vocabularyRecoveryOptions`）只認案例標籤與同義詞鍵，所以「客戶抱怨」能救（建議客戶 100 筆），「員工請假」「檢查錯字」「回覆訊息」只能落到一組與原問題無關的通用捷徑。

## 兩個方案

- **A（採用）**：只在嚴格零結果時，把單一 4–10 字中文連續詞讀成「完整覆蓋原詞、彼此相鄰、且站上真的存在的詞」，以它們的 AND 重查；結果區上方明講拆了哪些詞、顯示幾筆，並提供「只找完整句子」切回原狀。價值：訪客不必先讀空狀態再點一次；風險：拆詞會改變顯示的結果集，因此必須限制在原本就是 0 筆的情況，並揭露拆詞事實。
- **B**：只把拆詞結果放進既有空結果救援清單（風險更低，但要多一次點擊，且無法改善「先看到 0 筆」的第一印象）。

選 A。為了把風險壓在原本就沒有結果的情境：任何已選篩選、或多詞查詢一律不拆（那類空集合通常是訪客自己的篩選造成，既有救援已會指出該移除哪一項）；拆出的集合必須非空且小於全庫一半，才算「有縮小」；`tokenize()`、同義詞表、排序與案例資料全部未改。

## 已知限制

- 拆詞不是語意理解：只認字面，且要求整串被既有詞完整覆蓋；`帳單看不懂`、`員工請假` 這類「站上沒有其中一個詞」或「兩個詞從未同篇出現」的說法仍是 0 筆，改由既有救援提供可用詞。
- 仍無法處理長句（如「我想要找一個可以幫我整理照片的工具」）：整句不是複合詞，維持 0 筆。這是下一輪的真正缺口。
- 「只找完整句子」的選擇不寫進網址，重新載入或分享連結會回到預設（拆詞）狀態；說明列本身會講清楚目前是哪一種。
- 本次以 509 筆 corpus 量的都是本機 Chromium；未量測低階手機或正式站效能，也未做真人使用者研究。
