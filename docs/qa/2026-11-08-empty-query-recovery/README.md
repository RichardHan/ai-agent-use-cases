# 2026-11-08 自然問句零結果的可核對救援

基準：origin/main `7f3ddcab415c9dd19164246f6b95252df819181f`（PR #262 合併後）。原工作樹有未提交修改，本輪全程在隔離 worktree 操作，未動原工作樹。

## 問題與證據（修正前，正式站 2026-11-08）

訪客以口語問句搜尋時，`tokenize()` 把整句當成單一詞做 AND 比對，因此「想省錢」「客戶抱怨處理」「看不懂的帳單」皆為 0 筆。空結果復原原本只從案例標籤（`tags`）找原句子字串，並要求命中數 ≤ 全庫 10%（509 筆時等於 50），把真正可用的詞全部濾掉：

- 本機以 24 句口語問句抽樣，15 句嚴格零結果。
- 正式站 `?q=想省錢`、`?q=客戶抱怨處理`、`?q=看不懂的帳單` 三種不同問題顯示完全相同的 55 個通用捷徑，第一項都是「郵件摘要 · 搜尋「郵件」」，沒有任何與原問題相關的選項。
- 以 `vocabularyRecoveryOptions` 前置探測：`省錢` 62 筆、`帳單` 57 筆、`郵件` 157 筆、`訂閱` 87 筆皆存在，只是沒有被列出來。

## 改動

`assets/app.js` 新增 `vocabularyRecoveryOptions`，在嚴格零結果、且沒有單一關鍵字移除可用時，改用站上既有任務詞彙（案例 `tags` ＋ `SYNONYM_MAP` 同義詞鍵）比對訪客原句：

- 只接受字面出現在原句、長度 2–6 個中文字、且命中數少於全庫一半（避免「等於沒縮小」的建議）。
- 依詞長、命中數排序，最多 3 個，標示實際筆數。
- 仍屬建議：只有點選後才替換關鍵字，並保留其他篩選；原句沒有可用詞彙時，維持原本的通用捷徑與既有提示。

未改動 `tokenize()`、`SYNONYM_MAP`、搜尋排序或任何案例資料，因此既有查詢的結果集不變。

## 效能（實測，Node 23.7.0、本機 M2、509 筆 corpus）

`vocabularyRecoveryOptions` 只在零結果時執行。以同一份 corpus 直接呼叫 20 次取單次耗時：常見口語問句（3 字）約 24ms；刻意組成 1,146 字、含數十個詞彙的極端問句約 159ms；純 ASCII 或空白問句 < 1ms。未量測使用者端裝置或低階手機，也未做正式站效能剖析。

## 獨立審查

由未參與實作的獨立 agent 依需求、完整 diff 與自行重跑結果審查：核心行為與三筆示例（省錢 62、帳單 57、客戶 100）、`scenario=生活` 的 17 筆、四個既有查詢的結果集不變皆複核通過，未發現執行期缺陷；指出兩項測試強度缺口（復原後總數只驗證 ≤ 承諾值、排序測試先排序再比較而看不出上限與比較器變化），已於第二個 commit 修正並重跑。該審查未執行 Playwright 或正式站，該部分以本文件的實測為準。

## 已知限制

- 原句完全不含站上詞彙時（如「想要便宜一點」）仍只有通用建議；本輪未擴充同義詞表。
- 建議只在零結果時出現，因此不改變任何既有查詢的結果集，但也無法改善「有結果但排序不佳」的情況。
- 空結果的 55 個通用捷徑仍在 300px 內層捲動區（手機 390px 寬為 2 欄），鍵盤需經過多個 tab stop 才離開；本輪未改動，列為下一輪候選。
- 未做真人使用者研究；以上皆為工程與瀏覽器驗收。
