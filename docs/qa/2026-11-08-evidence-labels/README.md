## 問題證據

證據標籤是訪客判斷「這項成果是誰說的、能不能信」的主要依據。實際走查正式站後，發現三類
標籤與案例原文互相矛盾（皆為 CONFIRMED，非推測）：

1. **頁首只要提到「模板」，就蓋掉作者自己的實測等級。** 分類鏈把 `模板` 當成子字串比對，
   且排在 `author-demo` 之前。9 篇頁首明寫 `author-demo（作者自述實測）` 的案例（UC-039、
   054、072、274、344、347、352、407、422）因此顯示「模板／文件核讀」，詳情頁同時出現
   「成果主張來源：開源模板／規格文件」與下方原文列出的 `author-demo（作者自述實測）`。
   這些案例也被排除在首頁抽卡池之外。
2. **廠商／原廠第一手自述被說成第三方分析。** 舊分類鏈沒有廠商分支，`V級廠商員工…自報`
   （UC-152、154）、`V，廠商作者…`（UC-167、177、211、260）、`官方署名…`（UC-020、021）、
   `官方建議…`（UC-033）落到預設值「公開資料核讀」，詳情頁因此寫「成果主張來源：公開文獻／
   第三方分析」——正好與該案的推廣利益相反。UC-154 的原文自己就寫著「廠商員工有產品推廣利益」。
3. **同一個標籤有兩套定義。** 卡片標籤與詳情憑據引用 `PROOF_DEFINITIONS`，但「來源標籤怎麼看」
   說明面板與篩選說明引用另一份 `SOURCE_TYPES`。以「官方自報」為例，前者寫「未經第三方獨立驗證」，
   後者只寫「包含官方的能力說明或案例自報」，把最重要的保留條件拿掉了。手機上標籤定義只存在於
   `title` 屬性（觸控無法顯示），說明面板是唯一讀得到的版本，而它是最弱的那一份。

## 兩個方案

- **(A) 依「頁首最先宣告的等級」重新分類，並把兩份定義合併成一份。** 只在分類函式與標籤表
  動手，案例 Markdown、搜尋語意、排序、來源連結全部不動。
- **(B) 反過來改 9 篇案例的 Markdown，把「模板」字樣從證據行移除，並新增第七個標籤
  「原廠／廠商自述」。** 資料更貼近語意，但要改動原始資料與篩選 UI，回歸面大且會動到既有計數。

選 **A**。B 會修改來源資料（本庫原則是不為呈現而改寫原始紀錄），且新增第七個標籤要同步
篩選、圖例、計數與既有測試，成本明顯較高；A 的風險完全鎖在「標籤」這一層。

## 獨立審查

由未參與實作的 agent 依需求、完整 diff 自行重新解析 509 筆並比對執行結果。它確認 19 筆轉換
與宣告一致、計數與抽卡池相符、圖例在 1440／390 與 `PROOF_DEFINITIONS` 逐字相同，並抓出三項
真實缺陷，已全部修正並重驗：

1. 第一方偵測漏掉「產品員工」（UC-107／108）與 `V＋B，服務商員工`（UC-328）寫法 → 已擴充
   前置級別與員工名詞；同時收緊避免誤判 `產品設計者`／`產品創作者`／`服務商自己的測試`。
2. `/^(?:原)?模板|模板／文件核讀/` 的第二個分支未加錨點，`author-demo…另提模板／文件核讀資料`
   會被誤判 → 已改為 `/^(?:原)?模板/`。
3. 統一定義後，「作者報告／示範」少了「實際產物、完整過程與成效仍須逐案核對」的提醒 →
   已併回單一定義字串。

一項不同意並保留：審查者主張 UC-016 因 `official` 排在前面應改判官方自報。本輪維持
作者報告／示範，理由是詳情頁同時要印出「成果主張來源」——UC-016 的 `official` 是權限**文件**，
成果主張者是作者本人；改判會把作者自述貼上「官方團隊／原廠自述」，正是本輪要消除的錯置
（UC-050／455／501／486／420 同型，前一輪已特意改離官方自報）。此判斷已寫入程式註解。

## 已知限制

- 分類仍是**字面規則**，不是語意理解。證據行若同時宣告多個等級，只取最先出現的一個；
  混合來源案例（97 篇列出兩種以上標籤）仍只顯示單一頁首標籤，hero 與 README 已提醒
  不能把頁首標籤套用到每項主張，本輪未改變這個模型。

- 品質結論只針對標籤與其說明；搜尋語意、排序、來源連結與案例內容皆未改動。
