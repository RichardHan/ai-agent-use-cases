# 2026-11-09 詳情頁「怎麼開始／要注意什麼」沿用案例自己的段落

## 問題與目標使用者

詳情頁的「怎麼開始」與「要注意什麼」不是固定文案，而是從案例 Markdown 的同名段落抽出來的（`assets/app.js`：`HOW_HEADINGS`／`LIMIT_HEADINGS`）。抽取靠一份標題詞彙表；詞彙表沒收錄的寫法會被靜默跳過，詳情頁改印通用句：

- 怎麼開始 → 「先閱讀原始報告與限制，再用小範圍、去敏資料設計自己的測試。」
- 要注意什麼 → 「本庫尚未獨立重現；先確認權限與驗收方式，不把案例報告當成成效保證。」

兩句都以「本庫整理步驟與限制（非實測結果）」的卡片形式出現，讀者分不出哪一句是這篇案例的說法、哪一句是圖書館的填充句。目標使用者是從分享連結或搜尋進到單篇案例、正判斷「這篇能不能照做」的訪客。

## 基準（修正前，`origin/main` `66d51754`）

用 vm 載入真實 `assets/app.js` 對 506 個案例檔逐一 `metadata()`：

- 通用「怎麼開始」：**11 篇**（UC-164、181、192、193、217、221、234、235、236、238、302）
- 通用「要注意什麼」：**5 篇**（UC-072、185、195、278、430）
- 另有 2 篇（UC-188、UC-195）把頁首欄位當成步驟發布：「作者／語言：…；原發布日期：2026-10-01T12:02:43.664Z」。

正式站 `?case=UC-192` 實測即為通用句；`?case=UC-185` 的「要注意什麼」也是通用句，而原文 `## 官方背景與界線` 寫了權限、信箱與成本缺口。

## 兩個方案

1. **在 `assets/copy.json` 逐篇手寫 how／caution（12 篇）。** 優點是立即好看；缺點是 12 段等於本庫替作者重寫內容，之後新增案例仍會落回通用句，且與「不要補寫成事實」相衝。
2. **擴充抽取詞彙表，讓原文段落被讀到。** 成本較高、要對全語料回歸；價值是修正的是抽取規則，之後同型寫法自動生效，發布的文字仍是案例自己寫的。

選擇方案 2。改動只加「詞彙」，不改抽取後的措辭、不改任何案例檔。

## 改動

`assets/app.js`：

- `HOW_HEADINGS` 在「介面承諾的寫法」與「工作流程寫法」之間插入一層，每一項都寫明是誰設計的流程，且詞組必須結束標題；括號註記必須寫明是設計或未實跑：`…(?:（[^）\n]*(?:未實|未執|設計|自設)[^）\n]*）)?\s*$`（`…` 為前述流程詞組）。括號內容不得跨行，未閉合的「（」不會吃掉段落本文。刻意不收裸的「練習／試做／試法」，也要求詞組落在結尾：`作者離線試做結果`、`作者離線試做（結果）` 是作者成果報告，`自設離線練習（提示詞）` 是提示詞，都不是指示。獨立審查第三輪抓到這兩個反例後補上括號條件。這一層排在 `流程／作者實作` 之前，因為同時寫了兩者的案例已經指明哪一段是本庫設計的流程。
- 新增 `HOW_HEADING_REJECT = /^#{2,3}\s*(?:可貼|可複製|指令|提示詞)|練習卷/`，透過 `guidanceTiers()` 既有的 reject 參數套用：`可貼指令（自行設計，未測）` 是要貼上的文字，不是步驟順序，不能變成「怎麼開始」。規則只看標題的主體，「建議試法與可貼指令」仍保留其中的步驟。
- `LIMIT_HEADINGS` 末尾追加一層 `(?:官方|來源|平台|權限|費用|工具|服務)[^。\n]{0,10}界線`，只在前兩層都沒有段落時才回答（`官方背景與界線`、`來源與界線`）；裸的「界線」會把 `去重與界線` 這類計數說明當成採用限制，故不收。

`tests/actionable-guidance.test.cjs`：新增 7 項（設計流程標題優先於作者紀錄、提示詞區塊不得成為步驟、全語料設計流程掃描、`界線` 發布為限制、較強的限制標題仍優先、只有 `界線` 的案例不得落回通用句、只提及流程的標題不得成為步驟）。

### 刻意不做

- **放寬「實作」排除規則**（讓 `實作與限制` 通過）。實測會讓 UC-445「原作者實作與限制」的作者敘述變成「要注意什麼」，UC-278「實作與限制」的第一行是作者步驟而非限制；兩個都是把敘述誤植為建議，故放棄，UC-278 維持通用句並列為已知限制。
- 下降到 H3 子標題取步驟（UC-181 的步驟只寫在 `可參考步驟` 的子標題下），以及「整段都是引用行」的案例（UC-072、430），屬另一個題目。
