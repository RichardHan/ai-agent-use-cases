## 兩個方案

- **(A) 採用：保留主要類別，補上同案宣告的其他類別。** 宣告以子句（`＋`／`；`）切開，逐句分類，回傳有序的 `proofClasses`；第一個元素就是既有優先序算出的主要類別，所以篩選、計數、排序完全不動（可逐 byte 比對）。詳情頁每個宣告類別一個徽章，第一屏寫「成果主張：主要 X；另宣告 Y」，完整憑據說明逐類列出主張者與短邊界；卡片維持單一可見標籤以免掃讀變慢，但在 `aria-label`／`title` 明說同案還宣告了哪一類。價值：修正實際的錯誤歸屬，且不動已驗收的計數語意。成本：`assets/app.js` 兩個純函式、三處 render、`reader.css` 一組樣式、兩支新測試。取捨：`來源類型` 篩選仍以主要類別計一次，必須在說明與提示中寫清楚。
- **(B) 不採用：讓 `來源類型` 變成多選、各類別重複計數。** 表面上更「完整」，但 462 筆作者案例的宣告裡常附帶「本庫提示詞為 designed」，逐類計數會讓「設計／未實跑」從 3 筆膨脹到 110 筆以上，把作者實跑紀錄稀釋成設計稿；且此站前幾輪才把「數字必須加得起來」寫成驗收條件，改成重疊計數會同時破壞計數語意與既有驗收。
- **(C) 不採用：只修 UC-514 的頁首文字（把 `official` 拿掉）。** 只改一筆資料，其餘 128 筆同形狀的宣告與 pending 結構問題仍在，且等於用資料遷就呈現。

## 已知限制

- 截圖影像在此環境無法檢視，視覺結論以 DOM 文字、幾何、可見性與 axe 為準；未量測實機、低階手機或螢幕閱讀器。
- `來源類型` 篩選仍是單一主要類別；同案宣告的其他類別只在卡片提示與詳情出現，不會讓該案在那些類別的篩選結果中出現。這是刻意的計數口徑（每案計一次），已寫進篩選提示與來源判讀說明。
- 類別只從頁首證據說明行解析，且只認明確宣告：反引號標記的 `official`／`author-demo`／`designed`／`unverified`、子句開頭的 `unverified`／`designed`／模板，以及「作者自述／自報／實測…」這類陳述句。順帶一提，只是提及模板頁或把未核欄位寫成 `unverified` 的句子不再被算成一類（6 筆案例因此不再宣稱「模板／文件核讀」），只設計提示詞、沒有執行紀錄的子句也不再被算成「作者報告／示範」（UC-496）。這是本輪修正的一項過度歸屬，不是功能退步。
- `designed` 有時指「本庫提示詞未實跑」、有時指作者自己設計未實跑，兩者都列為「設計／未實跑」並沿用同一份主張者文字（提示詞設計者）。本輪不推測子句指的是哪一方。
