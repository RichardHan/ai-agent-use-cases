## 問題與目標使用者

目標使用者是「首頁載入較慢或失敗時，被首頁那行 fallback 連結送進索引頁」的訪客：`index.html:18` 寫「載入較慢時，可先在本站閱讀完整案例索引」。這頁同時也是鍵盤與低頻寬讀者的主要替代入口。

正式站 `/INDEX.html` 實測（同一次載入，Chromium）：

| 項目 | 1440×900 | 390×844 |
| --- | --- | --- |
| 頁面總高 | 62,107px | 108,157px |
| 案例表起點 `#case-list` | y=9,077 | y=19,853（約 23.5 個視窗） |

也就是說：被送來「先看案例」的訪客，先讀到 6,000–14,000px 的研究日誌，才看到第一筆案例；而唯一說明資料新鮮度的句子，位置在這些日誌之後。

同一頁的三個內容問題（皆可由程式與資料核對）：

1. `INDEX.md` 的「更新日期：2026-10-20」比同頁列出的內容舊 19 天——頁面已在 2026-11-08 收錄 `UC-508`–`UC-511`（`cases/511-…md` 的「首次收錄／最近查證：2026-11-08 08:52」）。
2. 「請以逐案計數報告的當前批次為準」沒有說那個批次是什麼時候、用多少頁量出來的；該批次其實是 2026-10-22 20:50、當時 420 個主要案例頁（`sources/qualification-audit-2026-10-16.md:3,7`），而索引現在列 503 筆。370／1,000 與 503 筆並排時沒有共同基準。
3. 研究日誌分成兩段、排序方向相反（前半 2026-10-22→10-17 新到舊，後半 2026-10-23→11-08 舊到新），最新一筆在檔案最後一行，沒有任何說明。

既有的回歸只守住「案例表列數＝`cases/` 檔數」與「主要案例（N）」；`更新日期`、批次日期、日誌順序完全沒有測試（`grep 更新日期 tests/` 為 0 筆）。

## 兩個方案

- **A（採用）**：把案例表移到索引頁最前面；把日期句換成可由資料重算的三個事實（筆數、最新 `頁首核對` 日、本頁校對日）；研究日誌整段移到頁尾並加上「歷史快照」說明與 `#research-log` 錨點；在把計數委派給稽核報告的那句話裡補上該批次的日期與當時的頁數。
- **B**：用 Liquid（`site.github.build_revision`／`builtAt`）在 Pages 建置時產生日期與筆數。成本接近，但 `INDEX.md` 同時是 GitHub 上的原始 Markdown 入口，Liquid 在 GitHub blob 會顯示成原字串；而且建置時間會在只有文件變動的部署時也更新，等於宣稱資料比實際新鮮。索引是人工維護的檔案，靜態事實＋漂移測試較誠實，也兩邊都可讀。

選 A：變更集中在一個 Markdown 檔與一支新測試，不動前端程式、資料與計數規則。
