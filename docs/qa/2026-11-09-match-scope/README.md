同一批資料暴露兩個既有缺陷：

1. 沒有說明。220 筆的畫面沒有任何一句話說其中 196 筆只是正文提及，讀者只能從第一張卡猜。
2. 措辭不實。既有 `#purpose-gap` 只在使用途命中為 0 時出現，並寫「下列 4 筆是**字面命中**」。實測 `出差報銷` 的 4 筆全部是**同義詞**命中（`報銷→對帳／核帳／reconciliation`），沒有一筆同時含「出差」「報銷」；`播客摘要` 的提示說沒有案例在做這件事，第一張卡卻正是把 Podcast 轉成整理文。這與本站「分開表達來源與驗證狀態、不編造」的承諾相反。

目標讀者：從首頁任務入口進來、心裡已有問題但不知道工具名稱的人；他們看到的第一個數字目前會誤導他們放棄或亂點。

## 兩個方案

- **(A) 採用：把筆數拆開講，並給一鍵收斂。** 當「只在正文或標籤命中」≥ 三分之二時，結果行下方寫出兩個數字（兩者相加等於結果總數），並提供「只看那 N 筆」；按下後沿用同一組查詢與篩選、把命中範圍設為「標題、用途與痛點」，網址與可移除條件同步。用途命中為 0 時保留既有的單字退路，但改掉「字面命中」的說法。
  - 價值：不動比對與排序，召回完全不變（沒有為了精準而漏掉案例的風險），但訪客一次點擊就能從 220 筆收斂到 24 筆，且筆數不再假裝全部相關。
  - 成本：`assets/app.js` 一個 render 區塊＋一個純函式、`index.html` 一個元素、`assets/style.css` 一段、2 支測試。
  - 取捨：手機 390×844 上這個提示會把第一張卡推到第一屏之下（實測 779 → 916px），代價與限制見下。
- **(B) 本輪不做：收斂同義詞組。** 實測 `審核` 同時屬於「審查」與「核准」兩組，`SYNONYM_MAP['審核']` 因此是兩組聯集；「核准」組本身命中 506 案中的 279 案（55%），因為「核准」是本站幾乎每篇限制段都會出現的治理詞。只拆「審核」一組就讓 3 支測試紅燈，其中 `信箱清理` 是靠錯誤的同義橋接（清理→審查→巡檢）才找到正確案例 UC-014；`報帳審核` 66→2、`發票報帳` 17→2、`出差報銷` 4→0。
  - 價值：直接修召回精度，是上一輪留下的最大題目。
  - 成本與風險：需逐案判斷產品語彙並改寫 11 支召回期望（`tests/problem-compound-queries.test.cjs` 目前把 `出差報銷` 的第一名釘在會計案例 UC-263，與同檔註解「應為 UC-284」互相矛盾）；在沒有逐案證據前改測試，等於把「降低斷言」當成果。

選 A：它把「筆數代表什麼」說清楚並提供收斂路徑，召回零變動、回歸風險可控；B 需要先確立語彙決策，屬獨立一輪。

## 獨立審查與後續修正

獨立 reviewer（未參與實作、獨立上下文，`ScientificOwl`）讀 diff、重跑全部套件（532 項、四支瀏覽器流程）並自行探測 165 組查詢／篩選組合後，指出五點；前四點已修並重新驗證，第五點列為限制：

## 已知限制

- 門檻是產品判斷（2/3），不是統計結論；它只決定「要不要多說一句」，不改變哪些案例被搜到。
- 「只在正文或其他欄位提到」是依站上的命中範圍欄位計算，不是語意理解：同義詞仍可能讓不相關案例通過（`報帳審核` 的 1 筆用途命中仍可能是別的事）。
- 手機 390×844：提示與動作可見（790 / 781 < 844），但第一張卡從 779 移到 916，需要一次短捲動；320×740 的動作按鈕需短捲動才完全可見（753–797，視窗 740；改動前該尺寸第一張卡已在第一屏之外）。
- 整句查詢按下收斂後，搜尋框會換成站上實際搜尋的詞（例如「會議、整理」），不是原本那句話；這是為了讓承諾與畫面用同一個條件。
- 收斂後回到全文只能透過「命中範圍」選單或移除條件 chip，沒有在提示位置提供「也看全文的 N 筆」；本輪未做雙向切換。
- 未量測真人、低階手機、螢幕閱讀器或正式站效能；未處理同義詞精度（方案 B）。
