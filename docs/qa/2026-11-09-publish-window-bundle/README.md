## 兩個方案

- **A（採用）整包是自描述檔案：接受「不比目錄舊」的整包，來源固定到整包自己的建置。**
  - 價值：換版空窗不再把完整語料丟掉；訪客用 1 個請求拿到 513 筆，來源連結也對得上實際讀到的文字。
  - 成本：`assets/app.js` 1 個驗證函式與 1 個固定條件、2 支測試（1 支改寫為新契約）、1 支瀏覽器回歸、`website-qa.yml` 1 行。
  - 取捨：`catalog.json` 與 `corpus.json` 的建置仍可能不同步，這是發布層的事；本輪只在客戶端容忍「較新」的方向。
- **B 讓兩個 manifest 永遠來自同一建置**：把目錄併進 `corpus.json`，或由建置輸出單一檔案。
  - 價值：從根本移除兩個檔案的耦合。
  - 成本：改動 Jekyll 發佈契約、快取鍵與所有讀取端（含 `published-version.cjs` 與多支發布檢查），回歸面大；本輪不做。

採用 A 的理由：它只放寬「較新」這一小段，仍保留「較舊或缺檔就退回逐篇」的保護；發布契約不動，回歸風險集中在一支已有多項測試的載入路徑。比較字串是 `site.time` 的 `%Y%m%d%H%M%S%N`：必須是 23 位數字才比較，其他格式（含長度不符的數字字串）維持原本嚴格相等，避免用猜測的順序放行。

## 驗收條件

1. `catalog.json` 較舊、`corpus.json` 較新且路徑集合完全相同 → 只發出 1 個 `corpus.json` 請求、0 個 `.md` 請求，513 筆完整。
2. 整包較舊、或路徑集合不同、或格式損壞 → 仍退回逐篇（不得把不完整語料當完整）。
3. 用整包載入時，內文的「GitHub 原始 Markdown」固定在**整包自己的** `sourceRevision`；逐篇備援仍不固定。
4. 前後畫面在相同資料與限速下，修正後第 9 秒已有 24 張卡與完整統計。
5. 首頁 390、結果 1440、詳情 390 的 axe 違規為 0；水平溢出 0。
