## 兩個方案

- **(A) 讓結果頁自己說清楚（採用）**：批次剩餘筆數夾住不為負；抽卡池改稱「可抽案例卡」並在差額時寫出「另有 N 筆不是可抽案例」；新增「命中性質」提示，當沒有任何案例的標題／用途／痛點同時包含查詢字詞時先說明，並提供一個站上真的有的單字（附實際筆數）。
  - 價值：修正矛盾與負數，並在訪客掃第一張卡之前說明限制。
  - 成本：`assets/app.js` 1 個 render 區塊、`index.html` 1 個元素、`assets/style.css` 1 段、1 支瀏覽器測試。
  - 取捨：不動排行與同義詞，因此「員工排班→輪班作品」這類跨任務誤配仍在（見限制）。
- **(B) 收斂跨任務同義詞組（本輪不做）**：把「報銷／對帳」、「審核／清理／過濾」、「審核／核准」拆開。
  - 價值：實測 `報帳審核` 由 66 筆降到 2 筆、`出差報銷` 由 4 筆降到 0 筆（站上確實沒有出差報銷案例）。
  - 成本與風險：會同時改動 11 支既有 recall 測試的期望（`tests/search.test.cjs`、`problem-compound-queries.test.cjs` 等），必須先決定產品語彙，屬下一輪工作。

## 獨立審查與後續修正
獨立 reviewer（未參與實作、獨立上下文）讀 diff 並重跑測試，指出 `syncDiscovery()` 的 `discoveryKey` 以「情境｜門檻｜可抽池 id」組成，只改其他篩選（例如收錄狀態）而池不變時不會重繪，`drawPoolMatches` 卻已更新，於是面板印出的兩個數字對不上新的結果數。已重現：`會議` 26 筆（24 可抽＋2 筆其他）→ 勾「用法靈感」後結果 25，面板仍寫「24 張可抽案例卡（另有 2 筆…）」。修正方式是把狀態句拆成「計數前綴 + 其餘文字」，池鍵未變時重算前綴，且只在目前文字仍以本程式上一次寫入的前綴開頭時才改寫，避免覆蓋載入中、載入失敗與空池訊息。`tests/result-count-honesty-browser.cjs` 新增該篩選步驟並斷言「可抽＋其他＝結果數」；`tests/keyboard-search-entry.test.cjs`「相同池不改寫狀態列」的既有契約仍通過。

同一輪審查另指出四點，前四項已修、第五項記錄為限制：

1. **空池分支沒有一起修（阻斷）**：空牌組的 `discoveryKey` 恆為 `"||"`，換字詞時提前返回，面板與佔位文字停在舊的「符合的 N 筆」。已改為由 `emptyPoolText()` 依目前的 `drawPoolMatches` 重建，並以 `drawStatusMode` 區分「計數列／空池列／其他訊息」；`tests/result-count-honesty-browser.cjs` 新增「模板來源＋摘要 → 會議」步驟，斷言空池不得殘留舊筆數。
2. **「只在正文出現」在有篩選時讀起來是全站宣稱**：改用全站（不帶 facet）的用途欄位計數判斷這句，動作承諾的數字仍用所選條件的計數。
3. **有篩選時動作整個消失**：改為兩個來源——篩選內有字詞可用就保留篩選，全都 0 時退回全站最佳字詞，按鈕明寫「（清除目前篩選）」並在點擊時清掉情境、收錄狀態、門檻、工具、主題、來源類型與排序；實測 `播客摘要`＋來源類型「官方自報」→ 按鈕 25 筆，點擊後 25 筆、篩選清空、URL `?q=摘要&scope=overview`。
4. **按鈕的 `aria-describedby` 指到「主題」範圍說明**：改指 `#purpose-gap-message`，描述與按鈕實際採用的「標題、用途與痛點」一致。
5. **效能**：`render()` 多一次 `filterEntries`（提示出現時每個字詞再各一次）。reviewer 實測 18 組查詢多為 0–1.6ms、長句無差異；語料再翻倍時需快取，列入限制。

## 已知限制
- 提示只判斷字詞是否「同時」出現在標題／用途／痛點，不是語意理解；同義詞仍可能讓無關案例通過（實例：`員工排班` 經「輪班」同義詞命中 UC-317 的標題，因此不觸發提示）。
- 抽卡差額只說筆數，沒有逐一列出哪一筆不可抽（經驗補充、待查線索、模板或重複 id）。
- 提示依輸入即時出現／消失，但不是 live region；螢幕閱讀器使用者要靠讀到結果前的順序發現它。
- 本輪未處理：手機首頁到第一個案例的行動成本（390×844 搜尋框 y≈2,583、首卡 3,367）、詳情頁核讀狀態在第一屏之外、`512 筆收錄` 與 `506 案例頁` 的口徑說明。
- 未量測真人、低階手機、螢幕閱讀器或正式站效能。
