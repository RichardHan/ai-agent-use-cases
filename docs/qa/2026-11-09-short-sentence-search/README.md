## 問題與目標使用者

目標使用者是第一次到站、用日常中文描述「想解決什麼」而不知道工具名稱的人。站上的嚴格比對要求每個詞都是字面子字串，`tokenize()` 又把一整段中文視為單一詞，所以這類問句常是 0 筆。上一輪（#268）加了「整句零結果時用站上詞彙重讀」，但前置條件是**去空白後 ≥ 10 字**。

| --- | --- | --- | --- |
| 每月信用卡帳單整理 | 9 | `0 / 509`，說明列隱藏，只有空結果建議 | 同句加一個「啊」→ 37 筆＋說明列 |
| 整理家族旅遊行程 | 8 | `0 / 509` | 同句加「了」仍 0 |

所以本輪不是新增一種解讀，而是把站上原本就提供的字面替換，改成預設顯示並要求說明列與「只找完整句子」切換同時出現。

以 40 句日常短問句在同一份 509 筆語料上量測：修正前 18 句落在「0 筆且沒有重讀」，修正後 5 句。

## 兩個方案

- **A（採用）**：把重讀門檻由「去空白後 ≥10 字」改為「≥5 個中文字」，其餘條件與揭露方式完全不動。
- **B**：改寫判準為「句中含站上詞彙，且該詞之外還有其他字」。看似更貼近語意，但實測這類「涵蓋率」判準會擋掉「整理家族旅遊行程」這種多詞問句（反而更糟），且要重跑既有 28 句長句基準，回歸面明顯更大。

選 A：風險鎖在原本就是 0 筆的情境，選詞、窄度、說明列、「只找完整句子」切換都沿用上一輪已測試的規則。

只計**中文字**而非全部字元，是為了保住既有設計：`旅遊 xyz987` 這種任務詞加自訂字串的查詢仍應是精確查詢，不能自動替換。

獨立複審另外指出：`整理履歷表 2025`（5 個中文字＋數字）在初版會重讀成「履歷」＋「整理」，把訪客打的年份默默丟掉；第二次複核又指出 `整理履歷表 GPT` 同樣會丟掉 `GPT`。因此 5–9 個中文字的短句帶若含任何英數 token（工具名、年份、版本、金額）就維持精確查詢：重讀只重寫中文行文，訪客自己打的 token 不該被略過。這是刻意的行為取捨：`每月信用卡帳單整理 2025` 由基準的 37 筆（忽略 2025）改為誠實的 0 筆，空結果頁仍提供「原問題包含「帳單」→ 搜尋 57 筆」。

## 已知限制

- 仍是字面比對，不是語意理解；重讀只保證「這些字出現在案例裡」，不保證案例解決同一個問題。單一過寬詞仍可能偏寬（例如「查詢股票價格」重讀為「價格」104 筆，全庫 1/3 為上限）。
- 英數守門只套用在 5–9 個中文字的短句帶。10 個中文字以上的問句仍可能忽略句中英數 token（基準版本已是如此，例如「每月信用卡帳單整理 2025」在基準重讀為 37 筆），本輪沒有同時改兩個規則；這是下一輪可以接續的缺口。
- 句中沒有站上詞彙的問句仍是 0 筆（電池中 5/40），本輪沒有新增同義詞或語意索引。
- 本環境無法檢視截圖影像，視覺判斷以 DOM 文字、筆數、axe、水平溢出與 `pageerror` 為準；截圖保存供人眼複核。
- 未量測真人訪客、低階手機或螢幕閱讀器；本站沒有追蹤器，無法取得實際查詢分佈。
- 尚未在正式站驗證；發布後需以 `catalog.json` 的 `sourceRevision` 與實際查詢核對。
