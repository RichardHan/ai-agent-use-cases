## 問題證據

### 為什麼不改推測規則就好

試過「句內否定就不算觸發」（例：`未公開…腳本` 不算），會連帶把 UC-483（Muse VM＋Kotlin／Gradle／adb／Android 模擬器）與 UC-302、UC-475 降級成較低門檻——那三案確實需要本機或程式環境，只是原文的否定句剛好包住唯一觸發詞。**在字面層面改規則，等於把一個錯誤換成另一個錯誤**；`cases/368`（Unreal Engine 本機匯入）也是同一形狀。所以本輪不調推測規則。

## 兩個方案

- **A（採用）案例可宣告門檻，未宣告才推測，且介面標明哪一種。**
  - 價值：把「讀者要什麼環境」交回案例頁（那是唯一知道答案的地方），推測值仍可用但不再冒充事實；已確認誤判的案例立刻修正。
  - 成本：`assets/app.js` 3 處（宣告解析、卡片、詳情）、`assets/style.css` 1 行、`templates/case.md` 1 行、9 個案例各 1 行、2 支既有測試檔追加 6 項。
  - 取捨：宣告是人工判斷，必須逐案看工具與步驟；推測規則本身仍是字面比對，未宣告的新案例仍可能誤判（介面已標示）。
- **B 只改文案**：在篩選說明加一句「門檻為本庫推測」。成本最低，但已確認誤判的案例仍然錯，`免寫程式` 篩選仍看不到 UC-063／UC-111／UC-472。

選 A：錯誤已在資料層確認，只加警語等於把已知錯誤留給讀者；而宣告欄位是既有案例頁首格式（`- 情境：`、`- 工具：`）的自然延伸，不需要新資料檔或第二次真相來源。
