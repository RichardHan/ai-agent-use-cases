## 問題證據

目標使用者是**讀到一條已結案的待查線索、要知道它去哪裡的人**，以及**用鍵盤讀詳情的人**。

`5de8fa98` 把 `mergedInto` 改成清單後，`resolved` 仍只看狀態行的日期，和「有沒有記錄目的地」無關。`resolvedPendingNote()` 對沒有目的地的條目回空字串，畫面其餘位置直接把空清單接進句子。為了重現這個形狀（今日 4 條線索都已有目的地），本輪在一份 `sources/pending.md` 複本加上一條只寫 `狀態：2026-11-10 已處理`、沒有 `併入 UC-nnn` 的 P-009，另建預覽（513→514 筆，僅供對照，不是站上資料）。`c4bef514` 的畫面：

| 介面 | 基準顯示 |
| --- | --- |
| 詳情徽章 | `待查線索・已併入`（後面沒有對象） |
| 結果卡徽章 | `已併入 （不另計數）` |
| 列印／詳情警示 | `待查線索已處理：已併入 ，不列為獨立案例…` |
| 交接區 | 完全不出現（條件是 `mergedInto?.length`） |
| 結案註記 | 完全不出現（`resolvedPendingNote()` 回空字串） |
| 統計註記 | `另有 3 個待查線索已處理並併入案例`（其中 1 筆沒有去向） |
| `待查線索` 篩選選項 | `（含 3 筆已併入，統計不計）` |

同一版還有一個鍵盤缺陷：`refreshMergedDestination()` 只要「任何一個目的地已載入」就重建整個 `.detail-merged-actions`，而它在每次語料刷新／補讀後都會被呼叫。實測（正式程式碼、390×844、`?case=P-004`，聚焦 UC-101 後呼叫一次沒有新目的地的刷新）：焦點從 UC-101 掉到 `BODY`，`document.activeElement` 離開 `<dialog>`；真有目的地晚到時也一樣，且新增按鈕會把正在讀的區塊往下推。

另外 `assets/copy.json` 的 P-004 `how`／`caution` 仍是上一輪之前的文字（「先以少量公開公告對照去敏能力摘要…先核對主案例的來源版本」），讀起來像尚未執行的單一計畫，與畫面上「已併入 UC-101、UC-102」不一致。

## 三個方案

- **A（採用）把「已處理」與「已併入」分成兩個狀態，並讓晚載刷新只在真的有新目的地時重建。**
  - 價值：沒有編號時畫面不再留下空的「已併入」，統計與篩選不再把它算成併入；鍵盤讀者不會因為背景刷新被踢出對話框，閱讀位置也不跳動。
  - 成本：`assets/app.js` 6 個顯示點＋刷新邏輯＋2 個統計字串、`assets/copy.json` 1 筆、`README.md`／`sources/pending.md` 各一段、3 支測試追加。
  - 取捨：`resolvedPendingNote()` 對「已處理但無去向」由回空字串改成回如實說明，屬既有契約變更（測試同步改）。
- **B 只把空字串換成「未記錄」三個字。** 成本最低，但統計與篩選仍說「已併入」，列印頁尾與卡片也還是空的。
- **C 回查 Git／研究檔補上目的地。** 會替來源檔補事實，違反本庫「不補寫」原則；且今日沒有這種條目，不該先改資料。

選 A：錯誤是「兩個狀態被壓成一個」，正確修法是把狀態分開並在介面說清楚，而不是補一個形容詞。

提出 1 項阻擋：

- **（已修）目的地晚到時可能用錯錨點**：原本以「重建前的第一個已載入入口」量位置，卻用「重建後第一個入口」校正，兩者不一定是同一個目的地。若缺的是排在前面 UC-101、讀者聚焦在 UC-102，UC-101 晚到會把 UC-102 往下推 54px，焦點雖然還在對話框內，閱讀位置卻跳動。修法：以聚焦目的地的 `data-merged-target` 為錨點，重建後找回同一個 ID 再補償 `dialog.scrollTop`。驗證（390×844，兩種到達順序）：缺 UC-102 時聚焦 UC-101 到達後位置 0px、`scrollTop` 不變；缺 UC-101 時聚焦 UC-102 到達後位置 0px、`scrollTop` +80（內容在上方長高），焦點都留在原本的目的地且在對話框內。
