## 問題證據

目標使用者是**用「這篇最近有沒有被核對」判斷要不要相信內容的訪客**，以及用首頁「最近核對的內容」找新資料的人。

- 網站只從頁首欄位取核對日（`assets/app.js:reviewDate()` 只讀第一個 `## ` 之前、且欄位名帶查證動作的行；這個「只認宣告、不從正文推測」的規則是刻意的，見 `app.js:879-887` 註解）。研究批次後來在正文追加 `## 2026-11-05 08:53補充：…` 時，並沒有回頭同步頁首欄位。
- 量測（同一份 511 頁語料）：**98 頁**的頁首核對日比它自己最新的帶日期標題還舊，其中 **42 頁差 ≥7 天**、4 頁差 ≥14 天，最舊差 **23 天**：
  - `cases/026-school-deadline-list.md` 頁首 `2026-10-13`，正文 `## 2026-11-05 08:53補充：…（不另計）`。
  - `072`（19 天）、`322`（16 天）、`293`（15 天）、`332`（13 天）。
- 這些標題都是本庫自己的核對紀錄，不是來源發布日：026 的那一節寫「X API 讀全文」「標記：作者自述；沒有截圖…」「不另計」，是讀來源的紀錄。全庫 270 個比頁首新的帶日期標題，語氣集中在 `補充`（228）、`補充 S-0xx`（7）、`補核`（6）、`補證`（3）、`覆核`、`併入來源`、`社群變體` 等本庫動作。
- 訪客看到的後果（1440×900，本機 preview `origin/main` 建置）：
  - 卡片與詳情顯示「頁首核對 2026-10-13」，但同一頁正文寫 2026-11-05 讀過新來源。
  - `?sort=reviewed`（首頁「最近核對的內容 →」的目標）把 UC-026 排在第 **508／518**，UC-005 第 142、UC-322 第 238 — 都排在比它們舊的頁面後面。

## 兩個方案

- **A（採用）改資料：把頁面自己最新的補充日寫回頁首宣告。**
  - 對 98 頁各加一行 `- 本次增補查證：<該頁最新帶日期標題的日期>；只核該節新增來源，未重驗全案。`（4 頁該節是計數／覆核而非新增來源，寫「依正文該節補核，未重驗全案」）。日期全部取自該頁自己的標題，不從正文推測任何新事實；`templates/case.md` 本來就規定這個寫法，網站也已支援（`REVIEW_DATE_KEY` 含 `本次增補查證`）。
  - 成本：98 個檔案的 1 行。風險：新增欄位可能被別的解析器讀到（已逐頁比對 11 個欄位，只有 `reviewedDate` 變；第一版插在頁首最前面時 `date` 欄位也被改變，因此改為插在頁首最後一行）。
  - 不採 **B（改程式：把正文帶日期標題也當核對日）**：那會讓網站從散文推測日期，違反本庫「只認宣告」的既有規則（分類、核對日、證據等級三處都是這個原則），而且正文標題日之後若被引用成來源發布日就會直接汙染信任訊號。資料缺漏就補資料，不改判準。
  - 也不採 **C（只改文案說「核對日可能較舊」）**：98 頁的宣告就是錯的，加註只把錯誤寫得更清楚。
