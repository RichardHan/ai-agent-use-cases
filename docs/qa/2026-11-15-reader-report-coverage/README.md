## 問題證據與目標使用者

目標使用者是**開啟案例詳情、希望在進入繁複的研究正文前先快速通讀作者真實操作紀錄與第一手成果（「原文紀錄先讀 · 非本庫實測」），評估該案例是否值得深入研究的訪客**。

全庫 524 個來源檔（含 520 篇案例）掃描與正式站（Chromium 1440×900、390×844、320×740）實測確認：
1. **閱讀器原文先讀識別盲區**：
   `assets/reader.js` 的 `selectReadingSection()` 中，第一優先級別匹配模式先前定義為：
   `/^(?:問題.*(?:實作|結果|成果|實際使用)|(?:原)?作者.*(?:實作|實際|做了|結果|完成範圍)|來源報告(?:與限制)?)$/`
   該正則在尾端使用嚴格行尾錨點 `$`，且動詞表未涵蓋全庫大量案例使用的習慣性陳述句式（例如以「什麼」結尾的 `作者實際做了什麼`、`原作者實際做了什麼`、`作者做了什麼`、`原作者做了什麼`、`作者做過什麼`，以及 `作者報告的流程與限制`、`作者報告及證據限制`、`原作者做法與證據`、`來源報告與界線` 等）。
2. **訪客體驗影響**：
   在全庫 520 篇案例中，高達 **155 篇案例**雖然正文內有結構完整且小於 3,200 字元的精確作者實做/報告段落，卻因標題未精準貼合原行尾模式，被閱讀器判定為未匹配（回傳 `-1`），進而在案例詳情頂部退回通用提示橫幅：
   `「這篇未提供適合提前完整呈現的短段落。請從原始研究核對實作、來源與限制。 開啟原始研究 ↓」`
   訪客無法在第一屏直接閱讀作者的第一手操作與限制紀錄，必須多點擊一次折疊面板展開全文尋找，增加了探索摩擦與資訊判讀成本。

## 兩個可行方案與取捨

- **方案 A（採用）**：
  在 `assets/reader.js` 中優化 `selectReadingSection()` 的第一層 pattern：
  `/^(?:問題.*(?:實作|結果|成果|實際使用)|(?:原)?作者.*(?:實作|實際|做了|做過|結果|完成範圍|做法|報告)|來源報告(?:與限制)?)/`
  1. 移除嚴格末尾 `$` 限制，並在動詞/名詞集合中補充 `做過`、`做法`、`報告`。
  2. 保持前導保守過濾函式 `eligible()` 100% 不變，嚴格排除包含 `本庫|設計|建議|預期|提示詞|補充|未測|未實|可參考` 或字元數大於 3,200 的章節，確保任何整理者推測、未測指令或歷史補充絕不會被誤提取為作者成果。
  3. 取捨：零修改案例 Markdown 內容，零改動現有 365 篇已匹配案例之段落選取；全庫「原文紀錄先讀」覆蓋率從 365 篇（70.2%）大幅提升至 **447 篇（86.0%）**（淨增 **+82 篇案例**）。
- **方案 B（不採用）**：
  批量修改全庫 82 篇案例的 Markdown 標題，強制將其改為 `## 作者實作與結果`。
  - 取捨：破壞原始案例檔案的提交歷史與語境表述，增加不必要的大規模檔案 diff，並可能影響既有外部引用或錨點定位。
